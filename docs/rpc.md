# varanda — UI <-> node RPC contract, version 1 (normative)

This document is the single normative reference for `@varanda/rpc` (`packages/rpc`): the JSON contract between the user interface (React Native app, web) and a Varanda node, which is the in-app Bare worklet (over IPC), `varanda-serve` (over a loopback WebSocket) or the browser node of `@varanda/web-member` (in memory, in the same page). Names, values, shapes, messages and constants are exact. Record formats, reason strings, the feed and the sync rules are those of `docs/protocol.md` (cited below as "protocol §n"); this document only says how they travel.

Conventions: CommonJS ES2020 with `'use strict'`, standard style, zero dependencies, no Node built-ins and no `Buffer` (the package loads unchanged in a Metro / react-native-web bundle, in Node >= 20 and in Bare; it uses only `Uint8Array`, `DataView`, `ArrayBuffer.isView` and `setTimeout`; UTF-8 is encoded and decoded in pure JS, section 3, because Bare has no `TextEncoder` / `TextDecoder`). Code and identifiers in English; every message a user can see is pt-BR. Tests use brittle (`npm test -w packages/rpc`).

Terms: `key` = `hex64` = exactly 64 lowercase hex characters; `ref` = `'<hex64>:<seq>'` with canonical decimal `seq` (no leading zero, a safe integer); "chars" = Unicode code points (`Array.from(s).length`, exactly as `packages/core/lib/records.js` measures them); "bytes" = bytes of the UTF-8 encoding.

## 1. Envelopes

Every message is ONE JSON object of one of three kinds. The protocol version is `v: 1`.

```json
{ "v": 1, "id": 7, "method": "post.create", "params": { "text": "olá" } }
{ "v": 1, "id": 7, "ok": true, "result": { "seq": 3, "ref": "<hex64>:3" } }
{ "v": 1, "id": 7, "ok": false, "error": { "code": "USAGE", "message": "registro inválido: text-length" } }
{ "v": 1, "event": "sync.event", "seq": 1, "data": { "runId": 1, "line": "sync ready" } }
```

- Request: exactly the keys `v`, `id`, `method`, `params`. `params` is always present and is a plain object (`{}` when the method takes none).
- Response: exactly `v`, `id`, `ok`, `result` when `ok` is `true`; exactly `v`, `id`, `ok`, `error` when `ok` is `false`. `result` is always a plain object. `error` has exactly `code` (a wire code, section 7) and `message` (a string of at most `MAX_ERROR_MESSAGE` = 200 UTF-16 units).
- Event: exactly `v`, `event`, `seq`, `data`; `data` is a plain object whose keys are fixed per event (section 6).
- `id` is a safe integer in `1..2147483647` (`MAX_ID`) chosen by the client and unique among ITS pending requests; an id may be reused once its response arrived. `seq` starts at 1 on every connection and increases by exactly 1 per event sent.
- Rejected (code `USAGE`): any key other than the listed ones at any level of an envelope (`error`, `data`, and `params` through the per-method key sets of section 5), a missing key, `v !== 1`, a bad `id`, an unknown method (prototype names such as `toString` are unknown), a non-object or array `params`, an array or `null` where an object is required, a non-plain object, and a request whose `id` is already pending on that connection (`'id repetido'`).
- `validateRequest(obj)`, `validateResponse(obj)`, `validateEvent(obj)` return `{ ok: true, value }` (a fresh envelope; for a request, `value.params` is the normalized params of section 5 with defaults filled in) or `{ ok: false, code: 'USAGE', message }`, and never throw, whatever the input (hostile getters and proxies included). Messages name a field, never echo a value.

An oversized event is replaced by the event `warning` `{ line: 'evento grande demais' }` with the same `seq`.
- Worst-case response sizes (checked by `test/sizes.test.js`). The most expensive character on the wire is a lone surrogate: `records.js` counts it as one char and accepts it in names and texts (a peer can write it), and `JSON.stringify` writes it as `\udXXX`, 6 bytes. A 4-byte UTF-8 character costs 4 bytes, `"` and `\` 2 bytes, LF (`\n`) 2 bytes; every other character JSON escapes (C0 controls) or `jsonLine` escapes (DEL, C1, U+2028/9, bidi controls) is forbidden in names and texts. Every other field takes its maximum: hex64 keys, `seq` = 9007199254740991, `at` = `'+275760-09-13T00:00:00.000Z'` (the longest canonical ISO), `id` = `MAX_ID`, and `skipped` / `future` full (100 entries each, reason `untrusted-association`), and every post carries `MAX_MEDIA_PER_POST` (4) descriptors with the longest `mime` and the widest number in every field (one descriptor 242 bytes, the list of 4 is 973 bytes). Every profile, PeekItem and Notice carries the widest avatar: `{ core: hex64, mime: 'image/webp', start: 8184, blocks: 8, bytes: 262144, sha256: hex64, width: 512, height: 512 }`, 235 bytes.
  - `feed.read`: one item (`kind`, 80-char name, 20-char username, 1000-char text, a reply, `quote: null`, 4 descriptors) is at most 7,790 bytes; a quote item (`replyTo: null` and a `quote`) is never larger and a repost item is smaller. 31 items = 261,964 bytes (fits, 180 bytes to spare) with `incomplete` full (16 hex64 keys) and `incompleteTruncated` at its widest; 32 items = 269,754 bytes (does not fit), so `FEED_LIMIT_MAX` = 31. With 4-byte characters instead of lone surrogates 32 items would be 199,508 bytes, but the lone-surrogate case decides. FeedItems carry no bio. (Re-measured when items gained `kind` and `quote`.)
  - `peek.read`: a PeekItem is a `feed.read` item plus `round` (<= 100000) and the author's `avatar`, so its worst case is a post with a reply or a quote ref (never both; a repost item is smaller); the envelope adds `next` (a cursor with the widest `round`, `at`, `author` and `seq`) and `diaries` / `skipped` of 4096. 31 items = 249,810 bytes with lone surrogates (fits, 12,334 bytes to spare). There is no `skipped` / `future` list, so it has more margin than `feed.read`; `PEEK_LIMIT_MAX` = `FEED_LIMIT_MAX` = 31 and the "one more does not fit" boundary is not asserted. (Re-measured when items gained `kind` and `quote`.)
  - `log.read`: one entry (a quote record of 1000 chars, with `replyTo: null`, a `quote` and 4 descriptors, 13 bytes more than a reply record) is at most 7,201 bytes on the wire; a profile record (80-char name, 280-char bio, with or without an avatar) is at most about 2.5 KB and a certificate record has fixed-size fields, so posts are the worst case. 36 entries = 259,414 bytes (fits, 2,730 bytes to spare); 37 = 266,615 bytes do not, so `LOG_LIMIT_MAX` = 36. (Before media the maxima were 35 and 42.) An `invalid` entry (`{ seq, reason }`) is smaller than any entry it replaces in the window.
  - `diary.peek`: 36 entries of worst-case quote records plus a profile (80-char name, 280-char bio, the widest avatar) and a 20-char username = 261,887 bytes (fits, 257 bytes to spare); every split of the 36 requested seqs between `entries`, `invalid` and `missing` is at most that, so `PEEK_SEQS_MAX` = 36.
  - `engagement.read`: 62 liked and 62 reposted refs = 10,483 bytes.
  - `notices.list`: 64 notices (the longest `kind`, an 80-char name of lone surrogates, the longest username, the widest avatar, the `post` ref of a repost, a three-key cursor and the flags) = 67,511 bytes (about 26% of `MAX_MESSAGE`).
  - `profile.read`: one profile (hex64 author, 80-char name, 20-char username, 280-char bio, the widest avatar) is at most 2,535 bytes; the envelope with empty lists is 71 bytes. 100 profiles = 253,670 bytes (fits, 8,474 bytes to spare); the largest count that fits is 103 (261,278 bytes; 104 = 263,814 bytes does not), so `PROFILE_LIMIT_MAX` = 100 leaves a margin. A `missing` entry (a hex64 key, 66 bytes) is smaller than the profile it replaces, and duplicates are folded, so `profiles` plus `missing` never exceed 100 entries.
  - FeedItems carry no avatar (followed authors' avatars come from `profile.read`), so `feed.read` and `log.read` are unchanged.
  - `group.read`: one item (hex64 `writer` and `diary`, 1000-char text of lone surrogates, a reply, four maximal private media items, `hidden`, 80-char name, 20-char username) is 8,852 bytes. Each private item is 492 bytes: the ciphertext descriptor (no `width` or `height`) plus `key`, `nonce`, `plainMime`, `plainSha256`, `w`, `h`, `ms` (5.39). 29 items plus the envelope (`next`, `hidden`, `incomplete`, `sealed`, `epoch`, `state`) = 257,137 bytes (fits, 5,007 bytes to spare); 30 = 265,990 bytes (does not fit), so both `GROUP_LIMIT_MAX` and `GROUP_LIMIT_DEFAULT` are 29. Public descriptors and text-only posts are smaller.
  - `group.members`: 100 members (80-char name, 20-char username, flags, `joinedAt`) = 67,081 bytes.
  - `community.info`: 32 groups (`MAX_GROUPS_PER_COMMUNITY`) with 80-char names of lone surrogates, `visibility`, `join`, `role`, `general`, a maximal `last` (80-char name, 20-char username, 140-code-point preview of lone surrogates, longest ISO `at`) and `unread` 99 on every row, plus a lone-surrogate community name = 68,184 bytes (about 26% of `MAX_MESSAGE`).
  - `community.list`: 64 communities (`COMMUNITY_LIST_MAX`) with 80-char names of lone surrogates, `join`, `state`, `role` and `general` = 44,924 bytes (about 17% of `MAX_MESSAGE`). `community.members` and `community.requests` are paged like `group.members` (`GROUP_MEMBERS_LIMIT_MAX`).
  - `follow.list`: 500 keys = 33,581 bytes (about 13% of `MAX_MESSAGE`).
  - `dm.thread`: a DM text is well formed (`packages/core/lib/dm.js`), so no lone surrogate reaches it and a 4-byte character is its widest code point. One message (32-hex `id` and `replyTo`, hex64 `from`, 1000 four-byte characters, the longest ISO `at`, `mine`, and 4 media items of 357 bytes each: the longest mime, 257 chunks, the largest ciphertext `bytes`, sides of 16384) is 5,661 bytes. The sealed frame cannot carry that much text with that many items (protocol section 11), so this is a bound, not a message that exists. 46 messages plus the envelope (`next`, `folder: 'request'`, `blocked`) = 260,540 bytes (fits, 1,604 bytes to spare); 47 = 266,201 bytes (does not), so `DM_THREAD_LIMIT_MAX` = 46.
- No method takes a filesystem path, a data dir, an association key, a bootstrap list, a DHT host, a secret key or a limit override. Those are node configuration, fixed when the node starts; a request carrying any of them fails on the unknown key.

## 3. Framing

### IPC (byte stream: the in-app worklet)

Each message is a 4-byte unsigned big-endian length followed by exactly that many bytes of UTF-8 JSON (the envelope). There is no other framing and no token (section 11).

UTF-8 codec (`lib/text.js`, pure JS):

- `utf8Encode(str)` -> `Uint8Array`. A lone surrogate in the JS string is written as U+FFFD (`EF BF BD`), exactly like `TextEncoder`; a surrogate pair is one 4-byte character. (Envelopes never reach it with a lone surrogate: `JSON.stringify` escapes them as `\udXXX`.)
- `utf8Decode(bytes)` -> string, strict: overlong forms (`C0`, `C1`, `E0 80..9F`, `F0 80..8F`), surrogates U+D800-U+DFFF (`ED A0..BF`), code points above U+10FFFF (`F4 90..`, `F5..FF`), truncated sequences and stray continuation bytes throw `TypeError('UTF-8 inválido')`. A BOM is kept as U+FEFF (and then fails `JSON.parse`). Its accept/reject decisions and output are identical to `new TextDecoder('utf-8', { fatal: true, ignoreBOM: true })` (checked by `test/utf8.test.js` on an edge-case table and a seeded fuzz of 5,000 byte strings).

- `encodeFrame(obj, max = MAX_MESSAGE)` -> `Uint8Array`. Throws `RpcError` `USAGE` when `obj` is not a plain object (`'mensagem não é um objeto'`) or its body exceeds `max` bytes (`'mensagem grande demais'`).
- `createFrameDecoder({ max = MAX_MESSAGE, onMessage, onError })` -> `{ push(chunk), failed }`. `push` accepts any `ArrayBufferView` and handles any chunking: a header split across chunks, several frames in one chunk, one byte at a time. The length is checked against `max` BEFORE the body buffer is allocated, so the decoder never allocates more than `max` bytes for a body (plus its fixed 4-byte header buffer).
- Protocol errors: length 0, length > `max`, invalid UTF-8 (`utf8Decode` above), invalid JSON, a top level that is not a plain object, or a chunk that is not an `ArrayBufferView`. On the first one `onError({ code: 'USAGE', message })` is called ONCE, the decoder enters its failed state (`failed === true`) and every later `push` is ignored. The transport MUST then close the stream. Frames fully decoded before the error were already delivered.
- The node decodes with `max = MAX_REQUEST`; the UI decodes with `max = MAX_MESSAGE`.

The pure JS codec is still needed. Measured on 2026-10-28 in the debug app on an Android emulator (API 36, x86_64), with the same 70 cases run in Node, in Hermes and in the Bare worklet (encode: ASCII, 2, 3 and 4 byte characters, U+10FFFF, NUL, BOM and lone or reversed surrogates; decode with `fatal: true, ignoreBOM: true` and with the defaults: valid input, truncated, overlong, surrogate, above U+10FFFF, stray and invalid bytes, BOM, views with an offset, `ArrayBuffer`, `DataView`, `stream: true`, labels, `encodeInto`, 200 KB):

- **Bare** (v1.33.4, bare-kit 0.16.0): `TextEncoder` and `TextDecoder` are not defined, so the worklet cannot use them. The codec is the only UTF-8 in the IPC framing there.
- **Hermes** (React Native 0.83.10, Hermes 0.14.1): both exist and match Node on all cases. `TextEncoder` is native. `TextDecoder` is not: Expo's UTF-8 fallback (`expo/src/winter`, expo 55.0.31) provides it, so it depends on that runtime being installed. The app uses them in `src/account.js`, `src/report.js` and `src/indexClient.js`.
- Not measured: iOS, a release bundle, a real device.

### WebSocket (`varanda-serve`)

One text frame per message, no length prefix. A binary frame is a protocol error (the transport closes the connection).

- `parseMessage(text, max = MAX_MESSAGE)` -> `{ ok: true, value }` or `{ ok: false, code: 'USAGE', message }`: a non-string is rejected; then the UTF-8 byte length of `text` is checked against `max` (computed without allocating, a lone surrogate counting 3 bytes); then `JSON.parse`; then the top level must be a plain object. Never throws. The server parses with `max = MAX_REQUEST`.

### In memory (the browser node)

The browser node (`packages/web-member/lib/node.js`, loaded by the web app as `varanda-node.js`) and the page's client exchange exactly what the WebSocket carries: one JSON text per envelope, in both directions, delivered asynchronously (the app uses a microtask). The node parses each request with `parseMessage(text, MAX_REQUEST)` and the client each response or event with `parseMessage(text, MAX_MESSAGE)`; a request that does not parse closes the connection, as on the WebSocket. No object is shared between the two sides. One connection at a time: a second `connect` closes the first.

## 4. Session

- `session.open` MUST be the first request on a connection. Any other method before a successful `session.open` -> `UNAUTHORIZED` `'sessão não aberta'`. A second `session.open` -> `USAGE` `'sessão já aberta'`.
- Token rule: a dispatcher created with `token` = a string (WebSocket) requires `params.token` and compares it with `tokensEqual`; one created with `token: null` (IPC) requires the open to carry NO token, and any token given is rejected. A failed open answers `UNAUTHORIZED` `'token inválido'`, then the dispatcher closes itself and calls `onProtocolError`; the transport closes the connection (one guess per connection).
- Events are sent only after a successful `session.open`.

## 5. Methods

Mutating methods (`MUTATING`, exported as a frozen array; test with `isMutating(method)`): `identity.create`, `cert.add`, `profile.set`, `profile.delete`, `username.add`, `post.create`, `post.reply`, `post.quote`, `post.delete`, `like.set`, `repost.set`, `follow.add`, `follow.remove`, `sync.start`, `sync.stop`, `node.close`, and the IPC-only host controls `identity.install`, `identity.clear`, `identity.reset`, `identity.forget`, `identity.sessionSaved` and `media.uploadFile` (5.50 to 5.56), `page.register` (5.87) and `identity.recoveryBind` (5.94, it rewrites the kv passkey record). All others are reads (`account.sign`, `report.sign`, `terms.sign`, `invite.sign`, `push.sign`, `age.sign` and `page.sign` sign but write nothing, 5.18, 5.20, 5.29, 5.30, 5.31, 5.32 and 5.84; `page.read` and `page.feed` only read, 5.85 and 5.86; `age.proof` stores a verified attestation in local storage only and is idempotent, 5.83; `recovery.sign` signs but writes nothing, 5.90, and the IPC-only recovery controls `identity.recoveryLookup`, `identity.recoveryOpen` and `identity.recoveryWrap`, 5.91 to 5.93, change no stored state (no diary, no kv record): lookup holds one wrap key in the worklet's memory, open consumes it whatever the outcome (a repeated open fails, 5.92), and wrap only draws a fresh nonce for a blob nobody has stored yet).

The IPC-only host controls of the in-app web node (5.50 to 5.56) carry what the browser handle does in-page (section 11). The in-app web node never offers the legacy-follows confirmation (the handle's `follows` API, section 11): its storage is created fresh and therefore has no unsigned follow list, so its host handle reports no legacy follows.

Params have an exact key set: every key not listed for the method -> `USAGE` `'parâmetro desconhecido'`; a missing required key -> `'parâmetro obrigatório: <name>'`; a wrong type or bound -> `'parâmetro inválido: <name>'`. Defaults listed below are filled in by `validateRequest` / `validateParams(method, params)` before the handler runs; the client sends the params exactly as given.

Results keep the field names of the CLI `--json` output (protocol §7, `apps/cli/lib/commands/member.js`). Results are produced by the node (T6); the dispatcher checks only that a result is a plain object and fits `MAX_MESSAGE`.

### 5.1 `session.open`

- Params: `{ token?: string, 1..256 chars }`.
- Result: `{ protocol: 1 }`. Handled by the dispatcher itself; it never reaches a handler.

### 5.2 `node.info`

- Params: `{}`.
- Result: `{ publicKey: hex64 | null, memberCert: boolean, memberCertDate?: string | null, ageVerifiedDate?: string | null, ageSince?: string | null, ageSinceUntil?: string | null, followCount: integer, sync: SyncState, publicDht: boolean, groups?: true, accountOrigin?: string }`.
  - `publicKey`: the own diary key, `null` when no identity was created yet.
  - `memberCert`: block 0 of the own diary holds a member certificate that passes `certForKey` against the trust root.
  - `memberCertDate`: the `date` field of that verified certificate (v1 and v2 member certificates alike, a canonical ISO-8601 UTC string covered by the issuer's signature), exactly as stored in block 0; `null` when `memberCert` is `false`, and also `null` (with `memberCert` unchanged) while a v2 certificate's `issuer` is in the revoked issuers of the stored blocklist snapshot. The date is cached with its issuer, and the issuer is checked against the current snapshot on every `node.info`, so a revocation a sync adopts later applies on the next call and a later snapshot that lifts it brings the date back. It is read only from the own diary's block 0 after `certForKey`, never from a peer or the URL. Present in the answer of the browser node session (`packages/web-member`, which the native app's worklet also runs in hosted mode); the core Node session does not send it. The app compares it with the age-since attestation (`ageSince`, `ageSinceUntil` below): the account service issues no certificate to a key without a recorded age band, so a certificate dated in the window `ageSince <= memberCertDate <= ageSinceUntil` means the age check was done for this account. The window counts only for a v2 certificate signed by the same issuer as the attestation: `node.info` answers `ageSince` and `ageSinceUntil` as `null` otherwise, so an issuer never vouches for another issuer's certificate or for a v1 association-signed one.
  - `ageVerifiedDate`: the `date` of the age-verified attestation stored by `age.proof` (5.83, kv `ageVerified`) when it verifies now for the own diary key, the configured association and the revoked issuers of the stored blocklist snapshot (`verifyAgeVerified` with `{ revokedIssuers }`, `packages/core/lib/age-proof.js`, protocol section 3 "Age attestations"); `null` otherwise (none stored, no identity, an attestation from a revoked issuer, or a stored object that does not verify, which is ignored). The kv is writable by the device owner, so the node re-verifies the stored object on each cold read (the first after the session starts, `identity.reset`, a new key pair setting, or a change of the stored blocklist snapshot, so a revocation a sync adopts later applies on the next `node.info`) and then caches the result, like `memberCertDate`.
  - `ageSince`: the `since` of the age-since attestation stored by `age.proof` (kv `ageSince`) when it verifies for the configured association (`verifyAgeSince`); `null` otherwise. Re-verified and cached like `ageVerifiedDate`. It is not per member, so it survives a new key pair setting but not `identity.reset`. Issuer binding: answered only while block 0 holds a v2 member certificate whose `issuer` equals the attestation's `issuer` (the cached certificate issuer, compared on every `node.info`); `null` with no certificate, a v1 certificate or a certificate from another issuer, even when the stored attestation verifies. `ageVerifiedDate` is not bound.
  - `ageSinceUntil`: the `date` of that same stored age-since attestation, under the same re-verification, revoked-issuer and caching rules; `null` whenever `ageSince` is `null`, so under the same issuer binding. The attestation vouches only for member certificates dated in `[ageSince, ageSinceUntil]`, so a saved older attestation never covers a certificate issued after it was signed.
  - `ageVerifiedDate`, `ageSince` and `ageSinceUntil` are read from the kv area only: `node.info` never opens a store and never preempts a sync for them. Present in the answer of the browser node session only; the core Node session does not send them. The app opens its age gate only from these fields: `ageVerifiedDate !== null`, or `memberCertDate !== null` and `ageSince !== null` and `ageSince <= memberCertDate <= ageSinceUntil` (canonical ISO strings compare in time order).
  - `followCount`: `follows.json` length.
  - `sync`: as `sync.status` (5.16).
  - `publicDht`: `true` when the node was started against the public DHT (no bootstrap override). Always `false` for the browser node, which uses no DHT (its only peer is the configured seeder).
  - `groups`: `true`, present in the answer of the BROWSER node only; the Node session (`packages/core/lib/session.js`) does not send the field, although it implements the group methods 5.36 to 5.49.
  - `accountOrigin`: a public https origin (`'https://<host>'`), present only when `varanda-serve` was started with `--account-origin` (`apps/cli/lib/serve/server.js` adds it to the session's answer). The app reads it as `config.accountOrigin` and shows the Páginas of a core node through that account service (5.84 to 5.87). Not a secret.
- It carries no path, no secret, no association key, no bootstrap list and no DHT host.

### 5.3 `identity.create`

- Params: `{}` (the association is node configuration).
- Result: `{ publicKey: hex64, association: hex64 }`, as `id create --json`. Idempotent: same key on every call. Never a secret key.

### 5.4 `identity.show`

- Params: `{}`.
- Result: `{ publicKey: hex64, association: hex64 }`, as `id show --json`. No identity -> `NOT_FOUND` `'identidade não encontrada'`.

### 5.5 `cert.add`

- Params: `{ cert: object }`: a plain object with `JSON.stringify(cert)` at most `MAX_CERT_BYTES` (4096) bytes. Only shape and size are checked here; the node verifies it (`certForKey` against the trust root, `cert.member` = own key).
- Result: `{ seq: 0 }`, as `cert add --json` (an identical block 0 already present is ok without append). Expected errors: `USAGE` `'certificado inválido (<reason>)'`, `USAGE` `'certificado já gravado'`.

### 5.6 `profile.set`

- Params: `{ name: string 1..80 chars, bio?: string 0..280 chars, avatar?: AvatarDescriptor | null }`; `bio` defaults to `''`. `avatar` has no default: an absent `avatar` stays absent in the validated params. An AvatarDescriptor is a media descriptor (5.7) with `mime` in `AVATAR_MIMES`, `width` = `height` = `AVATAR_SIDE` (512), `blocks` <= `MAX_AVATAR_BLOCKS` (8) and `bytes` <= `MAX_AVATAR_BYTES` (262144); anything else -> `USAGE` `'parâmetro inválido: avatar'`.
- Result: `{ seq, ref }`. (`profile set --json` prints only `{ seq }`; `ref` = `'<own hex64>:<seq>'` is added so the three publishing methods share one shape.)
- Control characters are checked by the node's record builder (`USAGE` `'registro inválido: control-chars'`), not here.
- `avatar`: absent = keep the newest own avatar; `null` = remove it (one plain profile record); a descriptor = set it.
  - Browser node: a descriptor deep-equal to the avatar of the newest own profile is kept without verification (its item may live in another device's media core, protocol §2). Any other descriptor must pass the verification of post media (5.8: one of this device's own declared media cores, every block local, the byte count and SHA-256 matching) and its bytes must read as a still 512x512 image (`stillImageSize`, `packages/core/lib/still-image.js`); otherwise `USAGE` `'mídia inválida'` and nothing is appended. A write that leaves an avatar in effect (a new one, or an absent `avatar` while the newest own profile has one) appends the compatibility pair (protocol §2) in ONE append; `seq` and `ref` are those of its second block. Any other write appends one plain record.
  - Core node, `varanda-serve` and the CLI: a non-null `avatar` -> `USAGE` `'mídia disponível só na versão web'` before anything is opened; an absent `avatar` while the newest own profile has one -> `USAGE` `'perfil com foto: mude o nome e a bio na versão web ou tire a foto'`; otherwise (absent with no avatar in effect, or `null`) one plain profile record.

### 5.7 `post.create`

- Params: `{ text: string 0..1000 chars, media?: [MediaDescriptor] }`: `media` is 1..`MAX_MEDIA_PER_POST` (4) descriptors with exactly the keys and ranges of protocol §2 (a sparse array is invalid); without `media` the text must have at least 1 char (`'parâmetro inválido: text'`), with it the text may be empty (a photo-only post).
- Result: `{ seq, ref }`, as `post --json`.

### 5.8 `post.reply`

- Params: `{ to: ref with seq >= 1, text: string 0..1000 chars, media?: [MediaDescriptor] }` (lowercase hex, canonical seq; block 0 is never a post), with the same `text` / `media` rule as 5.7.
- Result: `{ seq, ref }`, as `reply --json`.
- 5.6 to 5.8 require block 0: `USAGE` `'grave o certificado de membro antes de publicar'`; an invalid record: `USAGE` `'registro inválido: <reason>'`.
- `media` (5.7, 5.8): the descriptors come from the browser node's upload control (section 11), never from the bytes over RPC. The browser node accepts a descriptor only when it points into one of this device's own media cores that the own diary declares among its latest `media-core` records, with every block local and the byte count and SHA-256 matching; otherwise `USAGE` `'mídia inválida'` and nothing is appended. A post with media is never queued in the app's outbox (it needs the seeder now). The core node and `varanda-serve` answer `USAGE` `'mídia disponível só na versão web'` for any `media`, before anything is opened.

### 5.9 `follow.add` / 5.10 `follow.remove`

- Params: `{ key: hex64 }`.
- Result: `{ changed: boolean, followCount: integer }`: `changed` as in `follow` / `unfollow --json`, `followCount` = the length of `follows.json` after the call. The CLI's `follows` list is deliberately NOT returned, so a change that was written can never be turned into an oversized-response error; the UI re-reads `follow.list`. Expected errors: `USAGE` `'não é possível seguir a própria chave'`, `USAGE` `'limite de diários seguidos atingido'`.
- Follows are public and shared by every device of the member: the change is also written to the own diary as a `follow` record (protocol §2). The core node appends it in the same call once block 0 exists (protocol §7 `follow`). The browser node needs the identity unlocked (locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`) and is local-first: the call answers at once (kv `follows` and `followsPending` change together), and every queued change is signed with the identity key (Ed25519 over the UTF-8 of `'varanda-follow-op-v1\n' + key + '\n' + ('1' | '0') + '\n' + at + '\n' + <own key>`); the queue keeps one change per key (the newest wins) and at most `MAX_INVENTORY - 1` changes. The session later appends the pending changes as `follow` records itself, through the write gate and a push, only while the identity is unlocked and block 0 exists, verifying each signature first: a change without a valid signature (for example one planted in the storage of a signed-out profile) is dropped and never signed into the diary, the same rule as the app's text outbox. The drain appends at most one change per key (the newest `at`) and skips any change whose key already has a diary `follow` record with an `at` at or after the change's `at`; the record reuses the change's own `at`, so a consumed or older change is never appended again (copies and replays are no-ops). The queue is capped at `MAX_INVENTORY - 1` both when read and when written (a "drain": coalesced, at most one queued, never while a user's once run is alive; a failure is the warning `aviso: seguidos ainda não enviados` and the changes stay pending, retried on the next own-synced of a continuous run at most 3 times in a row). A device's follows from before `follow` records existed are never published automatically (the old local list cannot be authenticated): the page asks the person through the handle's `follows` controls (section 11), and only the confirmed keys become signed changes; until then the device keeps its old list locally and its fold does not apply other devices' follows. A device with nothing to confirm marks itself done on its own. Changes made on another device arrive through the sync's fold (event `follows.changed`, section 6).

### 5.11 `follow.list`

- Params: `{ offset?: integer >= 0 (safe), limit?: integer 1..500 }`; `offset` defaults to 0, `limit` to 100.
- Result: `{ follows: [hex64], total: integer }`: `follows` = `readFollows(dataDir).slice(offset, offset + limit)` (the stored order, sorted per protocol §1); `total` = the whole list length. An `offset` at or past `total` gives `follows: []`.
- Browser node (`packages/web-member/lib/session.js`): it reads the kv area (config and follows) on the serial chain, so a `follow.add` / `follow.remove` sent before it is listed, but it opens no core and never preempts a running sync (6.1); a concurrent follow-set fold is one JSON write, read either before or after.

### 5.12 `log.read`

- Params: `{ author?: hex64, limit?: integer 1..36, before?: integer >= 1 }`; `author` absent = the own diary; `limit` defaults to 20; `before` (an exclusive block-seq bound, safe integer) absent = the newest page. `0` is rejected (the window would be empty).
- Result: `{ key: hex64, entries: [{ seq, record }], invalid: [{ seq, reason }], entriesTruncated: integer }`.
  - The node takes `end = before === undefined ? length : min(before, length)` and the window of block seqs `max(0, end - limit) .. end - 1`, ascending by `seq` (a `before` past the length clamps to the newest page). Each block that passes `validRecordCopy(record, seq)` goes to `entries` with that copy; each other block goes to `invalid` with its `seq` and a reason code only (`validateRecord`'s reason, `'malformed'` for a block `decodeBlock` refused). A block that fails validation is NEVER returned as text (A8).
  - `entriesTruncated` = `max(0, end - limit)`, the number of blocks older than the window; `entriesTruncated === 0` means the window starts at the beginning of the diary. To page backwards, pass the lowest `seq` of the window (entries and invalid) as the next `before`.
  - A `delete` record (`{ type, seq, at }`, with an optional `media`, written by 5.33 and 5.34; valid only at `1 <= seq <` its own block seq) deletes its target whatever the target's type, and whether or not this copy holds the target block. A deleted block goes to `invalid` with reason `'deleted'`; the tombstone itself is a normal entry. A tombstone counts only in its author's own diary. The writers emit one only for the author's own post or profile block; a tombstone that targets a tombstone undoes that deletion, which the writers never do.
  - Same rules as `log --json`: local data only; an author with no local data -> `NOT_FOUND` `'sem dados locais para este diário'` and no core is created.
- Browser node (`packages/web-member/lib/session.js`): while a run exists it reads the run's own cores and does not preempt it (6.1). A followed (non-own) replica reads the blocks `feed.read` reads for it (5.13: the blocks up to its present length plus the newest run), so its log may have a gap while it downloads newest-first. The window is then taken by `seq` over those blocks: it ends at `before` (exclusive; absent = past the newest block) and holds up to `limit` of them, the ones with the highest seqs below it; a block that is not stored (the gap, or a hole the newest run passes because a stored tombstone deletes it) is skipped silently, never in `invalid`; a stored block that is malformed or deleted goes to `invalid` as above, and `entriesTruncated` = the number of those blocks below the window. The paging rule above is unchanged (pass the lowest `seq` of the window as the next `before`, while `entriesTruncated > 0`). The own diary has no gap, so for it this is exactly the window above.
- Size: `LOG_LIMIT_MAX` entries always fit `MAX_MESSAGE` (section 2).

### 5.13 `feed.read`

- Params: `{ limit?: integer 1..31, before?: { at, author, seq } }`, `limit` default 30. `FEED_LIMIT_MAX` = 31 pages always fit `MAX_MESSAGE` (section 2).
- `before` (absent = the newest page) has exactly the keys `at` (a canonical ISO string, `new Date(at).toISOString() === at`, at most 32 chars), `author` (lowercase hex64) and `seq` (a safe integer >= 1). With `before`, only items strictly before the cursor in feed order `(Date.parse(at), author, seq)` are considered and the LAST `limit` of them are returned (`buildFeed`'s `before`). The UI copies the cursor from the oldest item it holds; pages never overlap (feed order is total), and a page with fewer than `limit` items is the last page of the LOCAL data; while `incomplete` is non-empty or `incompleteTruncated > 0` older or newer items of those diaries may still arrive, and the UI says so instead of announcing the end. A sync between two requests may add older items, which later pages include; newer ones need a reload of the newest page. Cursors are navigation bounds, not snapshots: moderation (blocklist, revoked issuers) is re-checked on every request.
- Result: `{ items: [FeedItem], skipped: [{ key, reason }], skippedTruncated, future: [ref], futureTruncated, incomplete: [hex64], incompleteTruncated }`.
  - What is read per followed diary: on the core node and `varanda-serve`, the blocks up to its present length (protocol §2). On the browser node, which downloads a followed diary newest-first (protocol §6 "Browser node download order"), the blocks up to its present length plus the newest run: the unbroken run of blocks that ends at the signed length, a hole in it passed only when a stored tombstone targets it (`readVisible`, `packages/web-member/lib/node-store.js`). The newest run is read only when block 0 is stored (moderation reads it) and the signed length is within `MAX_LOG_BLOCKS`; a run that does not reach the signed length is not read. Every stored tombstone applies to both parts.
  - `items`: `buildFeed`'s FeedItem objects unchanged (protocol §7 "FeedItem": a post item `{ kind: 'post', author, name, username, seq, at, text, replyTo, quote, media }`, never both `replyTo` and `quote`, or a repost item `{ kind: 'repost', author, name, username, seq, at, to, text: null, replyTo: null, quote: null, media: null }`, one per target the author still reposts; ascending by `(at, author, seq)`, the LAST `limit` kept). The UI renders a repost item as the ORIGINAL post `to` (read with `diary.peek`, or `log.read` on the core node) under 'Nome republicou', and every action on it targets the original. `media` is a copy of the post's descriptors, or `null`; a reader fetches the bytes itself (the hosted web app over the seeder's `/media` route, protocol §7 "Seeder media route", verifying length and SHA-256 against the descriptor).
  - `username: string | null`: the name in the highest-sequence `username` record whose issuer delegation and signature verify for the configured association and whose member is the diary key (`latestUsername`, `packages/core/lib/username.js`). It matches `/^[a-z][a-z0-9_]{2,19}$/` and is not six hex characters. No verified record means `null`; neither the member certificate nor `profile.name` supplies this field. Both v1 and v2 diaries can carry it. A rename updates the handle on every post in that diary once the record is synced.
  - `skipped` (capped): followed logs not shown, with the reasons of protocol §7 `feed` (`no-cert`, `not-in-log`, `member-mismatch`, `untrusted-association`, `bad-signature`, `malformed`, `fork`).
  - `future` (capped): references of future-dated posts (protocol §2 R5.10). Uncapped it grows without bound (Verified V9: `limit: 1` with 4,000 future posts gave 287 KB).
  - `incomplete` (capped at `FEED_INCOMPLETE_MAX`, not `MAX_LIST`, with `incompleteTruncated` = the count cut): followed diaries shown in the feed (skip reason null) whose present length is below the signed length its local replica knows (`core.length`), i.e. older blocks between the prefix and the newest run, or newer blocks, may still arrive; in follow-list scan order, lowercased, duplicates and the own key excluded; a diary can be in `items` and in `incomplete` at once; a follow with no local replica stays `no-cert` in `skipped` and is NOT listed (that reason also means a diary that truly has no data); `fork`, `blocked` and every other skip reason are not listed; both fields are always present (`[]`, `0`); `feed --json` (CLI) is unchanged because apps/cli/lib/commands/member.js:196 destructures only items, skipped and future.
  - The CLI's stderr warnings (bad `follows.json` entries, skipped logs, future posts) are not events here; the lists carry the same information.
- Browser node (`packages/web-member/lib/session.js`): while a run exists it reads the run's own cores and does not preempt it (6.1).

### 5.14 `sync.start`

- Params: `{ once?: boolean, timeoutMs?: integer 1000..600000 }`; `once` defaults to `false`; `timeoutMs` is allowed only with `once: true` (else `USAGE` `'timeoutMs só com once'`) and then defaults to 30000.
- Result: `{ runId: integer }`, returned as soon as the run has started (it does not wait for the run). `runId` is a safe integer in `1..MAX_ID`, new for every run of the node. A `sync.started` event (section 6) is emitted for the run before this response.
- No identity yet -> `NOT_FOUND` `'identidade não encontrada'` (no run is started, no event).
- A second `sync.start` while a run is active -> `USAGE` `'sincronização já em andamento'`. The bootstrap, DHT host and association are node configuration.

### 5.15 `sync.stop`

- Result: `{ stopped: boolean }`: `true` when a run was active and was asked to stop (its `sync.stopped` event, reason `'stopped'`, is sent before this response: the node awaits the run), `false` when no run was active. A stopped continuous run is not restarted.

### 5.16 `sync.status`

- Params: `{}`.
- Result (SyncState): `{ state: 'idle' }` or `{ state: 'running', runId, once }`.

### 5.17 `node.close` (IPC only)

- Params: `{}`.
- Result: `{ closed: true }`.
- Offered only by the in-app worklet (`apps/app/worklet/main.js`), next to the session's handlers; the node session itself (`session.handlers`), `varanda-serve` and the browser node do not register it, so over the WebSocket it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6).
- The worklet detaches and closes the node session (any running sync is stopped and awaited, every store is closed and the data-dir lock released), then sends this response, then ends its side of the IPC stream and ignores every later frame. The host terminates the worklet after the response; only a received response means a clean stop, after which the next worklet needs no lock takeover (`recover`). Needed because the bare-kit IPC has no end-of-stream signal from the React Native side.

### 5.18 `account.sign`

- Params: `{ phase, nonce, username, sub }`, all required, nothing else: `phase` one of `'reserve'`, `'finish'`, `'rename'`; `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce); `username` matches `/^[a-z][a-z0-9_]{2,19}$/` and is not 6 hex characters (it would read like the fallback handle `'@' + key.slice(0, 6)`); `sub` is `''` for `'reserve'` and `'rename'` and, for `'finish'` only, the Google subject: 1..255 printable ASCII characters without space (`/^[\x21-\x7e]{1,255}$/`, so it can never contain the LF separator). A phase/sub mismatch -> `USAGE` `'parâmetro inválido: sub'`. Not mutating.
- The caller never passes the member, the association or any bytes: the node fills in `member` = its own diary key and `association` = its configured association, and signs exactly the UTF-8 bytes of these seven fields joined by LF (`0x0a`), no trailing LF (`accountLinkPayload`, `packages/core/lib/account-link.js`):

  ```
  varanda-account-link-v1
  <phase>
  <nonce>
  <member hex64>
  <username>
  <association hex64>
  <sub>          ('' for reserve and rename)
  ```

  The prefix separates this statement from every other signature of the protocol (member and issuer certificates, Hypercore blocks).
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service checks it with `verifyAccountLink(fields, signature)`, using `member` as the public key.
- Browser node (`packages/web-member/lib/session.js`): the diary key is the raw Ed25519 public key of the passkey-derived pair, so it signs. It opens no diary, does not preempt or start a sync, appends nothing and contacts no one. No identity -> `NOT_FOUND` `'identidade não encontrada'`; locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a pair for another diary -> `USAGE` `'passkey não corresponde ao diário guardado'`.
- Node session (`packages/core/lib/session.js`: the Bare worklet and `varanda-serve`): a Hypercore 11 diary key is not the signer's raw public key (protocol §1), so a signature could never verify against it: always `USAGE` `'assinatura disponível só no navegador'`, with or without an identity, and nothing is opened.

### 5.19 `username.add`

- Params: `{ record: object }`, nothing else: a plain object with `JSON.stringify(record)` at most 2048 bytes (`MAX_USERNAME_RECORD_BYTES` in `lib/methods.js`; larger -> `USAGE` `'parâmetro inválido: record'`). Only shape and size are checked here. Mutating.
- The record is an issuer-signed `username` record (docs/protocol.md section 3, "Username record"; `createUsernameRecord` in `packages/core/lib/cert.js`), as the account service returns it. The node verifies it with `verifyUsernameRecord(record, <own diary key>, <association>)`: exact shape, `member` = the own key, `association` = the configured association (the trust root), the embedded issuer delegation signed by the association and the record signed by the issuer. Anything else -> `USAGE` `'registro de nome inválido'` and nothing is written.
- Order: the newest `username` record by seq is the displayed name, so the record is compared with the diary's latest verified username record (`latestUsernameRecord` over the own entries, `packages/core/lib/username.js`), after the write gate in the browser node (below). Deep-equal to the latest -> `{ changed: false, username }`, nothing written (the browser node still retries an outstanding push, below). `date` earlier than the latest record's `date`, or the same `date` with a different record (two records of the same instant cannot be ordered) -> `USAGE` `'registro de nome antigo'`, nothing written: an earlier name would revert a rename. Otherwise a plain copy of the record (exactly its nine keys) is appended at the next seq (a `username` record is valid only at seq >= 1: before the member certificate, `USAGE` `'grave o certificado de membro antes de publicar'`) and the result is `{ changed: true, username, seq }`; a rename is a newer record appended this way.
- Browser node (`packages/web-member/lib/session.js`): a diary write like `profile.set` (section 11): no identity -> `NOT_FOUND` `'identidade não encontrada'`; locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; then the catch-up through the write gate (with the gate on and no seeder reachable, `USAGE` `'sincronize com o semeador antes de publicar'`), so a record another device already published arrives before the comparison and is not appended again; then the comparison, the append and the push. A record equal to the latest is not written, but while the seeder is not known to hold the local length a push runs anyway: a push that failed after the append is retried by handing the same record in again.
- Node session (`packages/core/lib/session.js`): the same verification, idempotence and `'registro de nome antigo'`, an identity required (`NOT_FOUND` without one), no write gate. A Hypercore 11 diary key is not the account-link signer (5.18), so the account service normally issues no record for it and the answer is `USAGE` `'registro de nome inválido'`.

### 5.20 `report.sign`

- Params: `{ nonce, target, seq?, writer?, group?, reason, text?, quote?, anexo? }`, nothing else: `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce); `target` the reported diary key (lowercase hex64); `seq` optional, an integer `1..99999` (`MAX_LOG_BLOCKS - 1`: seq 0 is the member certificate), present for a report of that post and absent for a report of the whole account; `reason` one of `'spam'`, `'assedio'`, `'ilegal'`, `'outro'`; `text` the reporter's own words, `0..280` code points (default `''`); `quote` the reported post's text, `0..MAX_TEXT` (1000) code points (default `''`). `writer` and `group` (both lowercase hex64) address a post of a group (public, or private with the reporter's decrypted quote, protocol section 10 "Sealed reports"): `writer` is the writer core that holds the post and `group` the group root key, and both require each other and `seq` (`writer` without `seq` or `group` -> `USAGE` `'writer só com seq e group'`; `group` without `writer` -> `USAGE` `'group só com writer'`); `target` is then the author's diary key. `report.sign` does not compare the keys with each other; the account service intake refuses a version 2 report whose `group` equals `target`, or whose `writer` equals `target` (`pedido-invalido`; a `writer` equal to `group` is accepted, the creator writes through the root core; protocol section 10 "Blocklist and moderation"). `anexo` optional, 64 lowercase hex, the sha256 of the attachment bytes, only with `writer` (`USAGE` `'anexo só com writer'` otherwise); the statement is then `varanda-report-v3` with the digest line, and the image bytes never enter the RPC request: the reporter uploads them to `POST /account/report/anexo` (protocol section 11 "Reports"). A quote without `seq` -> `USAGE` `'quote só com seq'`; `seq` with an empty (or absent) quote is allowed (the report of a photo-only post, whose text is empty). A block on a report without `group` whose target has no linked account waits for the account service to confirm that the local seeder serves the diary (HTTP 409 `alvo-nao-confirmado` otherwise; protocol section 10 "Blocklist and moderation"); discarding always works. Not mutating.
- The caller never passes the member, the association, a digest or any bytes: the node fills in `member` = its own diary key and `association` = its configured association, and signs exactly the UTF-8 bytes of these nine lines joined by LF (`0x0a`), no trailing LF (`reportPayload`, `packages/core/lib/report.js`). With `writer` and `group` (a report of a group message) the statement is version 2 and has these eleven lines, in this order: `varanda-report-v2`, `<nonce>`, `<member>`, `<association>`, `<target>`, `<group>`, `<writer>`, `<seq>`, `<reason>`, `<digest(text)>`, `<digest(quote)>`. The two prefixes keep a v1 signature from ever verifying as a v2 statement and back. The nine lines of version 1:

  ```
  varanda-report-v1
  <nonce>
  <member hex64>
  <association hex64>
  <target hex64>
  <seq>          (canonical decimal, no leading zero; '' for an account report)
  <reason>
  <digest(text)>
  <digest(quote)>
  ```

  `digest(s)` is the lowercase hex of the plain BLAKE2b-256 hash (`hypercore-crypto` `hash`) of the UTF-8 bytes of `s`; `''` hashes too (`0e5751c0…`). The digests keep any LF inside a post out of the framing. The prefix separates this statement from every other signature of the protocol (certificates, account links, moderation requests, Hypercore blocks).
- `report.js` refuses (`TypeError`) more than the RPC layer: `member === target`; a control character, DEL, C1, U+2028/U+2029 or a bidi control in `text` (and in `quote`, where LF is allowed); and a `text` or `quote` that is not well formed (`String.prototype.isWellFormed()` false: a lone surrogate encodes to the same UTF-8 bytes as U+FFFD, so the digest would not bind the exact string). The app therefore sends `quote = post.text.toWellFormed()`, and the same for the report text.
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service checks it with `verifyReport(fields, signature)`, using `member` as the public key. The signature proves that the reporter attested this text and this quote to the association's account service; it does NOT prove that the reported diary contains the quote (the moderator checks the diary).
- Browser node (`packages/web-member/lib/session.js`): signs like `account.sign` (5.18): it opens no diary, does not preempt or start a sync, appends nothing and contacts no one. No identity -> `NOT_FOUND` `'identidade não encontrada'`; locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a pair for another diary -> `USAGE` `'passkey não corresponde ao diário guardado'`; `target` = the own key -> `USAGE` `'não é possível denunciar a própria chave'`; a statement `report.js` refuses -> `USAGE` `'denúncia inválida'`.
- Node session (`packages/core/lib/session.js`): as 5.18, always `USAGE` `'assinatura disponível só no navegador'`, with or without an identity, and nothing is opened.

### 5.21 `profile.read`

- Params: `{ authors: [hex64] }`, nothing else: 1..`PROFILE_LIMIT_MAX` (100) lowercase hex64 keys; duplicates are allowed and folded. Not mutating.
- Result: `{ profiles: [{ author, name: string | null, username: string | null, bio: string | null, avatar: AvatarDescriptor | null }], missing: [hex64] }`, one entry per distinct author, in first-occurrence order within each list.
  - An author is in `profiles` when `feed.read` would show its diary: the own key always; a followed or unfollowed replica with local data that passes `skipReason` (not blocked, no fork, a valid block-0 certificate for the association, issuer not revoked). `name`, `bio` and `avatar` come from the newest valid `profile` record of the blocks `feed.read` reads for that diary (5.13: the whole local log up to its present length, plus the newest run on the browser node; `latestProfile`; a profile that has not arrived yet, e.g. in the middle of a diary still downloading, reads as `null` for a moment; none -> `null`, `null`, `null`; a plain profile -> `avatar: null`). A node that predates the avatar omits `avatar`; the app reads that as `null`; `username` = `latestUsername` (the newest candidate only, verified with the enforced revoked-issuer set; otherwise `null`).
  - Every other author is in `missing`: no local replica, blocked, fork, certificate failure, revoked issuer. The result never says why.
- No identity -> `NOT_FOUND` `'identidade não encontrada'`. Local data only: it never creates a core and works while the browser identity is locked. On the core node and `varanda-serve`, like every member read, it preempts a running sync (section 6.1), so a screen asks for all its authors in one batch; the browser node serves it on the live run's cores without preempting (6.1).
- A node that predates this method answers `USAGE` `'método desconhecido'`; the app treats that as "no profiles available".
- Size: `PROFILE_LIMIT_MAX` profiles always fit `MAX_MESSAGE` (section 2).

### 5.22 `peek.read`

- Params: `{ limit?: integer 1..31, after?: { round, at, author, seq } }`, `limit` default 30 (`PEEK_LIMIT_DEFAULT`, `PEEK_LIMIT_MAX`). Not mutating. `after` has exactly the keys `round` (a safe integer >= 0), `at` (a canonical ISO string, at most 32 chars), `author` (lowercase hex64) and `seq` (a safe integer >= 1). Absent = the first page, which rebuilds the snapshot.
- Result: `{ items: [PeekItem], next: PeekCursor | null, diaries: integer, skipped: integer, incomplete: boolean }`.
  - `PeekItem` = FeedItem (5.13: a post item with `media`, `replyTo` and `quote`, or a repost item with `to`) plus `round` and `avatar` (the author's avatar from the newest valid profile within the fetched window, or `null`). Replies, quotes and reposts in effect are publications like any post; the app resolves the parent of a reply, the quoted post and a repost's original with `diary.peek` (5.27), as in A Rua. Images of peeked posts are fetched by the app over the existing `/media` route exactly as for A Rua (the seeder serves them only while the diary<->core binding holds and the diary is not blocked). No new event (`EVENTS` also has `'follows.changed'`, unrelated).
  - `diaries`: candidate diaries of the snapshot (advertised by the seeder with length >= 2, not followed, not blocked; the viewer's own diary is fetched and paged exactly as if shown but its items are removed from its owner's page (its publications already live in A Rua) and counted neither in `diaries` nor in `skipped`; a member who does not follow that diary still sees it in their Espiadinha).
  - `skipped`: candidates left out by a problem (block 0 unavailable or failing the certificate gate, blocked or revoked issuer, fork, quota, a block over 16 KiB, a block that did not arrive), or whose scan reached the 64-block cap without finding a publication. A diary with nothing to show (only a profile or likes, or shorter than 2 blocks) and one followed after the snapshot was built are not counted.
  - `incomplete`: true when the seeder's inventory did not complete (`remoteHave.size < remoteCount` at the 5 s timeout, protocol §5), the 25 s page deadline cut a fetch, the 16 MiB page byte budget was reached (it counts received raw bytes), or a diary's scan reached the 64-block cap before supplying its posts (it may hold older publications behind likes and other records).
- THE RULE: round `r` (r = 0, 1, 2) holds the (r+1)-th highest-seq publication of every candidate diary ("most recent" = last written; a publication is a `post`, reply and quote included, or a `repost` still in effect, the last operation per target winning within the fetched tail; likes are never shown; a repost whose author is someone else still shows when its target is the viewer's own post). The Espiadinha ends after round 3 (`PEEK_MAX_ROUNDS` = 3), so no diary shows more than 3 publications. Page order is (`round` asc, `at` desc, `author` asc); a page holds the items strictly after `after`; `next` = the cursor of the last item when the page is full, `null` on the last page; the end is `next === null`. Before the viewer's own publications are removed the page is cut as in 5.13 (shorter than `limit` means last); because they are removed after the page is cut, a non-last page may hold up to 3 fewer items than `limit` for the viewer, and `next` may point at the position of a removed item. The pt-BR sentence the app shows (`PEEK_RULE`): "A Espiadinha mostra a publicação mais recente de cada diário que você não segue, da mais nova para a mais antiga; depois a segunda e, por fim, a terceira mais recente de cada um, do mesmo jeito: sem curtidas, sem sugestões e sem pesos escondidos."
- Cursors are navigation bounds, not snapshots (as 5.13): the node keeps an in-memory snapshot for at most 5 minutes; `after` absent rebuilds it from a fresh inventory (the previous snapshot is kept until the new one exists, so a failed refresh does not strand the list); an `after` on a missing or expired snapshot is refused with USAGE 'A lista expirou; atualize para continuar.' before any link is opened, instead of rebuilding (the app keeps its rows and asks for a pull to refresh). Follows and the stored blocklist snapshot are re-applied on every request, including continuation pages.
- Moderation: on every request, including continuation pages served from the snapshot, the node re-verifies each diary's block-0 certificate AND its username record against the current revoked-issuer set (a v1 certificate survives an issuer revocation, `packages/core/lib/cert.js`, but a username record from a revoked issuer must read as `null`, `packages/core/lib/username.js`).
- Where it runs: browser node only (`packages/web-member/lib/peek.js`): a short-lived second WebSocket link to the configured seeder (ephemeral Noise key, hello with an empty inventory, no announce, no `varanda/blocklist/1`), the seeder's inventory, then block 0 of each candidate (the gate), then blocks 1..2 and the newest 8 (older ones 8 at a time, up to 64 per diary) through Hypercore replication into memory cores. This link is always its own, whatever the sync state: never the running sync's link, even when a continuous run is live (privacy: that link already announced the member's diary key and follow inventory, so browsing unfollowed diaries over it would let the seeder bind the browsing to the member; the ephemeral link announces nothing, as `docs/design.md` requires). It is opened per page that needs blocks and closed after the page, on a budget overrun and on abort; the page neither borrows nor holds the lease (6.1). Nothing is written to storage; it works with the identity locked, like every read.
- Errors: no identity -> `NOT_FOUND` `'identidade não encontrada'`; no verified seeder within 15 s -> `USAGE` `'sem conexão com o semeador'`; a seeder at capacity (WebSocket close 1013) -> `USAGE` `'Semeador ocupado; tente novamente em instantes.'`; a continuation on an expired or missing snapshot -> `USAGE` `'A lista expirou; atualize para continuar.'`; a concurrent `peek.read` -> `USAGE` `'espiadinha já em andamento'`; node session -> `USAGE` `'Espiadinha disponível só no navegador'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21). The app shows the web-only notice for the last two.
- Unlike other member reads it does NOT preempt a running sync (6.1): it opens no storage core (the browser session's preemption exists only because two Hypercore instances on one storage corrupt it); the own-key lookup enters the serialized chain only while the key is not yet cached or an identity change (`reset`, `setKeyPair`, `clearKeyPair`) is pending, and may then preempt once; with the key cached it runs no serial step, so a write waiting on the chain does not delay it.
- Trust: every block is verified by Hypercore against the author key. The tail window is computed from the SIGNED length Hypercore verifies with block 0 (the memory core's length after the block-0 get, as the quarantine reads it, `packages/web-member/lib/sync.js`), never from the length the seeder advertises in its hello (`admission.js` copies it unsigned); the advertised length only selects candidates (>= 2). The seeder can withhold (inventory, blocks, a shorter length, or an older signed state it kept), which it can already do to A Rua, but cannot forge a post, cannot pick an older post as the newest, cannot bypass the block-0 gate (verified locally with the stored revoked-issuer set) and cannot unblock anyone (stored signed blocklist).
- Privacy: the link sends an empty inventory and no announce, but it requests the complement of the follow set (the own diary included, so the request does not single the member out), which the seeder already learns from the sync link's inventory on the same IP (protocol §5 "Bounded inventory"); the seeder logs one `peer` event per link with an ephemeral key; nothing new is stored on any server.
- Cost: 1 WebSocket + Noise + hello/inventory (~85 bytes per entry), then per candidate one channel open and <= 11 block requests in two phases (block 0, then the window), 16 diaries in parallel; ~3-5 s for 300 diaries at 50 ms RTT; 4096 diaries may hit the deadline or the byte budget -> `incomplete`. Candidates are fetched in a random order per snapshot, so a cut falls on random diaries, never systematically on the same ones.
- Memory: parsed posts (<= 1000 chars) and at most 64 records per diary, raw buffers dropped after each window. Memory cores use 64 KiB pages (`random-access-memory` defaults to 1 MiB pages); between pages the node keeps only block 0, profile and username records and the posts and reposts among the at most 64 fetched blocks per diary (`retainRecords`), within `PEEK_SNAPSHOT_MAX_BYTES` = 33554432 (32 MiB) of retained records; beyond it fetching stops and the page is `incomplete`.
- Size: `PEEK_LIMIT_MAX` items always fit `MAX_MESSAGE` (section 2).

### 5.23 `post.quote`

- Params: `{ to: ref with seq >= 1, text: string 1..1000 chars, media?: [MediaDescriptor] }`, nothing else (the text is required even with `media`). Mutating.
- Result: `{ seq }`. Appends a quote record (protocol §2: a `post` with `quote` = `to` and `replyTo: null`).
- Browser node: the `post.reply` path (unlocked identity, write gate, append, push; `media` checked as in 5.8). Core node: `media` -> `USAGE` `'mídia disponível só na versão web'` before anything is opened; no write gate. Block 0 is required (`'grave o certificado de membro antes de publicar'`). The app never queues a quote in its outbox: it needs a connection.

### 5.24 `like.set` / 5.25 `repost.set`

- Params: `{ to: ref with seq >= 1, on: boolean }`, nothing else. Mutating.
- Result: `{ seq: integer | null, on: boolean, changed: boolean }`. Idempotent: the own diary's current state (`engagementState`, protocol §2: the last operation per target wins) is compared first; when it already is `on`, nothing is written, `changed` is `false` and `seq` is that of the existing effective record (`null` if there never was one). Otherwise one `like` / `repost` record is appended, `changed: true`, `seq` its block. Liking or reposting an own post is allowed.
- Browser node: the `post.reply` path (unlocked, write gate, append, push); a call that writes nothing still pushes while the seeder is not known to hold the local length. Core node: the same toggle, no write gate. Block 0 is required.

### 5.26 `engagement.read`

- Params: `{ refs: [ref] }`, nothing else: 1..`ENGAGEMENT_LIMIT_MAX` (62) distinct refs with seq >= 1 (a duplicate -> `'parâmetro inválido: refs'`). Not mutating.
- Result: `{ liked: [ref], reposted: [ref] }`: the subsets of `refs` (request order) that the OWN diary currently likes / reposts. Other people's engagement is not here (counts come from the seeder index, and so does the who-liked and who-reposted list, protocol §7 "Seeder index route").
- Local data only; works while the browser identity is locked. On the core node and `varanda-serve`, like every member read, it preempts a running sync (6.1), so the app calls it before its peeks; the browser node serves it on the live run's cores without preempting (6.1).

### 5.27 `diary.peek`

- Params: `{ author: hex64, seqs: [integer >= 1], profileSeq?: integer >= 1, usernameSeq?: integer >= 1 }`, nothing else: `seqs` 1..`PEEK_SEQS_MAX` (36), strictly ascending (so distinct). Not mutating.
- Result: `{ key, length, entries: [{ seq, record }], invalid: [seq], missing: [seq], profile: { name, bio, avatar } | null, username: string | null }`. Each requested seq lands in exactly one list: `entries` (a block that passed `validRecordCopy`, the copy), `invalid` (a block that failed; never returned as text, A8) or `missing` (not available within the deadline, or beyond the length the node may read). `length` = the length of the core read. `profile` = the block at `profileSeq` if it is a valid `profile` record (`avatar` its descriptor, or `null` for a plain record), else `null`; `username` = the block at `usernameSeq` only if it is a `username` record for `author` that verifies (`verifyUsernameRecord` with the configured association and the revoked issuers; no fallback to an earlier record), else `null`. The hints come from the seeder index: which record is the latest is the seeder's claim. A block hidden by a tombstone (5.12) is cleared on official replicas, so it lands in `missing` (below).
- Browser node (`packages/web-member/lib/session.js`, protocol §6 "Browser node on-demand reads"): outside the serial chain, like `peek.read` (5.22). It is served by the running sync's verified seeder link, never preempts it and never restarts a run itself (a restart beside a `withStore` write could corrupt the storage). At most 2 peeks in flight (`USAGE` `'ocupado'` beyond). When no verified run is live it queues a serial no-op (so `restartWhenIdle` restarts a wanted continuous run safely; a run that ends while the peek waits runs that check again, 6.1) and waits up to `PEEK_TIMEOUT_MS` (8 s); then `NOT_FOUND` `'semeador indisponível'`, which the caller may retry. The peek holds the lease (6.1 `borrow`) from its wait to its answer. A peek the run drops while stopping (preempted by a write) is retried once on the next verified run within the same deadline. A blocked, ungated, forked or unknown author -> `NOT_FOUND` `'diário indisponível'` (never why). Nothing is stored. A closed session -> `LOCKED` `'sessão encerrada'`.
- A seq the seeder deleted and cleared (protocol §2 "Clearing deleted bytes") answers as absent: the seeder no longer holds the block, so the request is not answered and the seq lands in `missing` after the fetch timeout (`PEEK_TIMEOUT_MS`), never in `entries`. A cleared profile head (`profileSeq`) gives `profile: null`, not an error. A deleted block the seeder still holds (`VARANDA_NO_CLEAR=1`, or before it learned the tombstone) is hidden by the seeder's own fold and the app drops it.
- Core node (`packages/core/lib/session.js`: native app, `varanda-serve`): always `USAGE` `'leitura sob demanda só na versão web'`, before anything is opened. The app then falls back to local data (`log.read` of followed diaries) with a note.
- Size: 36 worst-case entries with a profile and a username always fit `MAX_MESSAGE` (section 2).

Topic search is not an RPC method. The hosted app calls `GET /index/topic/<tokens>[/<cursor>]` (protocol §7 "Seeder index route") and verifies each returned ref with `diary.peek` (at most 36 seqs per call, two calls in flight), re-checking the words in the verified text. No new method and no row in the size table.

The follower and following counts and lists ("N seguindo", "N seguidores", the Seguindo and Seguidores lists) are not RPC methods either: the app calls `GET /index/follows/<author>` and `GET /index/follows/<author>/(seguindo|seguidores)[/<cursor>]` (protocol §7 "Seeder index route", §5 "Seeder follow index") and verifies each row with `diary.peek` of the signed follow record. No new method and no row in the size table.

Who liked and who reposted is not an RPC method either. The hosted app calls `GET|HEAD /index/likes/<author>/<seq>[/<cursor>]` and `GET|HEAD /index/reposts/<author>/<seq>[/<cursor>]` (protocol §7 "Seeder index route") and verifies each engager with one `diary.peek` `{ author, seqs: [seq], profileSeq?, usernameSeq? }`. The entry must be that `like` or `repost` with `on: true` and `to` equal to the post; anything else is dropped and counted as unavailable. Names come from the peeked profile and the verified username. There is no new method and no row in the size table. On the core node, `diary.peek` stays `USAGE` `'leitura sob demanda só na versão web'`.

A node that predates 5.23 to 5.27 answers `USAGE` `'método desconhecido'`.

### 5.28 `notices.list`

Who started following the caller and whom the caller does not follow yet ("follow-back notices"), who replied to, quoted or mentioned the caller, and who liked or reposted the caller's posts. Private to the caller; the result carries no count and no total.

- Params: `{ limit?: integer 1..64, after?: { at, key } }`, `limit` default 30 (`NOTICES_LIMIT_DEFAULT`, `NOTICES_LIMIT_MAX`). Not mutating. `after` has exactly the keys `at` (a canonical ISO string) and `key` (lowercase hex64), or exactly `at`, `key` and `seq` (an integer >= 1) after a notice of any kind but `follow`; absent = the first page. There is no new param. A different key set is rejected as for every method.
- Result: `{ notices: [Notice], next: { at, key } | { at, key, seq } | null, incomplete: boolean, supported: boolean, activity: boolean }`.
  - `Notice` = `{ kind: 'follow' | 'reply' | 'quote' | 'mention' | 'like' | 'repost', key: hex64, seq: integer >= 1, at: ISO string, name: string | null, username: string | null, seen: hex32, avatar: AvatarDescriptor | null, post?: string }`: `kind` is derived by the browser node from the signed block and the own diary, never taken from the seeder; a `like` or `repost` is a signed `on: true` block whose `to.author` is the caller and whose `to.seq` is one of the caller's own post blocks; it is absent on a notice of a node from before it and means `follow`. For `follow`, `key` is the follower's diary key, `seq` the block of their signed `follow` record and `at` that record's `at`; for `reply`, `quote` and `mention`, `key:seq` is the author's signed POST block that replied to, quoted or mentioned the caller (a reply or quote of one of the caller's posts, or an `@nome` in the text naming one of the usernames the caller's diary verifiably held, so a renamed member still receives mentions of the old name) and `at` is that post's `at`. For `like` and `repost`, `key:seq` is the engager's signed block, `at` its `at`, and `post` is `'<hex64>:<seq>'`, the caller's post it targets; `post` is absent on every other kind. A later signed block of the same type for the same post in the engager's fetched tail drops the row: an `on: false` is an undo, and a newer `on: true` is the row the seeder should name instead. One row per block, with the priority reply > quote > mention; a `like` or `repost` row is one per (engager, post, kind) per read. `name` is their profile name, `avatar` their profile avatar and `username` their verified username, for every kind (all `null` when unknown; the app shows 'sem nome' for a missing name and never a key). There is no `count`, `total` or `unread` field anywhere.
  - `seen` is an opaque token, 32 lowercase hex: the first 32 hex of BLAKE2b (`hypercore-crypto` `hash`) over `'varanda-notices-seen-v1\n'`, the 32-byte identity seed and `<own>\n<key>:<seq>`, computed by the browser node for each returned row at return time. It is stable for one identity and one follow (the same `(key, seq)` gives the same token on every read and after a reload) and different for another follow or another identity. Being keyed by the identity secret, which exists only in the unlocked session, it cannot be linked to the follower's key without that secret. It exists so the app can remember which notices were seen without storing anything derivable from follower keys (which are public): whoever reads the origin's storage while the passkey is locked cannot confirm who followed (docs/app.md, Avisos). A lock in the middle of a read fails it like a locked proof.
  - Order: newest `at` first (by `Date.parse`), then `key` ascending, then `seq` descending; `after` is exclusive and `next` is the cursor of the last item when more rows may follow (the cursor of a read over channel v2 or v3 carries `seq`, the other one does not), `null` otherwise. A two-key `after` read over v2 or v3 means `seq` 1, so the rest of that `(at, key)` group is skipped. Only `next === null` ends the list: a page may be short or even empty with a `next` (the read dropped rows already followed, blocked or unverifiable, or stopped after 8 seeder pages), and the caller continues from it; the app does so automatically up to 4 times per action (`readNotices` in `apps/app/src/notices.js`).
  - `incomplete`: true when the seeder's index was not complete (a cap was hit or a diary was still being scanned), the 25 s read deadline, the byte budget, the 8 seeder pages or the per-row block cap cut the read, or a block did not arrive.
  - `activity`: false only when the rows came over the follows-only channel (`'varanda/notices/1'`) because the seeder took neither `'varanda/notices/3'` nor `'varanda/notices/2'`: the list then has follows only and the app says the rest is not available from this seeder. Every other result, an empty or incomplete one included, says `true`; an older node omits it, which the app reads as true.
  - `supported`: false (with `notices: []`, `next: null`) when the seeder opens none of the three notices channels (an older seeder); the app says so; its 5-minute poll keeps asking, so an upgraded seeder is picked up without a reload.
- Where it runs: browser node only (`packages/web-member/lib/notices.js`). Every row is verified in the browser against the author's signed blocks before it is returned (protocol "Notices link"), and a v2 or v3 read also reads the own diary once, inside the serial step (on the live run's cores while a run exists, 6.1), for its post seqs and held usernames: the seeder can withhold a row but cannot add one or change its kind. Rows of a follow already followed, blocked, the own key or listed twice never appear; follows and the stored blocklist are re-applied on every request, including rows served from the evidence cache.
- Errors: the node session (`packages/core/lib/session.js`, the CLI and `varanda-serve`) answers `USAGE` `'avisos disponíveis só no navegador'` without opening anything; a concurrent `notices.list` -> `USAGE` `'avisos já em andamento'`; no identity -> `NOT_FOUND` `'identidade não encontrada'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'` (the proof needs the identity key); no verified seeder within 15 s or a link lost under the read -> `USAGE` `'sem conexão com o semeador'`; a seeder at capacity (WebSocket close 1013) -> `USAGE` `'Semeador ocupado; tente novamente em instantes.'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21). The app shows the web-only notice for the first and the last.
- Like `peek.read` it does NOT preempt a running sync (6.1) and writes nothing; no new event. Its own-key lookup follows `peek.read`'s rule (5.22): it enters the chain only while the key is not yet cached or an identity change is pending. Disconnect, lock, reset and close abort a running read and free the slot at once.
- Size: `NOTICES_LIMIT_MAX` notices always fit `MAX_MESSAGE` (section 2, `test/sizes.test.js`).

### 5.29 `terms.sign`

- Params: `{ nonce, version }`, nothing else: `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce from `POST /account/terms/start`); `version` an integer `1..9999`.
- The caller never passes the member, the association or any bytes: the node fills in `member` = its own diary key and `association` = its configured association, and signs exactly the UTF-8 bytes of these five lines joined by LF (`0x0a`), no trailing LF, no date (`termsPayload`, `packages/core/lib/terms.js`):

  ```
  varanda-terms-v1
  <nonce>
  <member hex64>
  <association hex64>
  <version>      (canonical decimal)
  ```

  The prefix separates this statement from every other signature of the protocol (certificates, account links, reports, moderation requests, Hypercore blocks).
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service checks it with `verifyTerms(fields, signature)`, using `member` as the public key. It proves that this diary key accepted that version of the Termos de Uso and the Política de Privacidade for this association, bound to a single-use nonce (`POST /account/terms/finish`, `docs/protocol.md`).
- Where it runs: browser node only (`packages/web-member/lib/session.js`), like `account.sign`: not a diary write, no append, no network. Not mutating.
- Errors: the node session (`packages/core/lib/session.js`, the CLI and `varanda-serve`) answers `USAGE` `'assinatura disponível só no navegador'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### 5.30 `invite.sign`

- Params: `{ action, nonce }`, nothing else: `action` is `'issue'` (mint one invite, `POST /account/invites/finish`) or `'summary'` (read the member's own weekly allowance, `POST /account/invites/summary`; mints nothing). The action is one of the signed lines, so a signature for one action never verifies as the other; `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce from `POST /account/invites/start`).
- The caller never passes the member, the association or any bytes: the node fills in `member` = its own diary key and `association` = its configured association, and signs exactly the UTF-8 bytes of these five lines joined by LF (`0x0a`), no trailing LF, no date (`invitePayload`, `packages/core/lib/invite.js`):

  ```
  varanda-invite-v1
  <action>
  <nonce>
  <member hex64>
  <association hex64>
  ```

  The prefix separates this statement from every other signature of the protocol (certificates, account links, terms acceptances, reports, moderation requests, Hypercore blocks).
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service checks it with `verifyInvite(fields, signature)`, using `member` as the public key. With `'issue'` it proves that this linked member asks the account service to mint one signup invite for this association, bound to a single-use nonce (`POST /account/invites/start`, then `POST /account/invites/finish`, `docs/protocol.md`); with `'summary'` it proves that this linked member asks to read its own weekly allowance (`POST /account/invites/start`, then `POST /account/invites/summary`), and nothing is minted. The statement carries no e-mail and nothing about the invited person.
- Where it runs: browser node only (`packages/web-member/lib/session.js`), like `terms.sign`: not a diary write, no append, no network. Not mutating.
- Errors: the node session (`packages/core/lib/session.js`, the CLI and `varanda-serve`) answers `USAGE` `'assinatura disponível só no navegador'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### 5.31 `push.sign`

- Params: `{ nonce, action, endpoint, p256dh, auth }`, all required, nothing else: `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce); `action` is `'on'` or `'off'`; `endpoint` is printable ASCII (0x21-0x7E), 1..2048 characters, `https:` (the global URL parser must accept it with an empty username, password and hash) and canonical: `new URL(endpoint).href === endpoint` (no explicit `:443`, no uppercase host, no `.` or `..` segments); a query string is accepted; a URL with credentials, a fragment or a backslash is rejected; `p256dh` matches `/^[A-Za-z0-9_-]{1,128}$/` and `auth` matches `/^[A-Za-z0-9_-]{1,32}$/` (base64url, no padding). Not mutating.
- The caller never passes the member, the association, the endpoint hash or any bytes: the node fills in `member` = its own diary key, `association` = its configured association and `endpointHash` = the lowercase hex64 BLAKE2b-256 hash (`hypercore-crypto` `hash`) of the UTF-8 bytes of `endpoint`, and signs exactly the UTF-8 bytes of these eight lines joined by LF (`0x0a`), no trailing LF (`pushPayload`, `packages/core/lib/push-proof.js`):

  ```
  varanda-push-v1
  <nonce>
  <member hex64>
  <association hex64>
  <action>       ('on' or 'off')
  <endpointHash> (hex64 hash of the UTF-8 endpoint)
  <p256dh>
  <auth>
  ```

  The hash keeps the endpoint out of the framing. The prefix separates this statement from every other signature of the protocol (certificates, account links, reports, terms acceptances, moderation requests, Hypercore blocks).
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service verifies it at `POST /account/push/finish` (`docs/protocol.md`), using `member` as the public key. It proves that this diary key set this browser push subscription `on` or `off` for this association, bound to a single-use nonce. The HTTP call that stores the subscription is separate from this RPC and is never retried by the client.
- Where it runs: browser node only (`packages/web-member/lib/session.js`), like `account.sign`: not a diary write, no append, no network. Not mutating.
- Errors: the core node (`packages/core/lib/session.js`), `varanda-serve` and the CLI answer `USAGE` `'assinatura disponível só no navegador'` (with or without an identity, and nothing is opened); no identity on the browser node -> `NOT_FOUND` `'identidade não encontrada'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; an endpoint or key the statement refuses although the params passed (`packages/core/lib/push-proof.js`) -> `USAGE` `'inscrição de notificação inválida'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### 5.32 `age.sign`

- Params: `{ action, nonce }`, nothing else: `action` is `'session'` or `'result'`; `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce from `POST /account/age/start`).
- The caller never passes the member, the association or any bytes: the node fills in `member` = its own diary key and `association` = its configured association, and signs exactly the UTF-8 bytes of these five lines joined by LF (`0x0a`), no trailing LF, no date (`agePayload`, `packages/core/lib/age.js`):

  ```
  varanda-age-v1
  <action>       ('session' or 'result')
  <nonce>
  <member hex64>
  <association hex64>
  ```

  The prefix separates this statement from every other signature of the protocol (certificates, account links, terms acceptances, signup invites, push subscriptions, reports, moderation requests, Hypercore blocks).
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload or a key. The account service checks it with `verifyAge(fields, signature)`, using `member` as the public key. It proves that this diary key asks the account service to open an age-verification session (`'session'`, `POST /account/age/session`) or to read its result (`'result'`, `POST /account/age/result`) for this association, bound to a single-use nonce (`docs/protocol.md`). It never carries an age, a birth date or anything about the person: the age band comes from the verification provider and is recorded by the account service alone.
- Where it runs: browser node only (`packages/web-member/lib/session.js`), like `invite.sign`: not a diary write, no append, no network. Not mutating. It needs an identity but no member certificate (the age check runs before the account link).
- Errors: the core node (`packages/core/lib/session.js`), `varanda-serve` and the CLI answer `USAGE` `'assinatura disponível só no navegador'` (with or without an identity, and nothing is opened); no identity on the browser node -> `NOT_FOUND` `'identidade não encontrada'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a pair for another diary -> `USAGE` `'passkey não corresponde ao diário guardado'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### 5.33 `post.delete`

- Params: `{ to: ref with seq >= 1 }`, nothing else. Mutating.
- Result: `{ seq, ref, changed, deleted }`. `seq` and `ref` are those of the tombstone block last written; when `changed` is `false` nothing is written and they are those of the existing tombstone. `deleted` is the array of the targeted seqs (here one, the post's own seq).
- The target must be the caller's own post (a `post` record, reply and quote included). Refusals, all `USAGE`, nothing written: another author's block, a seq at or past the diary's length, or a block that is not a valid record -> `'referência inválida'`; a profile block -> `'o registro não é uma publicação'`; a tombstone or any other type -> `'não é possível apagar este registro'`. A diary at its limit -> `'limite do diário atingido'`.
- The tombstone is `{ type: 'delete', seq, at }`, with `media` only when the post carries descriptors whose intervals no surviving own post or profile overlaps, in a media core the diary declared (protocol §2). The fold then hides the post (5.12).
- Browser node: the `post.reply` path (unlocked, write gate, append, push); a call that writes nothing still pushes while the seeder is not known to hold the local length. Core node: no write gate.
- After the tombstone is written, the node clears the targeted blocks and the listed media ranges in its own store (protocol §2 "Clearing deleted bytes"); the delete has succeeded whatever the clear does, and a clear that is skipped (`VARANDA_NO_CLEAR=1`) or fails is finished the next time the data dir is opened. A repeat on a target whose bytes are already cleared answers `changed: false` from its tombstone. The cleared seq reads as `invalid` with reason `'deleted'` in `log.read` (5.12). The same applies to 5.33.

### 5.34 `profile.delete`

- Params: `{ to: ref with seq >= 1 }`, nothing else. Mutating.
- Result: `{ seq, ref, changed, deleted }`, with the same meaning as in 5.33. A profile version that forms a compatibility pair (a plain profile block at seq n immediately followed by the same profile with an avatar at n+1, equal name, bio and `at`, the only order `profileRecords` writes; protocol §2) is deleted as one version: `to` may name either block, a plain block pairs only with the block after it and an avatar block only with the block before it, `deleted` lists both seqs in ascending order, and the two tombstones are appended in ONE append (`seq` and `ref` are those of the second).
- The target must be the caller's own `profile` record. Refusals are those of 5.33, with `'o registro não é um perfil'` in place of `'o registro não é uma publicação'` for a post block (the same message, with the kinds swapped, for a profile block passed to 5.33).
- The tombstone and its `media` are as in 5.33.
- Browser node and core node: as in 5.33.

### 5.36 `group.create`

- Params: `{ name, join, visibility?, community }`, nothing else: `name` `1..MAX_GROUP_NAME` (80) code points; `join` `'open'` (anyone may join) or `'approval'` (an admin admits each request); `visibility` `'public'` (default) or `'private'`. Mutating. `community` (lowercase hex64, required) names the community that holds the group: a group always lives in exactly one community (protocol, communities). Creates a group (protocol, groups) inside it: the caller becomes its creator and first admin. Only the community creator creates groups, and only from the device that holds the community root: a caller that is not the creator of the community (in its final state, with a live community writer) -> `USAGE` `'só quem criou a comunidade cria grupos'`; the creator from a device that does not hold the community root -> `USAGE` `'crie pelo aparelho que criou a comunidade'`; community admins moderate but never create groups; the creator whose root lost its powers (the community result's `rootAuthority` is false, the fold's own criterion: after a confirmed creator leave, or a leave written on the root, protocol section 10, "The creator's root after a leave") -> `USAGE` `'sem permissão na comunidade'`; a community the node does not hold yet -> `USAGE` `'aguarde a sincronização da comunidade'`; a community that already holds 32 groups (`MAX_GROUPS_PER_COMMUNITY`) -> `USAGE` `'a comunidade chegou ao limite de grupos'`; a malformed or blocklisted community key -> `NOT_FOUND` `'comunidade não encontrada'`. A private group forces join `'approval'` whatever `join` says (the call is not refused), writes its root header with `name: null` (the name is still required: it travels sealed in a `group-meta`, readable only by members) and starts its first epoch key, which never leaves the node.
- Result: `{ group: hex64 }`, the root key of the new group. Visibility is fixed at creation and no method changes it afterwards (`group.meta` takes no visibility, so one is refused as an unknown field). Needs an identity with a genesis block. A full group list that cannot give up an entry -> `USAGE` `'limite de grupos atingido'` (created groups are never evicted).

### 5.37 `group.join` / 5.38 `group.leave`

- Params: `{ group, community? }`, nothing else (`community` an optional lowercase hex64): `group` the group root key (lowercase hex64). Both mutating. `group.join` joins an open group at once or files a request in an approval group; `group.leave` ends the caller's own membership (and every device's writer of the same diary, protocol section 10) and writes `cuts`: every counted writer of the caller's diary at its local length (the fold reads them only for the creator's root; the records of the diary's other devices are withdrawn whatever they say, protocol section 10), at most `MAX_GROUP_WRITERS_PER_DIARY` entries. The caller needs a live CW in the community of the group (status `'member'` in it, see 5.63), else `USAGE` `'entre na comunidade primeiro'`. `community` is the hint for a group whose root is not held yet (state `'pending'`): a pending root and a call without `community` -> `USAGE` `'informe a comunidade do grupo'`; a held root whose header names another community than `community` -> `USAGE` `'o grupo não é dessa comunidade'`; an orphan group (its header names a community that is not a valid community root) -> `USAGE` `'grupo sem comunidade'`; the group's community not held -> `USAGE` `'aguarde a sincronização da comunidade'`. A group the caller already belongs to answers its state without a new writer. When the caller's own diary is not among the fold's members the state is `'left'`, never null.
- A G root its creator's diary marked (protocol §10, "Creator marks on group roots") is never the device's own writer again: it is not live and is not used for leaving. A returning creator's `group.join`, or the Geral step of `community.join`, writes a new G writer bound to its live CW.
- Result: `{ state: 'member' | 'requested' | 'left' | 'pending' }`. `'pending'`: the node does not hold the group root yet; `group.join` then creates the caller's writer, writes the diary join and lists the group, and the next sync fetches the root (the ban, approval and rejoin checks apply once it arrives). A repeated `group.leave` answers `{ state: 'left' }` without writing anything. Errors (pt-BR messages, never echoing a key): a `group.join` while `bans` lists the caller's diary, a `group.leave` only when the caller's member status is `'banned'`, and a join while the caller's own diary is blocked -> `USAGE` `'sem permissão no grupo'`; a join whose writer would fall outside the 512-writer cap, or when the caller's diary already binds `MAX_GROUP_WRITERS_PER_DIARY` (8) writers in the group -> `USAGE` `'limite do grupo atingido'` (a writer the fold did not count never reports `'member'`); a `group.leave` with nothing to end -> `USAGE` `'nada a alterar'`; a `group.leave` while the group is `'pending'` (root not stored yet) when the caller's own diary join history binds any writer of the group other than this device's -> `USAGE` `'aguarde a sincronização do grupo para sair'`; a loaded `group.leave` never waits for other devices (anyone leaves at once), and its only refusal is the creator's: the caller's diary is the creator's, the root is bound and the root is not among the leave's cuts -> `USAGE` `'saia pelo aparelho que criou o grupo'` (holding the root core suffices; in a loaded group this practically never triggers); a root key on the blocklist, or a malformed key, -> `NOT_FOUND` `'grupo não encontrado'`. A joined group whose root is not held is not an error, see `'pending'`.

### 5.39 `group.post`

- Params: `{ group, text, replyTo?, media?, sealed? }`, nothing else: `text` `1..MAX_TEXT` (1000) code points without media, `0..MAX_TEXT` with media; `media` is optional, an array of 1..4 items with distinct `(core, start)` identities (neither `null` nor an empty array); `sealed` is an optional boolean, absent means false; `replyTo` optional `{ writer, seq }` (exactly these two keys: `writer` lowercase hex64, `seq` an integer `>= 1`), the group post answered. Mutating. There is no `seen` parameter: the node writes `seen` from its own fold at send time. Before the permission check: an orphan group -> `USAGE` `'grupo sem comunidade'`; the group's community not held -> `USAGE` `'aguarde a sincronização da comunidade'` (the same two checks come first in `group.hide` (5.48), `group.meta` (5.49) and `group.rekey` (5.61)). The caller must be a `member` with a live writer, else `USAGE` `'sem permissão no grupo'`; a writer outside the cap -> `USAGE` `'limite do grupo atingido'`.
- Public media items are the exact image descriptors of protocol section 2: `{ core, mime, start, blocks, bytes, sha256, width, height }`, or a voice descriptor with exactly those keys plus `ms`: `mime` is `audio/mp4`, `width` and `height` are 0, `ms` is an integer 1..120000, and `bytes` is at most 1572864 (1.5 MiB). The remaining descriptor rules still apply, including `(blocks - 1) * 32768 < bytes <= blocks * 32768`. A voice note is the only item of its post, never mixed with images or another voice note. Diary posts and avatars remain image-only. With `sealed: true`, every item is a private item of protocol section 10, exactly `{ core, mime, start, blocks, bytes, sha256, key, nonce, plainMime, plainSha256, w, h, ms }`: where the ciphertext lives, with `mime: 'application/octet-stream'` and no `width` or `height` (ciphertext has no image size), then the secret and what it hides. `core`, `start`, `blocks` and `sha256` keep the descriptor bounds (`start` 1..8191, `blocks` 1..256, `start + blocks <= 8192`), with `bytes = blocks * MEDIA_BLOCK_BYTES` because the final block is padded; `key` and `plainSha256` are lowercase hex64, `nonce` is lowercase hex48, `plainMime` is one of `MEDIA_MIMES`, `w` and `h` are integers 1..16384, and `ms` is 0 for images. A private voice item instead has `plainMime: 'audio/mp4'`, `w: 0`, `h: 0`, integer `ms` 1..120000 and at most 49 blocks (the 1.5 MiB plaintext cap plus the 16-byte MAC and padding); it also must be the only item of its post. Mixed lists and a mismatch between the item shape and `sealed` fail with `USAGE` `'parâmetro inválido: media'`; `sealed: true` without `media` fails with `USAGE` `'parâmetro inválido: sealed'`. The node checks the group visibility: private media in a public group -> `USAGE` `'mídia cifrada só em grupo privado'`; public media in a private group -> `USAGE` `'grupo privado exige mídia cifrada'`. Media lives in the writer's media cores, outside the DM blob channel. Text-only posts keep the v1 record shape; posts with media use the exact v2 shape of protocol section 10, with reserved `card: null` and `fwd: 0` filled by the node, never supplied as RPC params.
- Result: `{ seq: integer >= 1 }`, the block of the new record in the caller's writer core.

### 5.40 `group.read`

- Params: `{ group, limit?, before? }`: `limit` `1..GROUP_LIMIT_MAX` (29), default `GROUP_LIMIT_DEFAULT` (29); `before` optional, exactly `{ at, writer, seq }` (`at` a canonical ISO string, `writer` hex64, `seq` an integer `>= 1`), the group-order position of the oldest item the caller holds. Absent = the newest page. Not mutating.
- Result: `{ items: [{ writer, diary, seq, at, text, replyTo, media, hidden, name, username }], next, hidden, incomplete, sealed, epoch, state }`: newest first. `writer` the writer core that holds the post, `diary` the author's diary key, `replyTo` `null` or `{ writer, seq }`, `hidden` boolean, `name` and `username` the author's profile name and verified username (`null` when unknown); `next` `null` or the cursor for the next page; `incomplete` true when the node could not read every writer of the group. `media` is `null` for text-only or hidden posts, otherwise the public descriptors or decrypted private items of 5.39 (including the per-item key and nonce, never the epoch key). **Hidden items are INCLUDED** with `text: ''`, `media: null` and `hidden: true` (the client decides whether to show a placeholder), and `hidden` (the top-level integer) counts the hidden items of THIS page. Posts of authors whose diary the node does not hold or has blocked are left out. A group whose root is not held yet answers `{ items: [], next: null, hidden: 0, incomplete: true, sealed: 0, epoch: null, state: 'ok' }`. Peer text goes through `displayText` (section 10).
- Private groups: `sealed` is an integer, the records of the group this node could not decrypt (no epoch key held; they are left out of `items`; 0 in a public group); `epoch` is `{ writer, seq }`, the `kid` of the epoch key the caller would seal with, or `null` (public group, or no usable epoch); `state` is `'ok'`, `'rekey-pending'` (a removal or admin change observed has no new epoch yet: `group.post`, `group.hide` and `group.meta` answer `USAGE` `'aguardando nova chave'` until a distributor runs `group.rekey` or the new key arrives) or `'locked'` (the browser node is locked, so no epoch key is in memory and nothing can be decrypted or sealed; unlock first). A public group always answers `sealed: 0`, `epoch: null`, `state: 'ok'`. No method ever returns an epoch key, only its `kid`.

### 5.41 `group.list`

- Params: `{ offset?, limit? }`: `offset` an integer `>= 0` (default 0), `limit` `1..GROUP_LIMIT_MAX` (default `GROUP_LIMIT_DEFAULT`). Not mutating.
- Result: `{ groups: [{ group, name, join, role, members, community }], total }` for every group in the caller's local list (`groups.json` or kv `groupWriters`), including groups the caller left. The browser node adds every group root the caller's own diary binds with an `on: true` `group-join` once that root is stored (another device of the account wrote there): only the roots the diary binds now, chosen like the seeder (the first 64 groups by live join seq), and a root not stored yet is not listed. A diary-bound row with no kv `groupWriters` entry on this device, while the fold's status for the caller's diary is absent or `'left'`, answers `role: 'pending'` (name, join and community stay as the fold has them, and the row gains no other field): the account's writer cores are not stored yet, so the app shows "aguardando sincronização" instead of "saiu". A device that already has its own entry keeps the fold's role, and `'banned'` and `'requested'` stay as the fold says. The core node is unchanged, its diary is per device; a group whose root is blocklisted is left out of the list and of `total`. `role` is one of `'creator'`, `'admin'`, `'member'`, `'requested'`, `'banned'`, `'left'` or `'pending'` (`'left'`, never null, when the caller's own diary is not among the fold's members, except that diary-bound row, which answers `'pending'` while the account's writers are not here yet); `members` counts the diaries whose state is `member`. `community` is the root key of the group's community (hex64). An orphan group (header names no valid community root) is left out of the list and of `total`. A group joined before its root arrived is listed as `{ group, name: null, join: null, role: 'pending', members: 0, community: null }`.

### 5.42 `group.info`

- Params: `{ group }`. Not mutating. Result: `{ group, name, join, creator, role, members, state, community, orphan, visibility, memberInvite, writerHere, canWrite, writersBound }`, where `writerHere` (boolean) is whether THIS device has its own writer in the group, and `canWrite` (boolean) is whether a post from this device would succeed: the caller's fold status is `'member'`, this device has a live writer, that writer is counted by the fold (the same check that refuses an uncounted writer with `'limite do grupo atingido'`), the group is not an orphan, the group's community root is held here (and not blocklisted), and a private group's post would not be refused with `'aguardando nova chave'` (the fold is rekey-pending, it has no current epoch, or this device does not hold that epoch's key); a pending group answers `writerHere: true, canWrite: false`; `writersBound` (browser node only, a non-negative integer, not capped at 8: the fold counts only the earliest 8, but every bound writer stays in the count) counts the distinct writers the caller's own diary ever bound in the group with an `on: true` `group-join` (a later leave frees no slot at the seeder), `0` for a pending group, so the app can say why the automatic enrolment of a second device stopped (5.63); a missing field is how an older node answers; `visibility` is `'public'` or `'private'` (`'public'` for a pending group), `name` of a private group is the sealed title when the caller can decrypt it, else `null`, and `role` is as in 5.41 and `state` is the caller's fold state (`'member'`, `'requested'`, `'banned'`, `'left'`, or `'pending'`). On a held root this device has no kv `groupWriters` entry for, that the caller's diary binds now, while the fold status for that diary is absent or `'left'`, `role` is `'pending'` and `state` stays the fold's (`'left'` when the diary is absent), so the screen does not offer a newcomer join while the account's writers are still arriving. `'banned'` and `'requested'` are unchanged, and a device that already has its own entry keeps the fold's role; `memberInvite` is a boolean, whether plain members may invite (default `false`, `false` on a pending result; 5.71); `community` is the root key of the group's community (hex64, `null` for a pending group) and `orphan` is `true` when the header names a community that is not a valid community root (an orphan answers its fold state and every write method refuses it with `USAGE` `'grupo sem comunidade'`); the former `communities` array was removed in protocol v2; `'left'` also when the caller's own diary is not among the fold's members (never null). A malformed or blocklisted root -> `NOT_FOUND` `'grupo não encontrado'`. A group joined before its root arrived answers `{ group, name: null, join: null, creator: null, role: 'pending', members: 0, state: 'pending', community: null, orphan: false, memberInvite: false, writerHere: true, canWrite: false, writersBound: 0 }`; until then `group.read` answers an empty page with `incomplete: true`, `group.leave` works, and every other group method answers `NOT_FOUND` `'grupo não encontrado'`.

### 5.43 `group.members`

- Params: `{ group, offset?, limit? }`: `offset` an integer `>= 0` (default 0), `limit` `1..GROUP_MEMBERS_LIMIT_MAX` (100, also the default). Not mutating.
- Result: `{ members: [{ member, name, username, admin, banned, joinedAt }], total }`: the diaries whose state is `member` or `banned` (requests and departed members are not listed), in key order; `joinedAt` the header time of the diary's oldest bound writer.

### 5.44 `group.requests`

- Params: `{ group, offset?, limit? }`, paged like `group.members` (`limit` `1..GROUP_MEMBERS_LIMIT_MAX`, 100 by default): a group of up to 512 writers can hold more pending requests than one response carries. Not mutating, for admins (else `USAGE` `'sem permissão no grupo'`). Result: `{ requests: [{ member, name, username, at }], total }`, the pending join requests of an approval group, plus (in approval groups) an admitted member with a counted writer the current admission does not cover, such as a device added after the admission, so admins may admit again; `at` is the header time of the diary's newest writer (a rejoin is a new request).

### 5.45 `group.admit` / 5.46 `group.ban` / 5.47 `group.admin`

- Params: `{ group, member, on }`, nothing else: `member` the member's diary key (hex64), `on` a boolean. All mutating. Written through the caller's own writer in G when it holds authority in G, else (for `admit` and `ban`) through its community writer (CW) with `group: G` when the caller is the creator or an admin of the community, else `USAGE` `'sem permissão no grupo'`. `admit` and `ban` are for admins with a live writer; `admin` is for the CREATOR only and writes through the root. `admit` admits (`on: true`) or withdraws an admission; `ban` bans (`on: true`) or lifts a ban (`on: false` names the latest ban in `lifts`; none -> `USAGE` `'nada a alterar'`); `admin` grants (`on: true`) or revokes admin rights. When G's root is marked (a valid `group-cut` of its creator for G's root, protocol §10, "Creator marks on group roots"; a diary gap alone does not count), `admin` with `on: false` writes a CW demotion with `group: G` through the caller's community writer instead, only when the caller's diary is C's creator holding a valid mark on G's root (otherwise it writes nothing and answers `USAGE` `'sem permissão: a saída anterior ainda não foi confirmada'`), and `on: true` -> `USAGE` `'sem permissão no grupo'`. Each record carries `cuts` computed from the writers of `member` the node has folded: `admit` with `on: true` and an unban (`ban` with `on: false`) cut each writer at max(contiguous length, signed length), so records the member signed during the ban that the admin has not downloaded stay banned, while `admit` with `on: false` and a ban (`on: true`) keep the contiguous length. `admin` with `on: true` lists every counted writer of the promoted diary at max(contiguous length, signed length) (never seq 0), because an `on: true` admin grant gives authority only to the writers it lists (protocol section 10); a diary with more counted writers than `MAX_GROUP_CUTS` -> `USAGE` `'limite do grupo atingido'`. A positive `admit` covers only the writers its `cuts` list (unlisted writers keep their previous state), so a writer created after an admit stays hidden until a later admit lists it; a repeated admit names every held counted writer in its `cuts`. An unban (`ban` with `on: false`) likewise covers only the writers its `cuts` list: an unlisted writer stays banned, including one created after the unban, and the unban may cite the same ban again while any counted writer of that diary stays banned; an `admit` withdrawal and a ban still cover unlisted writers from seq 0. An `admit` with `on: true` is refused with `USAGE` `'aguarde a sincronização do grupo para admitir'` when the member's diary is not held or binds a counted writer that is not held, because an admit missing an unheld writer would leave that writer hidden (`on: false` admits and bans are unchanged). A new device of an admin needs a new grant. Targeting the creator, or an admin with `admit`/`ban`, -> `USAGE` `'sem permissão no grupo'`; so does any other caller. Result: `{ ok: true }`.

### 5.48 `group.hide`

- Params: `{ group, target, on }`, nothing else: `target` exactly `{ writer, seq }` (the post), `on` a boolean. Mutating. The post's author may hide or unhide it even after leaving the group (any bound writer of the author's diary); anyone else must be an admin with a live writer, else `USAGE` `'sem permissão no grupo'`. Result: `{ ok: true }`. Orphan and missing-parent errors as in 5.39.

### 5.49 `group.meta`

- Params: `{ group, name?, join? }`: at least one of `name` (`1..MAX_GROUP_NAME` code points) and `join` (`'open'` or `'approval'`); none -> `USAGE` `'nada a alterar'`. Mutating, for the CREATOR only (root record; others `USAGE` `'sem permissão no grupo'`). On a marked root (protocol §10, "Creator marks on group roots") `group.meta` and every other append on the root, key distribution from the root included, are refused with `USAGE` `'sem permissão no grupo'`. Result: `{ ok: true }`. In a private group a `join` other than `'approval'` -> `USAGE` `'grupo privado exige aprovação'` (a private group is always approval). ### 5.50 `identity.install` (IPC only)

- Params: `{ prf: hex64, credentialId: string, userId: hex64 | '', rpId: string, resumed: boolean }`, all required, nothing else. Mutating. `prf` is the passkey's 32-byte PRF output in lowercase hex; `credentialId` is 1..1024 printable ASCII characters without space (`0x21`..`0x7e`); `userId` is the passkey's user handle in lowercase hex or `''`; `rpId` is 1..253 characters; `resumed` is `true` when `prf` comes from the host's stored session rather than a ceremony just finished.
- Result: `{ publicKey: hex64, resumed: boolean }`.
- IPC only, offered only by the in-app web-node worklet (the `web` node kind: `packages/web-member` running inside the Bare worklet), next to its session's handlers; the node session (`session.handlers`), the browser node's own session, `varanda-serve` and the browser page do not register it, so elsewhere it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6), as 5.17.
- The host's counterpart of the browser handle's `install` step (section 11, `identity.unlock` / `identity.complete`): the host runs the WebAuthn ceremony itself and hands over only its PRF output; the worklet derives the identity and media key pairs (`packages/web-member/lib/passkey.js`), zero-fills `prf` and its copies, and answers. A key pair for another diary, or a legacy store, leaves the node locked and fails with `USAGE` `'passkey não corresponde ao diário guardado'`; any failure after the pairs went in leaves the node locked.
- Security: `prf` is the root secret every member key derives from. It crosses the IPC exactly once per unlock (or per resume from the host's stored session) and never appears in a result, an event, an error message or a log. A non-resumed install binds the passkey record but does NOT lift the `signedOut` marker (5.54): only 5.55 does, after the host saved the new session. A resumed install while `signedOut` is set is refused, and the host then deletes its stored session, so a stored record never outlives 'Sair'.

### 5.56 `media.uploadFile` (IPC only)

- Params: `{ name: string, mime: string, width: integer, height: integer, kind?: 'voice', ms?: integer, sealed?: boolean }`, `name`, `mime`, `width` and `height` required, nothing else. Mutating. `name` matches exactly `/^[0-9a-f]{32}\.bin$/` (32 lowercase hex characters then `.bin`, the name the host generates). Images use `mime` in `MEDIA_MIMES`, integer `width` and `height` 1..16384, and neither `kind` nor `ms`. A voice upload requires `kind: 'voice'`, `mime: 'audio/mp4'`, `width: 0`, `height: 0` and integer `ms` 1..120000. Audio without `kind: 'voice'`, an image with that kind, and zero image dimensions are refused. `sealed: true` asks the node to seal the image or voice note for a private group. The node checks voice bytes with `audioBounds` and enforces the 1572864-byte plaintext cap; neither bytes nor paths cross RPC.
- Result: the media descriptor of the browser handle's `media.upload` (section 11, `packages/web-member/lib/session.js` `mediaUpload`): `{ core, mime, start, blocks, bytes, sha256, width, height }`, the value a later `post.create` / `post.reply` / `post.quote`, public `group.post` or `profile.set` `avatar` carries for images. A voice descriptor additionally carries `ms`, has zero dimensions and is accepted only by public `group.post`. With `sealed: true`, the node seals the image or voice note under a fresh key and nonce (protocol section 10: padded to whole blocks, secretbox), appends only the ciphertext to the writer's media core and answers with the private item `{ core, mime, start, blocks, bytes, sha256, key, nonce, plainMime, plainSha256, w, h, ms }` (`mime` `'application/octet-stream'`, `plainMime` the given `mime`, `w` and `h` the given `width` and `height`, `ms` 0 for images or the voice duration), the value a later private `group.post` carries with `sealed: true`. The key appears only in this result and, later, inside the group-sealed post; it is never logged and never uses the DM blob channel.
- IPC only, offered only by the in-app web-node worklet (the `web` node kind: `packages/web-member` running inside the Bare worklet), next to its session's handlers; the node session (`session.handlers`), the browser node's own session, `varanda-serve` and the browser page do not register it, so elsewhere it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6), as 5.17.
- Why a name and not a path: one request is capped at `MAX_REQUEST` (64 KiB) and an item may be 8 MiB, so the host writes the prepared media to its cache directory and names the file. The worklet joins `name` to the cache directory passed at worklet start and resolves no caller-supplied path: deciding on the real path of a requested path and then opening that path string again would leave a window in which a writer swapping a parent directory for a symbolic link gets a file outside the cache read, published and deleted. The name rule leaves no separator, dot segment or other directory to name. The worklet refuses (`USAGE`) a final component that is a symbolic link or not a regular file (`lstat` before the open) and requires the opened descriptor to be that same regular file (`fstat`: same device and inode); anything else is refused and nothing is read. The bytes then follow the `media.upload` rules (size, the unlocked identity with a media key, block 0, the first upload's `media-core` declaration). That same file is deleted after a successful upload. Neither the name nor anything about the bytes appears in a result, an error message or a log.

Creates the community root and its first group, Geral (protocol, communities). Result: `{ community, group }`: the community root key and the root key of Geral (both hex64). A full group list that cannot give two slots (the community and Geral) -> `USAGE` `'limite de grupos atingido'`. A create interrupted after the root was written is resumed by repeating the call (the node reuses the root and the Geral already written) and answers the same keys.

### 5.59 `community.info`

- Params: `{ community }`. Not mutating. Result: `{ community, name, join, creator, role, state, members, admins, groups: [{ group, name, visibility, join, role, general, last, unread }], general, incomplete, memberInvite, writerHere, canWrite, rootHere, authorityHere, writersBound, generalWritersBound }`: `writersBound` (browser node only) is as in 5.42 for the community root (`0` on a pending result); `generalWritersBound` (browser node only) is the same count for Geral's root, read from the caller's own diary so it holds even before Geral's root is here (`0` when Geral is unknown and on a pending result), because `community.join` also joins Geral and spends a slot there; `writerHere` (boolean) is whether THIS device has its own community writer, `canWrite` (boolean) whether a community write from this device would succeed: the caller's fold status is `'member'` and this device has a live community writer that the fold counts (in an approval community a community writer is live when the diary is a member; a writer past the cap still looks live so the write can name the cap, but it is not counted, so `canWrite` is false), and `authorityHere` (boolean) whether this device's own community writer carries community authority in the fold now (the creator's root or writers, or an admin's granted writers; pending answers `false`), and `rootHere` (boolean) whether this device holds the community root as its own writer (the creating device); a device that only holds the root answers all three `false`, and a second tap of `community.join` there creates the device's writer; a pending result answers `canWrite: false`; `writerHere` is `true` when this device already has a kv `groupWriters` entry for the community, and `rootHere` is `true` when that entry holds the root nonce (the creating device, including an interrupted `community.create` that already stored the root); with no entry all of them are `false`; a missing field is how an older node answers. `state` is `'ready'`, or `'pending'` when the community root is not held yet; `role` is as in 5.41 (`'left'` when the caller is not a member; `'pending'` on a held root this device has no kv entry for, that the caller's diary binds now, while the fold status for that diary is absent or `'left'`, with `state` still `'ready'`, so the screen does not offer a newcomer join while the account's writers are still arriving; `'banned'` and `'requested'` stay, and a device that already has its own entry keeps the fold's role); `members` counts the diaries whose state is `member`; `admins` is an integer count of admins (the creator included); `groups` is the catalogue in key order, at most `MAX_GROUPS_PER_COMMUNITY` (32), and `name`, `visibility`, `join` and `role` of a row are `null` when the node does not hold that group root; `last` and `unread` are on every row, an unheld root included (`last: null`, `unread: 0`): `last` is `null` or `{ name, username, preview, at, mine, hidden }`, the newest post in causal order among the posts `group.read` (5.40) would list, only when the row's `role` is `creator`, `admin` or `member` and the root is held, else `null` (`name` and `username` are `string|null`, `preview` is the peer text cut to 140 code points and `''` when hidden, `at` a canonical ISO string, `mine` and `hidden` booleans, `mine` true when the post's diary is the own diary key); `unread` is an integer `0..99` (99 means 99 or more) counting those posts after this device's seen mark (`group.seen`, 5.82) in causal order: the posts listed after the marked post when it is still listed, else those whose group-order position `{ at, writer, seq }` (the `before` order of 5.40) is greater; no mark, or a mark dropped by the 512 cap, counts all of them; it excludes the own diary's posts and hidden posts, and is `0` whenever `last` is `null`; a private group this device cannot open (browser locked or no epoch key) contributes no post and no sealed plaintext, and the read never writes, not even the seen file; `general` is the key of Geral, `null` while unknown; `incomplete` is `true` when the fold reports a missing part; `memberInvite` (boolean) is whether plain members may invite (default `false`, `false` on a pending result; 5.72); `dropped` (sorted hex keys, protocol §10) lists the groups currently taken off the list; `repair` (boolean) is `true` when the caller is C's creator, C's root has no authority, the community result's `cwDemote` is true and the caller has a live CW: the creator can then use `community.meta` through its CW and `community.removeGroup` (5.70); `leavePending` (boolean) is `true` only when this device holds a local note of the creator's own C leave (protocol §10, `community-leave.json`) whose writer is the local CW, the diary join of that CW is still on, and the block at the note's seq, on an unforked own CW, is the `group-leave` whose `leaveDigest` is the note's `digest`, whatever the diary's status in C: the creator's leave was interrupted and `community.leave` finishes it. The read writes nothing. A pending community answers `{ community, name: null, join: null, creator: null, role: 'pending', state: 'pending', members: 0, admins: 0, groups: [], general: null, incomplete: true, dropped: [], repair: false, leavePending: false, memberInvite: false, writerHere: false, canWrite: false, rootHere: false, authorityHere: false, writersBound: 0, generalWritersBound: 0 }`. An interrupted `community.create` that already stored this device's community writer answers that same pending result with `writerHere: true`, and with `rootHere: true` when the entry holds the root nonce. A malformed or blocklisted root -> `NOT_FOUND` `'comunidade não encontrada'`. Peer text goes through `displayText` (section 10).

### 5.60 `community.admin`

- Params: `{ community, member, on }`, nothing else: `member` a diary key (hex64), `on` a boolean. Mutating, for the CREATOR of the community only (it writes a `group-admin` through the community root; others `USAGE` `'sem permissão na comunidade'`). Grants (`on: true`) or revokes admin rights; a community admin acts as an admin in every group of the community (ban, admit, hide, through its community writer) and never appoints group admins. for `on: true`, `member` must be a `'member'` of the community, else `USAGE` `'a pessoa precisa ser membro da comunidade'`; `on: false` also revokes an admin that left the community or is pending, so its grant never shields it from a ban; `member` equal to the community creator -> `USAGE` `'o criador da comunidade já administra'`; `on: false` for a diary C's root never granted -> `USAGE` `'nada a alterar'` (both nodes); the node decides by the community result's `rootAuthority` (protocol §10): `on: true` needs it; without it, `on: false` writes a CW demotion (`group-admin` with `group: null`, protocol §10) through the creator's live CW only when the community result's `cwDemote` is true (a confirmed creator leave, or a creator leave written on C's root, bounds the root), so a returning creator can still remove any admin; otherwise it writes nothing and answers `USAGE` `'sem permissão: a saída anterior ainda não foi confirmada'`; `on: true` without it -> `USAGE` `'sem permissão na comunidade'` (5.69). Result: `{ community, member, on }`.
- Cuts follow the group admin rule of 5.47, computed by the node from the counted community writers (CW) of `member` it has folded. `on: true` lists them at max(contiguous length, signed length) (never seq 0) and gives authority ONLY to the writers it lists, from the listed seq on: nothing is retroactive, and a new device of the admin needs a new grant. `on: false` lists every known CW at its contiguous length and keeps the restrictive rule: an unlisted writer is cut at seq 0. A grant carries at most 8 cuts (the writers a diary may bind) and never more than `MAX_GROUP_CUTS`. A community admin acts as an admin in every group of the community; the cut also covers the member's writers in those groups.

- Mutating community methods follow the same client rule as group methods (never resent, `uncertain: true` on a lost connection); see the event rules in section 6 for what each one emits.

### 5.61 `group.rekey`

- Params: `{ group }`, nothing else. Mutating. Writes a new epoch key for a private group and distributes it (`group-key`, sealed to each current recipient, protocol section 10) after a removal or admin change; allowed only to an authorized distributor (the creator, a group admin, or a linked community creator or admin holding power in the group). Result: `{ group, epoch: { writer, seq } }`, the `kid` of the new epoch. The key itself is never returned by this or any other method.
- Errors (pt-BR): an orphan group or a missing parent community as in 5.39; a public group -> `USAGE` `'grupo público não usa chave'`; a caller who is not a distributor -> `USAGE` `'sem permissão no grupo'`; a locked browser node -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a malformed or blocklisted root, or a group the node does not hold -> `NOT_FOUND` `'grupo não encontrado'`. A rekey on a group already at a current epoch still writes a new one.
- History re-share (browser node, automatic): a device that may distribute in a private group (the creator, a group admin or a community authority, through its live counted writer) hands every epoch key it holds to each entitled writer the epoch's recipients do not list yet, after its own diary or the group grows: continuation `group-key` blocks only, no rotation; the same hand-off this method does before rotating. A second device of the creator or of an admin is entitled (protocol section 10, "History on admit"); a requested writer never is. It writes nothing while the browser is locked, and a hand-off that would not fit the log writes nothing.

### 5.62 `community.list`

- Params: `{}`, nothing else (any field -> `USAGE`). Not mutating. Result: `{ communities: [{ community, name, join, state, role, general }] }`: `community` is the community root key (lowercase hex64); `name` and `join` the community's name and join rule, or `null` when the root is not held yet; `state` is `'ready'` when the root is held and folds, else `'pending'`. A diary-bound community this device has no kv `groupWriters` entry for, while the fold's status for the caller's diary is absent or `'left'`, is listed with `state: 'ready'` (its root is held and folds) and `role: 'pending'` (name, join and general stay), so the app shows "aguardando sincronização" instead of "saiu". A device that already has its own entry keeps the fold's role, and `'banned'` and `'requested'` stay as the fold says. `role` is otherwise as in 5.41; `general` the key of Geral, or `null`.
- Entries: every community in the caller's local list (created or joined; the core node's `groups.json` entries and the browser node's kv `groupWriters` entries of kind `community`), one entry per key. The browser node also lists every community root the caller's own diary binds with an `on: true` `group-join` once that root is stored, even when this device never wrote there: only the roots the diary binds now (chosen like the seeder: the first 64 groups by live join seq), a root not stored yet is not listed, and a community every device left is not listed on a device that never wrote in it. The core node is unchanged, its diary is per device. Order: creator, admin, member, then the rest; within each, by name (`null` last), then by key. At most `COMMUNITY_LIST_MAX` (64) entries, never paged. A blocklisted root, and a held root that is not a community root, are left out. `group.list` (5.41) never lists a community. Peer text goes through `displayText` (section 10).

### 5.63 `community.join`

- Params: `{ community }`, nothing else (lowercase hex64). Mutating. Joins an open community at once or files a request in an approval community: the node writes the caller's community writer (CW) and the diary join in it, and, when the caller becomes a member, joins Geral too.
- Interrupted creator leave: when this device holds a local note of the creator's own C leave that matches (the same check as the `community.leave` retry and `leavePending`, 5.59 and 5.64), the join first finishes that leave, whatever the diary's status in C and before any new CW: the missing root marks at the noted cuts, the `group-confirm` of exactly that leave unless present, the off join, and clearing the note. Only then does it write the new CW and its join. A failure there throws (`uncertain: true`) and nothing is joined. The new CW's `rejoin` then names that leave, now confirmed.
- Binding join: when a node binds a new CW of a community whose header has a `rejoin` (a fresh CW, a reused CW never bound, or a CW the pending path of `community.join` reuses while C's root is not held yet), its first `on: true` `group-join` carries the same `rejoin` (the 6-key join, protocol §2); a CW without `rejoin` gets the 5-key join. The fold counts the CW's generation only when the two match (protocol §10).
- Rejoin (a diary that left): the new CW's `rejoin` names a leave of the caller's own device when it can, so a leave a stolen sibling appends never becomes the boundary of this device's history (protocol §10, "Leave sets and stale leaves"). In order: the counted leave of this device's CW when it is of the diary's latest leave set; else, when this device's CW (not the community root) is bound and counted and holds no leave, the node first appends a `group-leave` on it (cuts listing every counted own CW held, each at its contiguous length, never C's root, so a creator returning after a forged leave keeps its root powers; `seen` the fold's latest leave), then the diary's `group-confirm` for exactly that leave (the confirmation, protocol §10 "Confirmed leaves") and the `group-join` `on: false` for that CW, and names it once counted; else the first confirmed leave of the diary's latest leave set (`confirmedLeaveOf`); else the diary's causally latest counted leave (`lastLeave`). A failure after that extra leave surfaces like any other failure of the call (`uncertain: true`).
- Result: `{ state: 'member' | 'requested' | 'left' | 'pending', group: hex64 | null }`: `group` is Geral when a Geral writer of the caller exists after the call. `'pending'`: the community root is not held yet; the next sync fetches it. Errors: the caller banned -> `USAGE` `'sem permissão na comunidade'`; a writer outside the cap -> `USAGE` `'limite da comunidade atingido'`; a full group list -> `USAGE` `'limite de grupos atingido'`; a malformed or blocklisted key -> `NOT_FOUND` `'comunidade não encontrada'`. A partially landed join (the CW written, Geral not) is reconciled by re-reading `community.info` and repeating the call, which is idempotent; the client never resends it by itself.
- Automatic enrolment (browser node): a device of the same passkey enrols by itself, after a sync, through the same path as this method and `group.join` (a public `group-join` in the diary, and one of the 8 writer slots per account per root that the seeder never releases). Only a root the caller's own diary binds now (an `on: true` join, chosen like the seeder), that this device holds and has no kv `groupWriters` entry for (so it is enrolled at most once: an approval community never gets a second CW while the first waits), whose fold says the diary is a `member` there, and where the diary binds fewer than 6 of the 8 writers (`AUTO_ENROL_RESERVE` = 2: the last two are spent only by an explicit tap; `writersBound`, 5.42 and 5.59, shows the count). Communities first; then groups, only when this device's community writer is admitted (in an open community, or for its creator, the CW the same pass writes counts at once). Geral is planned like any group, with its own checks (the diary's status in Geral, the reserve, a full root): a diary that left Geral is not put back, and the automatic path never takes `community.join`'s Geral step, which the explicit method keeps. A listed writer the own diary never bound (a join whose diary append failed) is bound again through the same writer, never a second one; binding it spends a slot, so the reserve applies. Never a left, banned, requested, blocklisted, unheld or orphan root, never a root of an opened link or a catalogue the diary did not join, never through the pending path (a root not held, or a community whose creator is not bound yet), and never a private group while the browser is locked. Nothing is admitted or granted automatically: in an approval community a plain member's new CW counts at once, but its writers in the community's groups wait for an admin, and a private group keeps its approval step. A skipped root keeps the explicit `community.join` / `group.join`. The core node is unchanged (its diary is per device).

### 5.64 `community.leave`

- Params: `{ community, force? }`, nothing else. `force` is optional: a boolean, or a non-empty array without duplicates of `'root'`, `'devices'` and `'groups'` (anything else -> `INVALID_PARAMS`); `true` skips every wait below, an array skips only the waits it names. The nodes check the waits in the order root, devices, groups; the CLI `--force` sends `true`. Mutating. Ends the caller's membership in the community (every device's writer of the same diary) and writes `cuts` as `group.leave` does (5.38). In the same call it first writes a `group.leave`-shaped `group-leave` on every live writer of this device in every held group of the community (best effort), then the community leave, then turns the joins off. After leaving, the caller has no authority in the community's groups: its earlier bans, admissions and nominations there stop counting (protocol §10, owner decision). A pending request in an approval community is withdrawn the same way. A member whose only CW is one C's ban layer still covers (an unban that did not list it) leaves through that CW (bound, counted, holding no leave), so a member is never locked in C. Every node that appends a community leave writes, in its diary, the `group-confirm` for exactly that leave (`writer`, `seq`, `digest` = `leaveDigest`; protocol §2 and §10, "Confirmed leaves"); only that record confirms the leave, and the off join that follows confirms nothing. Order for a member: the C leave, the `group-confirm`, the off join. For C's creator, a confirmed leave (or one written on C's root) ends the root's authority for good (protocol §10, "The creator's root after a leave"): after returning it no longer names admins, edits the community or creates groups. A forged, unconfirmed leave on another device ends nothing. Order for C's creator: the local note, the C leave, the root marks, the `group-confirm`, the off join, then the note is cleared. The marks are one diary `group-cut { group: G, writer: G, cut: <the root's held length> }` per group root of C's catalogue that the creator's own diary bound (an `on: true` `group-join` with `writer` equal to the group) (protocol §2 and §10, "Creator marks on group roots"). A held bound root counts only when its block 0 is a valid v2 group header with kind `group`, `community` equal to this C and `diary` equal to the creator's own; a held root naming another community or diary is skipped (not marked, not waited for), while an unheld bound root stays missing (`force` passes it). Once a confirmed creator leave bounds C's root (`creatorConfirmSeq` finite), a later leave neither marks nor waits for a group it left unmarked: marks written after that confirmation do not count (protocol §10), so that root stays without root authority for good. A confirmed leave that does not touch C's root does not stop the marks. Catalogue entries without that binding are ignored: never waited for, never marked. A bound root held but forked is skipped (no wait, no mark). A bound root held, unforked and non-empty is marked at its held length, read after the creator's own group leaves. A bound root not held (or empty) makes the call answer `USAGE` `'aguarde a sincronização dos grupos da comunidade para sair'` with nothing written, unless `force` skips the groups wait: then the leave proceeds and those roots stay unmarked, and after the confirmed leave what such a root did before no longer counts (protocol §10, `rootCut` 0). The note's `roots` lists exactly the marked roots. Each root is tried; if any mark fails, the call fails (`uncertain: true`) after trying the rest, and neither the `group-confirm` nor the off join is written, so the leave stays unconfirmed (protocol §10, "Confirmed leaves"). The creator's local note (v 2, protocol §10: `{ community, writer, seq, digest, roots: [{ group, cut }] }`) is written BEFORE the append, with `seq` the CW length then; after the append the block at `seq` must be that leave, else the note is kept and the call fails with `'a saída gravada não confere; tente sair de novo'`. A failed mark keeps the note. A later `community.leave` finishes a noted creator leave whatever the diary's status in C, on the same rule as `leavePending` (5.59: the note's writer is the local CW, its diary join is still on, and the leave at `note.seq` on an unforked own CW has `note.digest`): it writes the missing marks at the NOTED cuts, the `group-confirm` unless present, then the off join, then clears the note, and answers `{ state: 'left' }`; otherwise it writes nothing and answers `{ state: 'left' }`. A leave on the own CW that does not match the note is never confirmed by this device. A returning creator's G-root powers do not come back either; it still acts in G as C's creator through its new CW. Result: `{ state: 'left' }`.
- Errors: the caller banned -> `USAGE` `'sem permissão na comunidade'`; nothing to end -> `USAGE` `'nada a alterar'`; the creator from a device whose cuts miss the root -> `USAGE` `'saia pelo aparelho que criou a comunidade'`; C's creator whose diary bound C's root while this device's copy of C's root is behind the root's signed length, unless `force` skips `'root'` -> `USAGE` `'este aparelho ainda não baixou tudo da comunidade: aguarde para sair'`, nothing written; with `force` skipping `'root'` the leave proceeds and lists C's root at the contiguous length held, so a tail not yet held never counts; C's creator while any counted own CW in C (not the root) is not held or is held below its signed length, unless `force` skips `'devices'` -> `USAGE` `'aguarde a sincronização dos seus aparelhos nesta comunidade para sair'`, nothing written; the creator while a group root of C its diary bound is not held locally (or is empty) and `force` does not skip `'groups'` -> `USAGE` `'aguarde a sincronização dos grupos da comunidade para sair'`, nothing written; the community `'pending'` while other devices of the diary are bound -> `USAGE` `'aguarde a sincronização da comunidade para sair'` (not a `force` wait: `force` does not skip it, and the app offers no "Sair mesmo assim" for it).

### 5.65 `community.members`

- Params: `{ community, offset?, limit? }`, paged like `group.members` (5.43): `offset` an integer `>= 0` (default 0), `limit` `1..GROUP_MEMBERS_LIMIT_MAX` (100, also the default). Not mutating. Result: `{ members: [{ member, name, username, admin, banned, joinedAt }], total }`, with the same meaning as in 5.43 for the community. Errors as in 5.43, with `NOT_FOUND` `'comunidade não encontrada'`.

### 5.66 `community.requests`

- Params: `{ community, offset?, limit? }`, paged like `community.members`. Not mutating, for the creator and admins of the community (else `USAGE` `'sem permissão na comunidade'`). Result: `{ requests: [{ member, name, username, at }], total }`, with the meaning of 5.44.

### 5.67 `community.admit`

- Params: `{ community, member, on }`, nothing else: `member` a diary key (hex64), `on` a boolean. Mutating. Admits (`on: true`) or withdraws the admission of a member, with the rules and cuts of 5.45 written through the community writers. An `admit` with `on: true` when the member's diary is not held, or binds a counted CW that is not held -> `USAGE` `'aguarde a sincronização da comunidade para admitir'`. Result: `{ ok: true }`.

### 5.68 `community.ban`

- Params: `{ community, member, on }`, nothing else. Mutating. Bans (`on: true`) or lifts a ban (`on: false`) with the rules of 5.46. Targeting the creator or an admin of the community -> `USAGE` `'sem permissão na comunidade'`; so does any caller who is not the creator or an admin. Result: `{ ok: true }`.

### 5.69 `community.meta`

- Params: `{ community, name?, join? }`: at least one of `name` (`1..MAX_GROUP_NAME` code points) and `join` (`'open'` or `'approval'`); none -> `USAGE` `'nada a alterar'`. Mutating, for the CREATOR only (others `USAGE` `'sem permissão na comunidade'`). Result: `{ ok: true }`. While C's root has authority (`rootAuthority`, protocol §10) the node writes the meta on the root. Once the root's powers ended and `cwDemote` is true, it writes a CW meta (`group-meta` with `group: null`) on the creator's live CW, which sets name and join (protocol §10, "Community repair after the creator's return"). With the root's powers gone and `cwDemote` still false -> `USAGE` `'sem permissão na comunidade'`, nothing written. `community.admin` `on: true` (5.60) still needs `rootAuthority`. A forged, unconfirmed leave leaves `rootAuthority` true.

### 5.70 `community.removeGroup`

- Params: `{ community, group, undo? }`, nothing else (`community` and `group` lowercase hex64, `undo` an optional boolean, default `false`). Mutating. With `undo: true` it writes a `group-drop` with `on: false` on the creator's live CW, which puts a dropped group back in the list; a group that is not currently dropped -> `USAGE` `'nada a alterar'`; same gate and Geral refusal as removal. Otherwise it takes `group` out of the community's catalogue by writing a `group-drop` on the caller's live CW (protocol §10, "Community repair after the creator's return"); the group then resolves as an orphan. Only C's creator, a member, once the root's powers ended (`cwDemote` true and `rootAuthority` false), through its live CW; otherwise `USAGE` `'sem permissão na comunidade'`. Geral -> `USAGE` `'o grupo Geral só sai com a comunidade'`; a group not in the list -> `USAGE` `'nada a alterar'`. A removal writes `group-drop` with `on: true`. Result: `{ ok: true }`. Emits `groups.changed` for C and G. As every mutating method, it is never resent by the client, and an unknown outcome surfaces `uncertain: true`.

- Community root not held yet (5.65 to 5.70): the two nodes answer differently, and both are as implemented. The core node (`packages/core/lib/session.js`) refuses with `USAGE` `'aguarde a sincronização da comunidade'`; the browser node refuses with `NOT_FOUND` `'comunidade não encontrada'`. Clients treat either as "not available yet" and never resend a mutating call by themselves.

- Mutating community methods (`community.create`, `community.join`, `community.leave`, `community.admit`, `community.ban`, `community.meta`, `community.admin`, `community.removeGroup`, `community.invitePolicy`), `group.create` and `group.invitePolicy` are never resent by the client; a lost answer surfaces `uncertain: true` (section 9).

### 5.71 `group.invitePolicy`

- Params: `{ group, members }`, nothing else: `group` a lowercase hex64 key, `members` a boolean. Mutating. Turns "membros podem convidar" on (`true`) or off (`false`) for the group; it only says whether plain members may invite (the invite itself only notifies and this setting never changes admission). The group's creator or a group admin writes a `group-invites` record on its own writer; a creator or admin of the group's community writes it through its community writer with `group: G` (protocol §10). Private groups are allowed: the record is plaintext.
- Errors (pt-BR): anyone else -> `USAGE` `'sem permissão no grupo'`; the same value as the current setting -> `USAGE` `'nada a alterar'` (nothing written); an orphan group -> `USAGE` `'grupo sem comunidade'`; a malformed or blocklisted key, or a group the node does not hold -> `NOT_FOUND` `'grupo não encontrado'`, as in 5.49. A lost answer is `uncertain: true` and is never resent. Result: `{ ok: true }`.

### 5.72 `community.invitePolicy`

- Params: `{ community, members }`, nothing else: `community` a lowercase hex64 key, `members` a boolean. Mutating. Turns "membros podem convidar" on or off for the community. The community's creator (on the root while it has authority, or on its live community writer after the root's powers ended, as in 5.69) or a community admin (on its own community writer) writes a `group-invites` record with `group: null` (protocol §10).
- Errors (pt-BR): anyone else -> `USAGE` `'sem permissão na comunidade'`; the same value as the current setting -> `USAGE` `'nada a alterar'` (nothing written); a malformed or blocklisted key -> `NOT_FOUND` `'comunidade não encontrada'`. A lost answer is `uncertain: true` and is never resent. Result: `{ ok: true }`.

### Conversas (5.73 to 5.81, 5.88)

Private 1:1 messages between two diaries (protocol section 11): text with optional photos or one voice note. Browser node only (`packages/web-member/lib/session.js`). No read receipts, no typing state, no presence, and no method below accepts a field for any of them. A photo or voice note travels as an end-to-end encrypted blob on the anonymous blob channel (protocol section 13); the message carries its media item (5.75), whose `key` decrypts it, and the item reaches the UI only in a `dm.thread` result of the owning session, never in an event, an error or a log. Every `text`, `preview` and `quote` a result carries is peer text: the UI renders it through `displayText` with `multiline: true` (section 10, section 11).

- Node session (`packages/core/lib/session.js`): every `dm.*` method except `dm.reportSign` answers `USAGE` `'mensagens diretas disponíveis só no navegador'`, with or without an identity, before anything is opened, read or written (the box key derives from the passkey PRF output, which only the browser node holds). `dm.reportSign` answers `USAGE` `'assinatura disponível só no navegador'`, as `report.sign` (5.20).
- Browser node: with no identity -> `NOT_FOUND` `'identidade não encontrada'`; locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a key that does not match the stored diary -> `USAGE` `'passkey não corresponde ao diário guardado'`. This applies to every method below except `dm.lookup`, which reads public records only.

### 5.73 `dm.enable`

- Params: `{}`, nothing else. Mutating.
- Derives the own box key pair for the current generation (protocol section 11, "Key") and appends one `dm-key` record to the own diary only when the diary has none, or its newest valid `dm-key` names another `gen` or another `box` than the derived one, or falls outside the newest `DM_KEY_REFRESH_BLOCKS = 256` blocks; otherwise appends nothing. Whether an append is due is read on the live run's cores (section 6.1), so a start whose local newest key has this `box` and `gen` within that window runs neither the write gate nor a preemption; an append still goes through the write gate of section 11 (catch-up, then push), like `profile.set`. A check made before the diary caught up (by `dm.enable` or the unlock refresh) is repeated once after the next catch-up of a continuous sync.
- Result: `{ box: hex64, gen: integer >= 1, seq: integer | null }`; `seq` is the appended block, `null` when nothing was appended. Safe to call on every start: the app calls it once per unlocked session on a hosted node, so every member can receive messages without first opening Conversas. As every mutating method it is never resent by the client; an unknown outcome surfaces `uncertain: true` and the UI calls it again only after re-reading (`dm.lookup` of the own key).

### 5.74 `dm.lookup`

- Params: `{ member }`, nothing else (`member` lowercase hex64). Not mutating.
- Result: `{ box: hex64 | null, gen: integer | null }`: the newest valid `dm-key` of that diary (highest `gen`, ties by highest seq) from the local replica, else through the on-demand read of `diary.peek` (5.27, protocol section 6 "Browser node on-demand reads"). A weak box key reads as `null`. `box: null` (and `gen: null`) means the person cannot receive messages yet; the app shows `'ainda não recebe mensagens'`.
- Opens no conversation and contacts the peer in no way; the on-demand read is the same exposure as opening a profile.

### 5.75 `dm.send`

- Params: `{ to, text, replyTo?, media? }`, nothing else: `to` lowercase hex64 (the recipient's diary key); `text` `1..MAX_TEXT` (1000) code points, or `0..MAX_TEXT` when `media` is present (a media-only message); `replyTo` optional, an inner message id (32 lowercase hex); `media` optional, `1..MAX_DM_MEDIA` (4) media items. A call without `media` is the text-only call of earlier versions, unchanged. Mutating.
- A media item is exactly `{ id, key, nonce, chunks, bytes, sha256, mime, w, h, ms }`, nothing else, every field required: a blob descriptor (protocol section 13; `id`, `key` and `sha256` lowercase hex64, `sha256` of the ciphertext; `nonce` 48 lowercase hex; `bytes` the ciphertext length, plaintext plus the 16-byte MAC, an integer `17..257 x 32768`; `chunks` `1..257` and equal to `ceil(bytes / 32768)`) plus `mime` one of `MEDIA_MIMES`, `w` and `h` integers `1..16384`, and `ms` `0` for images. A voice item uses `mime: 'audio/mp4'`, `w: 0`, `h: 0`, integer `ms` 1..120000 and at most 1572880 ciphertext bytes (1572864 plaintext bytes plus the 16-byte MAC); the same blob descriptor rules apply. A voice note must be the only media item of the message, never mixed with images or another voice note. The item is the result of `dm.putMedia` (5.88) on the native app, or of the node's media facade on the web (5.88), passed back unchanged; the node seals it as given, in the order given. The params check is `lib/methods.js`; the node checks the frame budget.
- A message with `media` is a v2 inner (protocol section 11): a reader of an earlier version drops it (no text fallback), as an older reader drops a post with media. Text and items share the fixed sealed frame, so the text that still fits shrinks with every item; the pure budget lives in `lib/dm-budget.js` (section 12), so the composer can count it without the node. A request at its largest (1000 four-byte characters and 4 items) is about 5.6 KB, far below `MAX_REQUEST`.
- Seals the message to the recipient's newest box key and a self copy to the own box (two drops, each with its own `dropId` and stamp, protocol section 11 "Multi-device"), puts both on the anonymous channel `'varanda/dm/1'` and files the own copy locally once the seeder acknowledged.
- Result: `{ id: hex32, at: ISO }` after the seeder's ack: the inner message id and its time.
- `USAGE` messages: `to` = the own key -> `'não é possível enviar para si'`; a blocked peer -> `'você bloqueou esta pessoa'`; no valid `dm-key` for `to` -> `'esta pessoa ainda não recebe mensagens'`; no stamp left and the seeder refused more today -> `'o limite de envio de hoje acabou'`; `replyTo` not a message of this conversation -> `'responda uma mensagem desta conversa'`; a text and media whose sealed frame does not fit (`buildInner`) -> `'mensagem longa demais'`. An empty `text` without `media` -> `'parâmetro inválido: text'`; a malformed item or list -> `'parâmetro inválido: media'` (the dispatcher, before any handler).
- A lost ack, a closed link or a timeout -> `uncertain: true`; the node never resends by itself. When the link was open and the put was written but no ack came back, the node answers USAGE `'não deu para confirmar o envio'`: this message is the uncertain signal for `dm.send` (the error envelope does not carry the node's flag), and the app treats it exactly as `uncertain: true`. A user retry of the same uncertain send re-puts the SAME drop bytes once (same `dropId`, same stamp; the seeder answers a repeated identical drop as success, protocol section 11 "Seeder storage"), so a retry never makes a second message.

### 5.76 `dm.pull`

- Params: `{}`, nothing else. Not mutating: it reads the seeder pool and writes only the local cursor and the local (secretboxed) copies, so it is safe to repeat and must survive an uncertain answer (a periodic pull). It never sends a drop.
- Pages the global pool on the anonymous channel from the local cursor, `DM_PAGE_MAX` = 8 drops per page, at most `DM_PULL_BUDGET_BYTES` per run, tries every drop with the own box key, files every message that opens (protocol section 11 "Local semantics") and applies every own `ctl`.
- Result: `{ added: integer >= 0, cursor: integer >= 0, incomplete: boolean }`: `added` the messages filed, `cursor` the new exclusive seq cursor, `incomplete` true when the budget ended the run before the pool's end. Emits `dm.changed` (section 6) when it filed a message or applied a `ctl`.
- A failed or lost answer (`TIMEOUT`, `CLOSED`, any error) may still have filed messages and applied `ctl`s before it ended. Since the method is not mutating the client gets `uncertain: false`, which here says only that a repeat is safe, not that nothing happened: the client re-reads `dm.list` (and `dm.thread` of the open conversation) after EVERY `dm.pull` attempt, success or failure, and after a reconnect. `dm.changed` is a hint, not the only signal.
- Locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`.

### 5.77 `dm.list`

- Params: `{ folder?, limit?, before? }`, nothing else: `folder` `'inbox'` or `'request'`, default `'inbox'`; `limit` `1..50`, default 30; `before` optional, exactly `{ at: canonical ISO, peer: hex64 }`, the position of the oldest conversation the caller holds (the `next` of the previous page). Not mutating; local only.
- Result: `{ conversations: [{ peer: hex64, folder: 'inbox' | 'request', preview: string, at: ISO, unread: boolean, mine: boolean }], next: { at, peer } | null, requests: boolean, inboxUnread: boolean }`. Conversations of that folder only, newest first (by `at` descending, then `peer` ascending, protocol section 11 "Local semantics"); `next` is the `before` of the following page, `null` after the last one. `requests` is true when any request conversation is unread, whatever `folder` was asked (the app shows a dot on the Pedidos entry, never a count); `inboxUnread` is true when any inbox conversation is unread, on any page, so the tab dot never depends on which page was read.
- `preview` is the raw text of the newest kept message cut by the node to at most 140 code points on a code-point boundary, with nothing appended (the app applies `displayText` and may add its own ellipsis); a message with media and empty text previews as the fixed label `'GIF'` when every item is `image/gif`, else `'Foto'` (protocol section 11), never a key, an id or a file name; `mine` says whether that message is the own one. `unread` is a boolean, never a count. A blocked conversation is not listed; a deleted or declined one only comes back with a later message.
- Size: the worst page is 50 rows x (140 code points x 4 B + about 200 B of keys, ISO and JSON) = about 38 KB, far below `MAX_MESSAGE` (262144 B, section 2).

### 5.78 `dm.thread`

- Params: `{ peer, before?, limit? }`, nothing else: `peer` lowercase hex64; `before` optional, a message id (32 lowercase hex) to page older messages; `limit` `1..DM_THREAD_LIMIT_MAX` (46), default 30. Not mutating; local only.
- Result: `{ messages: [{ id: hex32, from: hex64, text: string, replyTo: hex32 | null, at: ISO, mine: boolean, media: [MediaItem] | null | { unavailable: true } }], next: hex32 | null, folder: 'inbox' | 'request', blocked: boolean }`, oldest first within the page; `next` is the `before` of the older page, `null` at the start of the conversation. `at` is the effective time (protocol section 11). A message id is unique only per sender: the UI keys a row by `from` and `id` together. `before` resolves to the newest kept message with that id; an id no longer kept pages from the newest message, never an empty page while messages remain. `folder` and `blocked` are this conversation's own state from the same fold as `dm.list`, so the screen never infers them from a list page; `folder` is `'request'` only when the conversation keeps a message from the peer, none of the own, and the peer is neither followed nor accepted, and a conversation with no kept message is `'inbox'` (one the person may start); while `folder` is `'request'` the UI offers Aceitar, Recusar and Bloquear instead of the composer.
- `media` is `null` for a text-only message, else the message's media items exactly as 5.75 defines them, `key` included, in the sender's order: the UI needs the key to fetch and decrypt the blob (protocol section 13). The items are peer data: the UI keeps them in memory for this screen, never writes `key` to a log, a URL or storage the node does not own, and treats a blob that does not verify as missing. On the browser node the media of a received message is opened lazily on the first `dm.thread` read and kept in a sealed local cache under the local DM key (wiped on lock, sign-out and reset; at most 256 MiB of plaintext in all, the oldest entries evicted first, a message larger than that opened but not kept). While `folder` is `'request'` nothing is fetched by `dm.thread`: a stranger's blob is downloaded only on an explicit read of that item (`media.readDm`, a tap) or once the conversation is accepted. At most 2 opens run at once, the rest wait in order; the next `dm.thread` page drops the waiting opens of the previous one, and a lock drops every waiting open; when the blob is gone from the seeder or does not verify and nothing is cached, `media` is `{ unavailable: true }` instead of the items, and the text still returns. `text` may be empty when `media` is not `null`. No event carries an item (section 6).
- Size: the worst page is 46 messages x (1000 code points x 4 B + 4 maximal media items + ids, keys, ISO and JSON) = 260,540 bytes, below `MAX_MESSAGE` (262144 B, section 2); 47 would not fit (`test/sizes.test.js`).

### 5.79 `dm.set`

- Params: `{ peer, state }`, nothing else: `peer` lowercase hex64; `state` one of `'accepted'`, `'declined'`, `'blocked'`, `'unblocked'`, `'deleted'`. Mutating.
- `accepted` moves a request to the inbox. `declined` hides the current request messages; a later message from that peer opens a new request. `blocked` drops future messages from that key after they open and makes `dm.send` to it refuse; `unblocked` returns the conversation to the folder its follow state gives, with the messages from the blocked period still hidden. `deleted` erases the conversation on this device and, through the `ctl`, on the member's other devices; the peer keeps its copy and the seeder deletes only by retention.
- Every state seals one `ctl` envelope to the OWN box only (protocol section 11 "Multi-device") and NEVER sends anything to the peer.
- Result: `{ ok: true }`. As every mutating method it is never resent by the client; an unknown outcome surfaces `uncertain: true` and the UI re-reads with `dm.list`.

### 5.80 `dm.seen`

- Params: `{ peer }`, nothing else (`peer` lowercase hex64). Not mutating: an idempotent local mark.
- Clears the `unread` mark of that conversation on this device. It is not a read receipt: nothing is sent to the peer, the seeder or the member's other devices.
- Result: `{ ok: true }`. A failed or lost answer may still have marked the conversation seen; the client re-reads `dm.list` after every attempt instead of assuming either outcome, and may repeat the call.

### 5.81 `dm.reportSign`

- Params: `{ nonce, target, reason, text?, quote, anexo? }`, nothing else: `nonce` as `report.sign` (5.20); `target` the sender's diary key (lowercase hex64); `reason` one of `'spam'`, `'assedio'`, `'ilegal'`, `'outro'`; `text` the reporter's own words, `0..280` code points (default `''`); `quote` the chosen message's plaintext, `1..MAX_TEXT` (1000) code points (`''` only when `anexo` is present); `anexo` optional, 64 lowercase hex, the sha256 of the attachment bytes. Not mutating.
- With `anexo` the node signs `varanda-dm-report-v2`: the v1 lines plus a ninth line with the digest. The image bytes never enter the RPC request: the reporter uploads them to `POST /account/report/anexo` (protocol section 11 "Reports").
- The caller never passes the member, the association, a digest or any bytes: the node fills in `member` = its own diary key and `association` = its configured association and signs exactly the UTF-8 bytes of these eight lines joined by LF (`0x0a`), no trailing LF (`dmReportPayload`, `packages/core/lib/report.js`): `varanda-dm-report-v1`, `<nonce>`, `<member>`, `<association>`, `<target>`, `<reason>`, `<digest(text)>`, `<digest(quote)>`, with `digest` as in 5.20.
- The report carries the sender's diary key as `target`, so moderators can act on the account, and only the one chosen message as `quote`. It never carries the sender's signature: the quote cannot be proven to a third party and the moderator sees it as `não conferida`.
- Result: `{ signature: hex128 }`. Opens no diary, does not preempt or start a sync, appends nothing and contacts no one. Same lock rules as `report.sign` (5.20); `target` = the own key -> `USAGE` `'não é possível denunciar a própria chave'`; a statement `report.js` refuses -> `USAGE` `'denúncia inválida'`.
- Node session: `USAGE` `'assinatura disponível só no navegador'`, as 5.20.

### 5.82 `group.seen`

- Params: `{ group, upTo? }`, nothing else. `group` is lowercase hex64. `upTo` is optional and has exactly the shape of `group.read`'s `before` (5.40), `{ at, writer, seq }`, but it is inclusive: the newest post the group screen painted. Not mutating: an idempotent local mark, like `dm.seen` (5.80).
- Records on this device `{ at, writer, seq }` of the post marked, moving only forward. Without `upTo`, the post marked is the newest readable post of the group now (hidden and own included). With `upTo`, it is the readable post with that `writer` and `seq` (hidden and own included), and the node copies its `at` from its own copy of that post, never from the caller (the caller's `at` need not match). A cut-off that matches no readable post (unknown, not held yet, author blocked or removed, or a future seq) answers `{ ok: true }` and writes nothing, so a client can never push the mark past what this node holds. A malformed `upTo` is refused by the generic parameter rule (section 5, before 5.1). The forward rule is the same in both cases: a stored mark is replaced only when the stored post is listed before the marked post in causal order or, when the stored post is no longer listed, when the marked post's group-order position (5.40) is greater. With no readable post, or a pending local root, the answer is `{ ok: true }` and nothing is written. A malformed, blocklisted or unknown root -> `NOT_FOUND` `'grupo não encontrado'`. It is not a read receipt: nothing is sent to the peer, the seeder or other devices.
- Stores: the core node file `group-seen.json` in the member data dir (documented as `data/group-seen.json`) and the browser kv `groupSeen`, shape `{ v: 1, marks: [{ group, at, writer, seq }] }`, newest last, at most 512 groups (the least recently marked is dropped first, and that group then counts as never seen), cleared with the group state on identity reset (details in protocol.md). `community.info` (5.59) reads the mark for `unread`.
- Result: `{ ok: true }`. A lost answer may already have written the mark; the client re-reads `community.info` after every attempt and may repeat the call.
### 5.83 `age.proof`

- Params: `{ verified?, since? }`, nothing else, at least one of them (neither -> `USAGE` `'parâmetro obrigatório: verified'`): `verified` a plain object, the age-verified attestation of the account service (protocol section 3 "Age attestations"); `since` `null` or a plain object, the age-since attestation. Each object serializes to at most 1024 UTF-8 bytes of JSON (else `'parâmetro inválido: verified'` / `'parâmetro inválido: since'`); the dispatcher only bounds the size, the node verifies.
- Verification: `verified` must pass `verifyAgeVerified(verified, ownKey, association, { revokedIssuers })` and an object `since` must pass `verifyAgeSince(since, association, { revokedIssuers })` (`packages/core/lib/age-proof.js`: exact shape, the issuer delegation signed by the configured association, the issuer's signature, an issuer not revoked). `revokedIssuers` is the set of the stored blocklist snapshot (empty when none is stored or it does not verify), the same set the reads apply to member certificates and username records. Unlike `username.add`, which checks a new record without it and leaves the revocation to every read, an attestation from a revoked issuer is refused here. The own key is the stored diary's key, resolved like `age.sign` (5.32). Both given objects are verified before anything is written: if either fails, nothing is stored and the answer is `USAGE` `'comprovante de idade inválido'` (the reason is never named). Monotonic: an object `since` whose `date` is earlier than the `date` of the age-since attestation already stored, when that one still verifies, is refused the same way (nothing stored, `verified` included), so a replayed older attestation never replaces a newer one. The same `date` again is accepted, and `since: null` still clears.
- Storage: the browser kv `ageVerified` and `ageSince`, each `{ v: 1, proof }` holding the object exactly as given; `since: null` clears `ageSince`. An absent field leaves its entry as it is. Both entries are deleted by `identity.reset` (5.53 and the node's reset). Nothing reaches the diary, a peer, the seeder or the network.
- Result: `{ ageVerifiedDate: string | null, ageSince: string | null, ageSinceUntil: string | null }`, the values `node.info` (5.2) answers from now on, under the same issuer binding: `ageSince` and `ageSinceUntil` are `null` unless the certificate the node has cached for block 0 is a v2 certificate of the attestation's issuer (stored anyway; the client reads `node.info` after every attempt, see section 9).
- Where it runs: browser node only (`packages/web-member/lib/session.js`). It needs an identity (no identity -> `NOT_FOUND` `'identidade não encontrada'`) but no unlock and no member certificate: nothing is signed, and the age step runs before the account link. Not mutating: an idempotent local store, like `group.seen` (5.82). A lost answer may already have stored the objects; the client re-reads `node.info` after every attempt and may repeat the call.
- Errors: the core Node session (`packages/core/lib/session.js`), and so `varanda-serve`, answers `USAGE` `'disponível só no navegador'`, as for `age.sign` (5.32); an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### Páginas (5.84 to 5.87)

A page is a diary whose key the account service holds (protocol section 12). Its owner and admins act on it through signed requests to the account service (`POST /account/pages/start`, then `page.sign`, then `POST /account/pages/<action>`); the node never appends to a page diary and never holds a page key. Every text a page result carries is peer text: the UI renders it through `displayText` (section 10).

The account service's own answers (tokens such as `em-andamento` (409), `encerrada` and `movida` (409), `termos-pendentes` and `nao-vinculado`, the 2-per-24-hours cap on closes and moves, the 8-per-minute cap on notices reads, the capped `status.engagement`, the fresh nonce of a retried signed read and `GET /account/pages/successor/<hex64>`) are in protocol section 12, "Service answers and limits". The community actions are `'community-join'` and `'community-leave'` (op `{ community }`), `'group-join'` (`{ group, community? }`), `'group-leave'` (`{ group }`), `'group-post'` (`{ group, text, replyTo? }`) and `'group-read'` (`{ group, before?, limit? }`, a signed read: `before` = `{ at, writer, seq }`, `limit` 1 to 32, default 32); `'notices'` is `{ after?, limit? }`. None of them is a node method: the node only signs them (5.84). `start` derives the page key (create) or K2 (move) from the nonce, so a resend with the same nonce gets the same key and no pending table exists. `terms` can answer `limite` (5 per 10 minutes per actor, 20 per minute per host, one in flight per actor). A signed read with a nonce minted before a service restart answers `expirado`; the client asks again with a fresh nonce. `dm-send` and the reads (`dm-list`, `dm-thread`, `notices`, `group-read`) answer `sem-permissao` when the role is lost mid-request, and notices and `dm-*` on a moved page answer `movida` (409). `close` and `move` answer `indisponivel` (and refund the lifecycle use) when a group leave failed. `GET /account/pages/successor/<hex64>` can answer `limite` (120 per minute per host). The delegate check is cached for 60 s. The spent-nonce table evicts its oldest rows at its cap (protocol section 12). A `page-link` is appended only on create and move, never on accept.

### 5.84 `page.sign`

- Params: `{ action, nonce, page, op }`, all required, nothing else: `action` one of the page statement actions `'create'`, `'list'`, `'status'`, `'post'`, `'reply'`, `'quote'`, `'delete'`, `'like'`, `'repost'`, `'profile'`, `'avatar'`, `'rename'`, `'invite'`, `'dm-list'`, `'dm-thread'`, `'dm-send'`, `'dm-set'`, `'dm-seen'`, `'follow'`, `'follows'`, `'media'`, `'notices'`, `'terms'`, `'community-join'`, `'community-leave'`, `'group-join'`, `'group-leave'`, `'group-post'`, `'group-read'` (`ACTIONS` of `packages/core/lib/page-proof.js`; it has no unsigned `'offer-cancel'` action: the account service answers that route `pedido-invalido` and the owner cancels with the signed `'offer'` cancel below) or one of the record actions `'accept'`, `'remove'`, `'offer'`, `'transfer-accept'`, `'close'`, `'move'` (`'create'` is both); `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce); `page` the page key (lowercase hex64), or `''` for `'list'` and `'terms'` only (`''` for another action, `'create'` included, -> `USAGE` `'parâmetro inválido: page'`); `op` a plain object whose canonical JSON (`canonicalOp`, `page-proof.js`: keys sorted at every depth, no whitespace) is at most 16 KiB of UTF-8, at most 8 levels deep, made of own enumerable data keys, plain objects, dense arrays, strings without a lone surrogate, finite numbers (not `-0`), booleans and `null`; an object key that is a canonical array index (`/^(0|[1-9][0-9]*)$/`, such as `"0"` or `"10"`, which `JSON.stringify` would emit out of sorted order) or a key named `secretKey`, `pin`, `seed` or `association` at any depth is refused (`'parâmetro inválido: op'`): the association is never the caller's, the node fills it from its own configured association. Not mutating. The exact `op` of each action is checked by the node, after the params pass, except that an `'offer'` op with a `to` and an `exp` must carry both `null` or a lowercase hex64 `to` with a canonical ISO `exp` (one `null` -> `USAGE` `'parâmetro inválido: op'`).
- Record actions: `op` carries the record's own fields (protocol section 12) without `type`, `page`, `actor`, `association` and `signature`, which the node fills in (`association` from its own configuration, only into the records that carry it: `page-roster`, `page-origin`, `page-close` and `page-moved`, nested rosters included; `page-accept` and `page-offer` have no `association` field):
  - `'accept'` (the invitee): `{ gen, rosterSignature, at, nonce }`, signed into a `page-accept`.
  - `'remove'` and `'transfer-accept'` (the owner, or the offer's recipient): the resulting roster `{ gen, owner, admins, prev, at, nonce }`, signed into a `page-roster`.
  - `'offer'` (the owner): `{ to, exp, gen, at, nonce }`, signed into a `page-offer`. `{ to: null, exp: null, gen, at, nonce }` is the cancel, signed the same way (`null` fields written as `null` in the payload): the account service appends it on the page diary, which ends the offer for `pendingOffer` and the full-mode chain, and then clears the offer from its ACL. `to` and `exp` are both `null` or neither.
  - `'close'` (the owner): `{ gen, at, nonce }`, signed into a `page-close`.
  - `'move'` (the owner): `{ to, gen, fromSeq, owner, admins, at, nonce }`, `to` the new key K2 the service returned from start; signed into three records: a `page-moved` for this page (K1), and for K2 a `page-origin` (`from` = K1) and the genesis `page-roster` (`gen` 1, `prev` null, `owner` and `admins` from `op`, the same `at` and `nonce`).
  - `'invite'` (the owner, a statement that also yields a record): `{ member, gen, rosterSignature, roster }`, `roster` = `{ owner, admins, prev, at, nonce }` of the resulting roster and `rosterSignature` `''` (any value the caller sends is replaced). The node builds that roster (`gen` from `op`, its association), signs it, replaces `op.rosterSignature` with that signature, and then signs the statement over this completed op: `opHash` hashes `canonicalOp` of the op with the node's `rosterSignature`, so the client sends exactly `{ ...op, rosterSignature: record.signature }` to `POST /account/pages/invite`.
  - `'create'` (a statement that also yields a record): `{ username, name, bio, roster }`, `roster` = `{ gen: 1, admins: [], prev: null, at, nonce }`, and `page` is the key the service returned from start. The node signs the genesis roster and the statement over `op` as sent.
- The caller never passes the member, the actor, the association, the operation hash or any bytes. For a statement the node fills in `member` = its own key (5.87 on the core node), `association` = its configured association and `opHash` = the lowercase hex64 BLAKE2b-256 hash of the UTF-8 bytes of `canonicalOp(op)`, and signs exactly the UTF-8 bytes of these seven lines joined by LF (`0x0a`), no trailing LF (`pagePayload`, `packages/core/lib/page-proof.js`):

  ```
  varanda-page-v1
  <action>
  <nonce>
  <member hex64>
  <page hex64, or empty>
  <association hex64>
  <opHash>
  ```

  A record is signed over its own payload (`varanda-page-roster-v1`, `varanda-page-accept-v1`, `varanda-page-offer-v1`, `varanda-page-close-v1`, `varanda-page-moved-v1`, `varanda-page-origin-v1`, protocol section 12). The delegation trio (`issuer`, `issuerDate`, `issuerSignature`) and the issuer's `countersignature` are added by the account service, never by the node.

  ```json
  { "v": 1, "id": 11, "method": "page.sign", "params": { "action": "post", "nonce": "<base64url>", "page": "<hex64>", "op": { "text": "Abrimos às 7h" } } }
  { "v": 1, "id": 11, "ok": true, "result": { "signature": "<hex128>" } }
  ```

- Result: `{ signature: hex128 }` for a statement action; `{ record }` for `'accept'`, `'remove'`, `'offer'`, `'transfer-accept'` and `'close'`, the record with `signature` filled; `'create'` and `'invite'` answer `{ signature, record }`, `signature` the `varanda-page-v1` statement signature over the op the node hashed (above) and `record` the genesis roster (`'create'`) or the resulting roster with its `signature` (`'invite'`); `'move'` answers `{ record, origin, roster }` (`page-moved` for K1, `page-origin` and the genesis `page-roster` for K2), all three signed by the owner, and its HTTP request is authenticated by those record signatures, with no statement. On the core node `'terms'` (op `{ version, diary }`, exactly these keys: the Terms version and the own diary key) answers `{ signature, termsSignature }`, `termsSignature` a lowercase hex128 `varanda-terms-v1` signature (`signTerms`, `packages/core/lib/terms.js`) over `{ nonce, member: <delegate>, association, version: op.version }` with the same nonce, which the account service checks with `verifyTerms` before it records the delegate's acceptance; a delegate with no link row is refused `'nao-vinculado'`, one whose row holds older Terms `'termos-pendentes'`, and a Google-linked member is refused `terms` and can never register a delegate for its own linked diary (protocol section 12); no other action carries `termsSignature`, and the browser node never answers it (a hosted member accepts the Terms through `/account/terms`, 5.29). Never a key, the payload or the operation hash.
- Where it runs: the browser node (`packages/web-member/lib/session.js`), or a core node with a registered delegate (5.87), which signs with the delegate and fills `member` and `actor` with the delegate's public key. Opens no diary, appends nothing and contacts no one. The HTTP call that runs the operation is separate and is never retried by the client; a lost answer is `'incerto'` and a human retry resends the stored signed bytes, never re-signs.
- Errors: the core node without a delegate -> `USAGE` `'chave de página não registrada'` (nothing opened); no identity on the browser node -> `NOT_FOUND` `'identidade não encontrada'`; locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; a pair for another diary -> `USAGE` `'passkey não corresponde ao diário guardado'`; an `op` the node refuses for that action -> `USAGE` `'operação de página inválida'`; an older node -> `USAGE` `'método desconhecido'`.

### 5.85 `page.read`

- Params: `{ key, full? }`, nothing else: `key` the page diary key (lowercase hex64); `full` a boolean, default `false`. Not mutating.
- Reads the page's roster and lifecycle (`pageState`, `packages/core/lib/page.js`, and `page-lifecycle.js`): bounded by default (the highest-`gen` verifying roster within the newest windows), or the whole chain with `full: true` on the browser node. The core node ignores `full` (it reads the whole chain when it holds every block). Errors: a diary with no local data, a blocked or revoked one, or a forked replica -> `NOT_FOUND` `'sem dados locais para este diário'`.
- Result: `{ page: hex64, owner: hex64 | null, admins: [hex64], gen: integer | null, seq: integer | null, isOwner: boolean, isAdmin: boolean, complete: boolean, follows: [{ key: hex64, seq: integer }], followsCount: integer, followsTruncated: boolean, closed: boolean, movedTo: null | { to: hex64, seq: integer }, movedFrom: null | { from: hex64, fromSeq: integer }, links: [{ actor: hex64, diary: hex64, seq: integer }] }`. `gen` and `seq` are those of the roster in force and `seq` its block; `isOwner` and `isAdmin` compare with the caller's own key (or its delegate, 5.87); `complete` is false when the read could not cover every block it needed; `follows` are at most the newest 64 follows the page diary holds (`PAGE_READ_FOLLOWS_MAX`, newest first by the seq of the winning follow record), `followsCount` how many it holds in all (up to 4095) and `followsTruncated` true when `follows` left some out; the whole list is the signed `'follows'` read of the account service. `links` are the verified `page-link` records (a core member's delegate, its diary and the record's `seq`), newest `seq` first, at most one per roster member in force (`PAGE_READ_LINKS_MAX`, 17). With these bounds the worst case fits `MAX_MESSAGE`, where 4095 bare keys (about 274 KB) would not (`packages/rpc/test/methods.test.js`).

### 5.86 `page.feed`

- Params: `{ page, keys, limit? }`, nothing else: `page` the page key (lowercase hex64); `keys` 1..64 distinct lowercase hex64 keys (the page's newest follows); `limit` `1..FEED_LIMIT_MAX` (31), default `FEED_LIMIT_DEFAULT` (30), the same bound as `feed.read` because the rows are the same and a larger page would not fit `MAX_MESSAGE`. There is no cursor. Not mutating.
- A short-lived peek of those diaries over the seeder (block 0 gate with the blocklist and revoked issuers, the newest windows of each diary), folded like `feed.read` (5.13) with deletes and the moved cut applied. Nothing is appended to the caller's diary or the page's.
- Result: `{ items: [FeedItem], incomplete: boolean }`, `items` as in `feed.read`; `incomplete` true when a diary was not served or the budget cut the read, or when the seeder points at a page's close or move (`/index/page-end`, docs/protocol.md section 12) whose block did not arrive in time or did not verify as a close or move at or below that seq: that diary then gives no row above its head blocks. A pointer that verifies cuts the diary there, wherever it is; no pointer changes nothing. `page` is validated but not used by the browser node (the rows come from `keys` alone).
- Errors: a second `page.feed` in flight -> `USAGE` `'feed de página já em andamento'`; no verified seeder -> `USAGE` `'sem conexão com o semeador'`; a seeder at capacity -> `USAGE` `'Semeador ocupado; tente novamente em instantes.'`.
- Where it runs: browser node only. The core node answers `USAGE` `'feed de página disponível só no navegador'`, before anything is opened.

### 5.87 `page.register`

- Params: `{}`, nothing else. Mutating.
- Core node only (`packages/core/lib/session.js`): a core diary key is not an Ed25519 member key, so the node generates an Ed25519 delegate pair, stores it in `<dataDir>/private/page-actor.json` (mode 0600) and appends `page-delegate` `{ type, actor, at }` to its own diary. A later call, including a repeat after a partial write (key file saved, `page-delegate` not appended), never just returns the stored key: the node checks that its diary's newest `page-delegate` (deletes never affect `page-*` records) names the stored actor, appends one when it is missing or names another key, and only then answers. When the check passes it appends nothing.
- Result: `{ actor: hex64 }`, the delegate's public key; never the secret key.
- Errors on the core node: no identity yet -> `NOT_FOUND` `'identidade não encontrada'`; the member certificate not written yet -> `GENESIS_REQUIRED` (message `'grave o certificado de membro antes de publicar'`, no key file written); a malformed or symlinked `page-actor.json` -> `USAGE` `'chave de página inválida'`.
- The browser node answers `USAGE` `'registro de página disponível só no nó core'`. As every mutating method it is never resent by the client; an unknown outcome surfaces `uncertain: true` and a repeat is safe (it completes a missing `page-delegate` and returns the stored key).

### 5.88 `dm.putMedia` (IPC only)

- Params: `{ name: string, mime: string, width: integer, height: integer, kind?: 'voice', ms?: integer }`, `name`, `mime`, `width` and `height` required, nothing else. Mutating. The same rules as `media.uploadFile` (5.56) without `sealed`: `name` matches exactly `/^[0-9a-f]{32}\.bin$/`, the cache file the host wrote. Images use `mime` in `MEDIA_MIMES`, integer `width` and `height` 1..16384, and neither `kind` nor `ms`. Voice requires `kind: 'voice'`, `mime: 'audio/mp4'`, `width: 0`, `height: 0` and integer `ms` 1..120000. The node checks voice bytes with `audioBounds` and enforces the 1572864-byte plaintext cap. No `bytes` field, no base64 chunk method and no recipient: the bytes never travel inside a request (`MAX_REQUEST`, 64 KiB, against a photo of up to 8 MiB).
- Encrypts the file under a fresh blob key and nonce, puts its chunks on the anonymous blob channel (protocol section 13) and answers with the media item a later `dm.send` (5.75) carries: `{ id, key, nonce, chunks, bytes, sha256, mime, w, h, ms }`, with `w` and `h` the given `width` and `height` and `ms` `0` for images or the voice duration for audio. The file is opened, checked and deleted as in 5.56 (cache directory join, `lstat` and `fstat`, deleted after a successful put). Neither the name, the key nor anything about the bytes appears in an error message or a log; the item appears only in this result.
- IPC only, offered only by the in-app web-node worklet, as 5.56; elsewhere it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6).
- Web and PWA: the page's RPC client caps every request at `MAX_REQUEST` (`lib/client.js`), so the bytes cannot go over RPC there. The page hands them to the browser node's media facade (`media.putDm`, `packages/web-member`), a direct call on the node handle in the same page, not an RPC method, which applies the same rules and returns the same media item. The page reads the plaintext of a message's item back through the same facade, `media.readDm({ from, id, index })` -> `{ bytes, mime }` (from the sealed cache, or fetched, verified and cached on first read), never through an RPC response.
- A lost answer is `uncertain: true` and is never resent: the UI prepares the media again and calls again; a blob put but never sent expires with the channel's retention (protocol section 13).

### 5.89 `media.readFile` (IPC only)

- Params: a DM item `{ kind: 'dm', from: hex64, id: string, index: integer }` (`id` the message id, 32 lowercase hex; `index` `0..3`, the item's place in the message's `media`), or a private group item `{ kind: 'group', diary: hex64, item: object }` (`diary` the writer's diary key, `item` exactly the private item of 5.56 / `group.read`, every field checked as for `group.post`). Every field of the chosen kind required, none of the other kind, nothing else. Not mutating: it writes no diary, only a temporary file the node owns. A public group item is never read here: it is fetched like a diary photo.
- The node opens the item as the browser handle's `media.readDm` (5.88) or `media.readGroup` does (the DM sealed cache or blob channel; the private group ciphertext from the node's own seeder only, opened under the item's key), writes the plaintext to a fresh file in `<dataDir>/media-read` (created exclusively, mode `0600`, a regular file, the same name rule as 5.56: `/^[0-9a-f]{32}\.bin$/`, random) and answers `{ name, mime, w, h }`: `mime` the image type, `w` and `h` the dimensions (read from the image when the item has none, `null` when unreadable). The plaintext copy in memory is zeroed once written.
- Why a file and not the bytes: one response is capped at `MAX_MESSAGE` and the IPC frame decoder refuses anything larger, while a photo may be 8 MiB. So the answer goes the other way through a file, as 5.56 does for requests: only the name crosses the IPC, the host joins it to the read directory it knows (`<documents>/varanda/media-read`) and resolves no path the node chose; the name rule leaves no separator, dot segment or other directory to name, and the host refuses any other answer.
- Lifetime: the host deletes a read file when its image cache evicts it, on lock, on sign-out, on reset and when the app goes to the background (every read file and cached image is dropped; images are read again on return), and deletes every file in the read directory that matches the name rule when its handle is created, before any read, so a file left by a crash or force-quit is gone even if the worklet's start sweep fails. The worklet empties the read directory at start (once its data-dir lock is held), on every `identity.clear`, `identity.forget` and `identity.reset`, and at close; an image opened while one of those ran is deleted and the call answers `LOCKED` `'sessão encerrada'`. A read refused by the node (`USAGE` `'mídia indisponível'` and the like) writes nothing.
- IPC only, offered only by the in-app web-node worklet, as 5.56; elsewhere it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6). Web and PWA: the page reads through the facade (`media.readDm`, `media.readGroup`), never an RPC response. Neither the name, the key nor anything about the bytes appears in an error message or a log.

### Recuperação (5.90 to 5.94)

A member keeps the ORIGINAL root (the PRF output of the first passkey, from which every member key derives) reachable through recovery entries held by the account service: a second passkey, or a recovery code. Each entry is a blob, the root sealed under a wrap key, stored under a lookup id; both come from the wrapping secret (`docs/protocol.md`, `packages/web-member/lib/recovery.js`). A wrapping passkey's PRF derives only `lookupId` and the wrap key, never a member key. `recovery.sign` lets the account service know the request comes from the member; the four `identity.recovery*` controls are the in-app worklet's side of the wrap and unwrap (on the web the page calls the browser node's handle instead, section 11).

A recovery blob, wherever it appears below, is `{ v: 1, kind, nonce, ciphertext }`, exact keys: `v` the integer `1`; `kind` one of `'passkey'`, `'code'`; `nonce` 48 lowercase hex characters (24 bytes); `ciphertext` 164 lowercase hex characters (82 bytes: the 66-byte plaintext and its 16-byte MAC). Any other shape -> `USAGE` `'parâmetro inválido: blob'`.

### 5.90 `recovery.sign`

- Params: `{ action, nonce, kind?, lookupId?, blob? }`, nothing else: `action` one of `'put'`, `'remove'`, `'list'`; `nonce` matches `/^[A-Za-z0-9_-]{43,128}$/` (the account service's base64url nonce); `kind` one of `'passkey'`, `'code'`; `lookupId` lowercase hex64; `blob` a recovery blob (above). `put` requires `kind`, `lookupId` and `blob`, with `blob.kind` equal to `kind` (`USAGE` `'parâmetro inválido: blob'` otherwise); `remove` requires `kind` and `lookupId` and refuses `blob` (`'blob só com put'`); `list` refuses all three (`'list sem kind, lookupId nem blob'`). A missing one -> `USAGE` `'parâmetro obrigatório: <name>'`.
- The caller never passes the member, the association or a hash: the node fills in `member` = its own diary key and `association` = its configured association, computes `blobHash` itself from the blob (`blobHashOf`, BLAKE2b-256, `packages/core/lib/recovery-proof.js`; `''` for `remove` and `list`, as `kind` and `lookupId` are `''` for `list`), and signs the `varanda-recovery-v1` statement (`recoveryPayload`, same file; `docs/protocol.md`), whose prefix separates it from every other signature of the protocol.
- Result: `{ signature: hex128 }`, the Ed25519 signature by the identity key; never the payload, the blob or a key. The account service checks it with `verifyRecovery(fields, signature)` using `member` as the public key, and stores, removes or lists the member's entries (a Google-linked member only; at most 4 passkey entries and 1 code entry).
- Where it runs: browser node only (`packages/web-member/lib/session.js`), like `terms.sign`: not a diary write, no append, no network. Not mutating.
- Errors: the node session answers `USAGE` `'assinatura disponível só no navegador'`; the identity locked -> `USAGE` `'identidade bloqueada: entre com a passkey'`; an older node -> `USAGE` `'método desconhecido'` (as 5.21).

### 5.91 `identity.recoveryLookup` (IPC only)

- Params: `{ kind, secret?, code? }`, nothing else: `kind` one of `'passkey'`, `'code'`; `secret` (kind `'passkey'` only, and required there) the wrapping passkey's 32-byte PRF output in lowercase hex; `code` (kind `'code'` only, and required there) the recovery code as typed, 1..64 characters. Both `secret` and `code`, or neither, -> `USAGE`. Not mutating: it changes no stored state, and each call replaces the pending wrap key of the previous one.
- Result: `{ lookupId: hex64 }`, the id under which the account service keeps that entry. The worklet decodes the code (it normalises case, spaces, hyphens and look-alike letters and refuses a bad checksum: `USAGE` `'código de recuperação inválido'`), derives the lookup id and zero-fills every copy of the secret; neither the secret nor the code appears in the result, an error or a log.
- IPC only, offered only by the in-app web-node worklet, as 5.50; elsewhere it reaches no handler and the dispatcher answers `INTERNAL` `'erro interno'` (section 8, step 6).

### 5.92 `identity.recoveryOpen` (IPC only)

- Params: `{ blob, member: hex64 }`, both required, nothing else: `blob` a recovery blob (above) fetched from the account service; `member` the diary key the host expects. Not mutating (it changes no stored state), but not repeatable: it CONSUMES the pending wrap key.
- Opens the blob with the wrap key derived by the latest `identity.recoveryLookup` of the same kind, within 120 seconds of it (held in the worklet's memory only, zero-filled after this call, whatever its outcome, or a lock) and checks that the plaintext names `member`. Result: `{ prf: hex64 }`, the ORIGINAL root, exactly as `identity.install`'s `prf` input (5.50), for kind `'passkey'` and kind `'code'` alike: the host then calls `identity.install` and seals the keychain session as today (kind `'passkey'`), or holds the root while the person creates a new passkey (kind `'code'`, section 11). A blob that does not open, or names another member -> `USAGE` `'entrada de recuperação inválida'`, with no detail. A repeated call, or one with no pending wrap key or after it expired, fails with the same error: after a lost response the host never repeats it, it restarts the flow with a new ceremony (or the code typed again) and a new `identity.recoveryLookup`.
- IPC only, as 5.91.

### 5.93 `identity.recoveryWrap` (IPC only)

- Params: `{ kind, secret? }`, nothing else: `kind` one of `'passkey'`, `'code'`; `secret` required for kind `'passkey'` (the new passkey's PRF output, lowercase hex64) and refused for kind `'code'`. Not mutating.
- Requires an unlocked worklet holding the root (`USAGE` `'identidade bloqueada: entre com a passkey'` otherwise). Seals the root and the member key under a fresh nonce and answers `{ lookupId, blob }` for kind `'passkey'`, or `{ lookupId, blob, code }` for kind `'code'`, where `code` is a fresh recovery code (36 Crockford base32 symbols in 9 groups of 4, a 160-bit secret and a 20-bit checksum) that the app shows once. The app then registers `lookupId` and `blob` with the account service (`recovery.sign` `put`). At the end of a code recovery the host calls it right after `identity.install`; if it fails (or a cancel, lock or sign-out lands in between) the host rolls back: `identity.clear`, the keychain session it just saved deleted, the new passkey refused as `INSTALL_FAILED`, and the person enters the code again (`RECOVERY_BAD`).
- IPC only, as 5.91.

### 5.94 `identity.recoveryBind` (IPC only)

- Params: `{ credentialId, userId }`, both required, nothing else, with the rules of 5.50 (`credentialId` 1..1024 printable ASCII characters without space), except `userId`: a wrap-marked user id, lowercase hex64 whose last 16 bytes are the mark `'varanda-wrap-v1\n'` (`docs/protocol.md`), never `''`; the validator requires a non-empty hex64 and the worklet refuses one without the mark (`USAGE` `'passkey de recuperação inválida'`). Mutating (in `MUTATING`): it rewrites the kv passkey record, so a failed call is an unknown outcome the host never retries by itself.
- Requires an unlocked worklet holding the root. Rebinds the worklet's stored passkey record to the new credential (after 'Trocar a passkey' or a recovery with a code), so the next sign-in asks for that passkey. Result: `{}`.
- IPC only, as 5.91.

### Errors common to every method

- The data dir held by another process, or the node session in its error state -> `LOCKED` (message `'diretório de dados em uso'` for the lock). A request reaching a closed node session -> `LOCKED` `'sessão encerrada'`.
- A method that needs an identity before one exists -> `NOT_FOUND` `'identidade não encontrada'`.
- Anything else unexpected -> `INTERNAL` `'erro interno'`.

## 6. Events

| Event | `data` (exact keys) |
| --- | --- |
| `sync.started` | `{ runId, once: boolean }` |
| `sync.event` | `{ runId, line: string <= MAX_LINE chars }` |
| `sync.stopped` | `{ runId, reason: 'done' \| 'stopped' \| 'preempted' \| 'timeout' \| 'error' \| 'idle', result?: SyncResult }` |
| `warning` | `{ line: string <= MAX_LINE chars }` |
| `follows.changed` | `{ count: integer >= 0 }` |
| `groups.changed` | `{ group: hex64 }` |
| `dm.changed` | `{ added: integer >= 0 }` |
| `dm.sending` | `{}` |

- `follows.changed` (browser node only): the follow set changed from the own diary, normally another device's `follow` records folded in by the sync; `count` is the new number of follows. The UI reloads A Rua and the follow count. The browser node also restarts its continuous run once per distinct folded diary length (coalesced), so the run follows the new set; a once run is never restarted. The core node never sends it.
- `groups.changed`: the folded state of that group changed (new posts, members, requests or metadata), from a local write or from the sync. `group` is the group root key and nothing else is carried; the UI re-reads with `group.read`, `group.info` or `group.members`. The same event is reused for communities, with the same shape: `group` is then the community root key C and the UI re-reads with `community.info`; there is no separate community event. Every community mutation emits it with `group` = C, plus for each affected group: `group.create` emits G and C; `community.join` emits C and Geral (when written); `community.leave`, `community.admit`, `community.ban` and `community.admin` emit C and every group of C in the caller's local list; `community.meta` emits C only. Sync growth of a C core emits it for C and for every local group whose header names C. The browser node's automatic enrolment (5.63) emits it for every root it joined (a community, its Geral and each group), and its automatic key re-share (5.61) for each group it handed keys in.
- `dm.changed` (browser node only): a `dm.pull` (5.76) filed new messages or applied a `ctl` from another own device. `added` is the number of messages filed (0 when it only applied a `ctl`); no peer, id or text is carried. The UI re-reads with `dm.list` and, for an open conversation, `dm.thread`. The core node never sends it.
- `dm.sending` (browser node only): this device is about to put a drop of its own (a message makes two, a folder op one). It is emitted before the put, because the seeder can fire the DM wake before the put is acknowledged; the app uses it to tell its service worker to hide the wake its own drop causes. It carries nothing. The core node never sends it.

- `sync.started`: emitted every time a run starts, whether from `sync.start` or from the node restarting a continuous run after a preemption (section 6.1); `once` is the run's mode. With `sync.stopped` it lets the UI track the sync state from events alone: a run is active between its `sync.started` and its `sync.stopped`.

- `sync.event` `line` = the human stdout line the CLI prints for that `runSync` event (protocol §7 `sync`: `sync ready`, `peer member <peerKey8>`, `peer seeder <peerKey8>` / `... não verificado`, `admitted <key> <length>`, `rejected <key> <reason>`, `withdrawn <key> <peerKey8> <reason>`, `have <key> <length>`, `downloaded <key> <length>`), built with `safe()` exactly as `apps/cli/lib/commands/sync.js` `formatEvent` does. An event with no stdout line is not sent.
- `newest <key> <length>` (browser node only): the newest window of a followed diary is stored (every block of it stored or deleted, protocol §6 "Browser node download order") ahead of its history, so `feed.read` may now show its newest posts although no `downloaded` line came (the present length did not move). `key` is the diary key (64 lowercase hex), `length` the signed length the window ends at; escaped with `safe()` like the other lines. At most once per key and length in a run, and only for a diary that passed the local gate. It is a hint for the reader only: every advertised or measured length (`have`, `downloaded`, the run's goals and `settled`) stays the present length. The core node never sends it.
- `warning` `line` = a line the CLI prints on stderr, escaped with `safe()`: the `runSync` `log` lines (`aviso: ...`; a line that contains `/`, `\` or a run of 16+ hex digits, i.e. a raw error message that may carry a path or key material, keeps its prefix up to the first `': '` after `aviso: ` and ends with `': erro interno'`, and the full line goes only to the host's `onInternalError`), `aviso: diário <key8> ignorado (<reason>)` for a `skipped` event, and, before a `sync.stopped` with reason `'error'`, `'erro: ' + message` (a message that passes the section 7 safety rule, else `'erro: erro interno'`).
- `sync.stopped`: emitted once per run when it ends. Reasons: `'stopped'` = ended by `sync.stop`, by the connection closing or by the node session closing; `'preempted'` = the node paused the run to serve a request (or because the app went to the background, section 6.1); `'timeout'` = a `once` run ended at its deadline (`result.ok === false` with `errors[0]` = `'sem pares'` or starting with `'tempo esgotado'`); `'done'` = any other resolved run; `'error'` = `runSync` threw (no `result`); `'idle'` = (only when a host turns the lease on, 6.1; the shipped browser entry does not) the browser node ended a continuous run because its verified seeder link was settled for the lease hold (section 6.1): not a failure, no `result`, and the node keeps the continuous intent (it does not redial by itself; 6.1 says what does). Only the lease produces `'idle'`: a `sync.stop` (or a connection or session close) that lands while an idle run is still unwinding clears the intent, and that run's reason is `'stopped'`. The core node, `varanda-serve` and `once` runs never emit `'idle'`. `result` is present only for a resolved `once` run (whatever the reason, `'stopped'` and `'preempted'` included), and is the SyncResult passed through `capSyncResult` (below).
- The events of a run belong to the connection it started in. When that connection closes, the run's remaining events (`warning`, `sync.event`, the `sync.stopped` with reason `'stopped'`) are not delivered, not even to a connection that opens while the run is still stopping. A socket that replaces another one (`varanda-serve`, close code 4000) is not a close: the run goes on and its events reach the new socket.
- Lines and reasons are human text the node already escaped with `safe()` (A8). The UI still renders every line as text only (never markup) and through `displayText` (section 10).
- A run's events may reach the client before the `sync.start` response; the UI keys them by `runId`.

### 6.1 Preemption (the node session, `packages/core/lib/session.js`)

Every member operation opens the store and takes the data-dir lock, and a running sync holds that lock (protocol §9). The node therefore serves requests strictly one at a time, and before any request that opens the store (every member method, and `node.info` / `sync.start` while the own identity is not yet known to the session) it aborts the running sync and awaits it (`sync.stopped` with reason `'preempted'`). After the request, a continuous run (`once: false`) that the user did not stop is restarted with a new `runId` (`sync.started`, sent before that response); when several requests are queued the run is preempted once and restarted after the last of them. A `node.info` that preempted the run reports the restarted run in its `sync` field. A preempted `once` run is over: it is not restarted. `sync.status`, `sync.stop` and a `node.info` served from the session's cache never preempt. While the app is in the background (the host suspends the session) the run is paused the same way and restarted on resume; requests sent meanwhile wait.

The browser node's session (`packages/web-member/lib/session.js`) follows the same rules (one request at a time, the same preemption and restart, the same events), because two Hypercore instances on the same browser storage would corrupt it, with these exceptions. `feed.read` (5.13), `log.read` (5.12), `profile.read` (5.21), `engagement.read` (5.26), the group and community reads (`group.read` 5.40, `group.list` 5.41, `group.info` 5.42, `group.members` 5.43, `group.requests` 5.44, `community.info` 5.59, `community.list` 5.62, `community.members` 5.65, `community.requests` 5.66, `group.seen` 5.82, which writes only its local mark), the own-diary read of `notices.list` (5.28) and the plan of the automatic enrolment (5.63) stay serial requests but, while a run exists, read the cores that run already holds instead of stopping it: no `sync.stopped` `'preempted'`, the same `runId`, and the run's teardown waits for a read in progress before it closes any core; with no run they open and close the storage as before. The run lends the own diary, its followed replicas and the replicas of the diaries that bind its group cores, its own group cores, and the foreign group cores whose blocks stay stored when it ends (synced, failed but kept, or rechecked after being stored before the run). A read the run cannot serve (a stored replica or group core the run does not hold, such as an unfollowed diary or a core still in its gate, or a core the run closed or forked under the read) falls back to that exclusive path and preempts once; so an enrolment plan with nothing to do no longer stops the run, and only its writes do. While the run is still starting (it publishes its cores just before its first connection), such a read waits at most 3 s (`createBrowserSession` option `readerWaitMs`) for them; after that it takes the exclusive path too and preempts the starting run once (the warning `aviso: leitura sem esperar a partida da sincronização (<ms> ms)`, then the usual restart), so a slow or stuck startup never holds the reads, or the requests queued behind them, without a limit. Writes (and the follow drain, a media upload and a fold restart) still preempt. The other exceptions are `follow.list`, 5.11, which stays on the chain but reads only the kv area, `peek.read`, 5.22, which opens no storage core and serializes only its own-key lookup while the key is not cached or an identity change is pending, `diary.peek`, 5.27, which runs beside the chain inside the running sync, and `notices.list`, 5.28, which, like `peek.read`, opens no storage core of other diaries but, on a read over channel v2, reads the own diary once inside the serial step (`ownNoticeContext`); none of them preempts the run, and a `peek.read` or `notices.list` with the own key cached runs no serial step for its lookup, so unlike a serial request it does not restart a wanted continuous run after the lease gap. It has no suspend and resume. Its run (`packages/web-member/lib/sync.js`) has one peer, the seeder at the configured address, re-dialled with a backoff (1 s doubling to 30 s) while the run lasts. Its `sync.event` lines are the ones above except `withdrawn`, and its `peer` line always names the endpoint at the configured address (anything but a verified seeder is then dropped); its own `warning` lines are `aviso: sem conexão com o semeador; nova tentativa em <n> s`, `aviso: o endereço configurado não respondeu como um semeador verificado (<key8>)`, `aviso: partida demorada (etapa: <step>, <s> s)` (a run that has not reached its first connection to the seeder 5 s after it started, repeated every 5 s until then or until the run ends; `<step>` is the startup step it is on, local diagnostics only) and the session's `aviso: leitura sem esperar a partida da sincronização (<ms> ms)` above. In its SyncResult, `peers` and `seeders` are 0 or 1 (the verified seeder link), and an endpoint that fails the seeder check adds `semeador não verificado` to `errorsSoft`. The seeder address never appears in an event, a result or an error.

The lease (browser node only, `createBrowserSession` options `leaseHoldMs`, 0 = off, and `leaseGapMs`). The shipped browser entry (`packages/web-member/web/node.js`) passes `leaseHoldMs: 0`, so the lease is off: a visible hosted page keeps its seeder link (each visible page holds one external seeder slot; a dropped link redials, 1 s doubling to 30 s) and a hidden tab stops the sync through the app (`sync.stop`). The rest of this paragraph describes the lease when a host turns it on, kept as an escape hatch for seeder capacity: a verified seeder link that has nothing left to do is not held open. A user's continuous run whose link is settled (the seeder's inventory complete and not by its timeout, no unmet goal, no failing follow, and every own media core with blocks confirmed pushed at its length or `leaseMediaMaxMs`, 120 s, elapsed waiting for one) for the hold ends cleanly: `sync.stopped` `{ runId, reason: 'idle' }` without `result`, the continuous intent kept. The hold is counted across the preempted ends caused by writes and fold restarts (a run that ends `'preempted'` hands its settled time to the run that restarts and settles again; an unsettled link, or any other end, resets it); a read served on the run's cores neither ends nor extends the run, so a read per second does not keep the link up. The hold waits while a reader borrows the live link (the session's `borrow(fn)` counter; its only borrower is a `diary.peek`, 5.27, from its wait to its answer), never past 30 s from the first borrow. `peek.read` (5.22) is not a borrower: it never uses the sync link and does not touch the lease. A `diary.peek` still waiting for a link when a run ends (the lease ended it under its wait, or a request preempted it) gets the restart check again once the run is cleared, the gap cleared with it, so it never waits for a request that may not come. During the gap the member reads (`feed.read`, `profile.read`, `log.read`, `engagement.read`, `follow.list`, `node.info`, `sync.status`) do not restart the run; `sync.status` reports `{ state: 'idle' }`. What dials again, inside the gap or after it: a diary write (5.5 to 5.8, 5.19, 5.23 to 5.25, the follow drain and a media upload's declaration) restarts the continuous run after it, as after a preemption; a `diary.peek` (5.27) with no verified run restarts it; and `sync.start` while no run exists starts at once (a `sync.start` while a run exists is still `USAGE` `'sincronização já em andamento'`). After the gap, the next request that would restart a preempted run restarts this one. `sync.stop` clears the intent as always, also over an idle run still unwinding (its reason is then `'stopped'` and the gap no longer applies). After a link drop the next link confirms every own media core again from what that seeder advertises. Two sync sockets are never open at once (a `peek.read` page's own short link, 5.22, is apart from them): a run returns only after its last socket closed (at most 1 s after it asked), also when that socket's link already closed and the run was waiting to reconnect, and a new run starts only then.

### Capped SyncResult (`capSyncResult(result)`)

The SyncResult of protocol §6 reshaped so that a `sync.stopped` event always fits `MAX_MESSAGE` (pure; the input is not mutated):

```
{ ok, peers, seeders, admitted, rejected: null | reason, seederConfirmed,
  downloaded: { hex64: presentLength }, downloadedTruncated,
  unadvertised: [hex64], unadvertisedTruncated,
  skipped: [{ key, reason }], skippedTruncated,
  errors: [string], errorsTruncated,
  errorsSoft: [string], errorsSoftTruncated }
```

- Every list is capped to `MAX_LIST` entries with its `<name>Truncated` count; `downloaded` keeps the `MAX_LIST` smallest keys (sorted), the rest counted in `downloadedTruncated`.
- Strings are clipped to `MAX_LINE` chars (`errors`, `errorsSoft`) or `MAX_TOKEN_TEXT` chars (keys, reasons, `rejected`); a clipped string ends with U+2026.
- If the serialization still exceeds `MAX_SYNC_RESULT` bytes, `errorsSoft`, `errors`, `skipped` and then `unadvertised` are emptied in that order, each moving its whole length into its Truncated count, until it fits.
- `ok`, `peers`, `seeders`, `admitted`, `seederConfirmed` keep their meaning (protocol §6, `seederConfirmed` included).

## 7. Error codes

| Code | On the wire | Meaning |
| --- | --- | --- |
| `USAGE` | yes | bad request or bad params; too many pending (`'pedidos demais em andamento'`); duplicate id (`'id repetido'`); oversized response (`'resposta grande demais'`); a state conflict the user caused (sections 5.5 to 5.14) |
| `UNAUTHORIZED` | yes | no `session.open` yet, or a failed one |
| `LOCKED` | yes | the data dir is held by another process, or the node session is in its error state |
| `NOT_FOUND` | yes | no identity yet, unknown author |
| `INTERNAL` | yes | anything unexpected; always the generic message `'erro interno'`, never a path or a stack |
| `TIMEOUT` | no (client only) | no response within the client timeout |
| `CLOSED` | no (client only) | the connection was lost or the client closed |

- Messages are pt-BR, short and MUST never contain a filesystem path or key material (A6). The dispatcher enforces a backstop: a message that is not a string of 1..200 UTF-16 units, or contains `/` or `\`, or a run of 16 or more hex digits, is replaced by the generic message of its code (`USAGE` `'pedido inválido'`, `UNAUTHORIZED` `'não autorizado'`, `LOCKED` `'diretório de dados em uso'`, `NOT_FOUND` `'não encontrado'`, `INTERNAL` `'erro interno'`). An 8-hex `key8` is allowed.
- Exports: the seven codes as constants, `ERROR_CODES`, `WIRE_CODES`, `CLIENT_CODES`, `GENERIC_MESSAGES`, `MAX_ERROR_MESSAGE`, `class RpcError extends Error { code, uncertain }`, `isSafeMessage(message)`, `toWireError(err)` -> `{ code, message }` (never throws).

## 8. Server dispatcher (`createServerDispatcher`)

`createServerDispatcher({ handlers, send, token = null, onProtocolError = () => {} })` -> `{ receive(obj), emit(event, data), close(), opened, closed, pending }`, one per connection. `handlers` maps a method name to `async (params) => result`; `send(message, text)` delivers one envelope (`text` is its JSON serialization, for transports that want it). Throws `TypeError` for a missing `handlers` / `send` or an empty-string token.

`receive(obj)` (an already decoded envelope):

1. Validate the envelope and params (sections 1, 5). Invalid with a usable, not-pending `id` -> `USAGE` response with that id; otherwise (no usable id) `onProtocolError({ code: 'USAGE', message })`, and the transport MUST close the connection.
2. A pending `id` -> `USAGE` `'id repetido'` (the original request is not affected).
3. `session.open` -> section 4, answered here.
4. Not open yet -> `UNAUTHORIZED` `'sessão não aberta'`.
5. `MAX_PENDING` requests already in flight -> `USAGE` `'pedidos demais em andamento'` at once; the handler is not called.
6. No handler for the method -> `INTERNAL`.
7. Call `handlers[method](normalizedParams)` asynchronously. Its value (a plain object; `undefined` or anything else -> `INTERNAL`) is sent as the result, size-checked (`'resposta grande demais'`, section 2); a result that cannot be serialized -> `INTERNAL`. A throw or rejection becomes `toWireError(err)`: `err.code` if it is a wire code other than `INTERNAL`, with its message if that passes the section 7 safety rule; otherwise `INTERNAL` `'erro interno'`.

`emit(event, data)` sends `{ v: 1, event, seq: <next>, data }` only after a successful `session.open`; an invalid event (unknown name, wrong `data` keys) is dropped; an oversized one is replaced by `warning` `{ line: 'evento grande demais' }` with that seq. Returns `true` when the requested event was sent.

`close()` stops everything: later `receive`, `emit` and the responses of handlers still running are no-ops. A throwing `send` never breaks the dispatcher.

## 9. Client (`createClient`)

`createClient({ send, timeoutMs = 30000 })` -> `{ request(method, params = {}), receive(obj), on(event, fn), close(), closed, pending }`.

- `request` returns a Promise of the result. Before sending it validates the envelope and params locally (`USAGE`, nothing sent), enforces `MAX_PENDING` (`USAGE` `'pedidos demais em andamento'`, nothing sent) and `MAX_REQUEST` (`USAGE` `'pedido grande demais'`). Ids increase from 1, wrap after `MAX_ID` and skip pending ids.
- `receive(obj)` routes a response by id (an unknown id is ignored, and so is any response once its request timed out) and an event to the `on(event, fn)` listeners as `fn(data, envelope)` (a throwing listener is ignored). Returns `false` for anything ignored. `on` returns an `off()` function.
- An error response rejects with `RpcError(code, message)`, `uncertain: false`.
- Timeout (`timeoutMs`, per request) -> `RpcError` `TIMEOUT`; `close()` (connection lost) rejects every pending request with `CLOSED`; a `send` that throws rejects that request with `CLOSED`. For a mutating method these carry `uncertain: true` (it may or may not have happened); for a read `uncertain: false`. Requests made after `close()` reject `CLOSED`, `uncertain: false` (never sent).
- **Never resend**: the client never retries or resends a request on its own. After an `uncertain` failure the UI re-reads state (for example `log.read`, `follow.list`, `sync.status`) before offering the action again.
- `uncertain: false` on a non-mutating method means a repeat is safe, not that nothing changed. `dm.pull` (5.76), `dm.seen` (5.80), `group.seen` (5.82) and `age.proof` (5.83) write local state, and a lost answer may still have filed messages, marked a conversation or group seen, or stored an age attestation: the client re-reads `dm.list` (and the open `dm.thread`) after every attempt of `dm.pull` or `dm.seen`, `community.info` (5.59) after every attempt of `group.seen`, and `node.info` (5.2) after every attempt of `age.proof` (its age fields, not the `age.proof` answer, decide the age gate), success or failure, and after a reconnect. The group screen sends `upTo` of the newest row it painted (5.82); the re-read of `community.info` after every attempt stays.
- A request that timed out on the client may still be in flight on the server and still counts toward the server's `MAX_PENDING` until it answers.

## 10. Display rule (A8): `displayText(value, { multiline = false } = {})`

The single escaper the UI uses for EVERY peer-derived string (names, bios, post text, keys, reasons, event lines, error messages). Each unsafe code point becomes U+FFFD:

- C0 controls U+0000-U+001F, except U+000A (LF) when `multiline: true` (post text and bio only);
- DEL U+007F and C1 U+0080-U+009F;
- U+2028, U+2029;
- the bidi controls U+202A-U+202E and U+2066-U+2069;
- the direction marks U+200E, U+200F and U+061C (beyond `safe.js`);
- a lone surrogate U+D800-U+DFFF (records accept one, section 2; a well-formed surrogate pair is one code point and is kept).

This is the `isUnsafe` set of `packages/core/lib/safe.js` plus the three marks and lone surrogates. Non-strings are converted with `String()`; a value whose conversion throws gives `''`. Pure, total, never throws. The UI renders the output as plain text only.

## 11. Security rules

- IPC carries no token: the channel is private to the app process (the worklet is spawned by it). Its dispatcher is created with `token: null`. That is why the in-app web node's host controls (5.50 to 5.56, including the PRF output of `identity.install`) travel as IPC-only methods there, while the browser page reaches the same controls through the handle below. The recovery controls `identity.recoveryLookup`, `identity.recoveryOpen`, `identity.recoveryWrap` and `identity.recoveryBind` (5.91 to 5.94) exist only on that in-app web-node worklet. `identity.recoveryOpen`'s result carries the ORIGINAL root once, exactly as `identity.install`'s input does, so the host can call `identity.install` and seal the keychain session as today. No other result, event, error or log carries a PRF output, a wrapping `secret` or a recovery code, except `identity.recoveryWrap`'s `code` for kind `'code'` and `identity.recoveryOpen`'s `prf`; a wrapping passkey's PRF derives only `lookupId` and the wrap key, never a member key. The browser node's in-memory channel has no token either (`token: null`): it never leaves the page.
- The browser node is opened by `VarandaWebNode.start({ association, seederUrl })` (`packages/web-member/web/node.js`) before any RPC: it takes the exclusive Web Lock `varanda-node`, so a second tab of the same browser is refused (`'outra aba já usa o Varanda neste navegador'`, code `LOCKED`) before a session exists. The handle it returns exposes only `connect`, `close`, `identity` and `media` (frozen, no other member of the node is reachable from the page).
- The handle's `identity` API (the member's key comes from a WebAuthn passkey; `packages/web-member/web/node.js`): `identity.status()` -> `{ exists, publicKey, legacy, unlocked, synced, webauthn, prf, hybrid, platform, signal, rpId, rpIdError?, passkeyKnown, resumed, pending, refused }`, where `prf`, `hybrid` (the phone QR is available), `platform` (this device has a user-verifying authenticator) and `signal` (the browser can be asked to drop a passkey) are `'yes'|'no'|'unknown'`, `pending` is true while a creation waits for `complete()`, and `refused` is an array of `{ userId, code, cleaned, created }` (no credential id) for the passkeys Varanda refused, where `created` is true when this page made that passkey (a creation or the `complete()` of one, even after a reload; false for a sign-in `NO_PRF`), but the screen never names a passkey for deletion from `refused`: a stored refusal may since have become the account on another device or browser, so it names only passkeys created in the current page session whose live failure came back with `cleaned` false, clears those names on any successful unlock and on `reset()`, and words the step as conditional ('Se você não usou essa passkey para entrar em outro aparelho, apague...'); `identity.unlock({ register = false, any = false, phone = false })` -> `{ publicKey, created, sessionSaved? }` or `{ pending: true }` (a creation whose PRF result needs a second step): `any: true` signs in with any Varanda passkey of this rp.id (a discoverable request, ignoring the stored record for that attempt only, which stays; `MISMATCH` still protects another key's diary), `phone: true` narrows the WebAuthn hints to `['hybrid']` (the phone QR) for that call only and is remembered on the pending creation, so its `complete()` sends the same hint (the default is `['client-device', 'hybrid']` on a creation and no hints on a sign-in); `identity.complete()` -> `{ publicKey, created, sessionSaved? }`; `identity.lock()` (zero-fills the keys in memory; reads still work; the stored session survives it, so the next start resumes); `identity.signOut()` ('Sair', below); `identity.reset()` (deletes the diary, this device's media cores, the stored passkey record and the stored session).
- The handle's recovery steps (`identity`, same file; the account service calls are the app's): `identity.unlock()` may also resolve `{ wrapped: true, lookupId }` when the passkey used is a marked wrapping passkey (by the user handle the authenticator returned, or by the bound record when the credential is the bound one): the app fetches the blob for `lookupId` and calls `identity.unlockWrapped({ blob, member })`, which for kind `'passkey'` installs the original root and resolves `{ publicKey, created: false, sessionSaved? }`, and for kind `'code'` verifies the blob and resolves `{ needsPasskey: true }`, holding the root in memory for 120 seconds at most. Only the fetch's HTTP 404 with the exact body `{ "error": "nao-encontrado", "recovery": true }` means "no entry"; any other 404, such as an older service's unknown route, is the service being unavailable, and in both cases the app calls `identity.cancelRecovery()` and the node stays locked. A passkey whose handle is not marked, including one that returned no user handle and is not the bound one, is installed directly as before and nothing is looked up at the account service: the original passkey opens the account without internet on any device, while an added passkey or the code needs the account service at every new sign-in ceremony (only a kept session avoids it). Limit: a non-compliant password manager that omits the user handle for an added passkey on a device where it is not bound makes that passkey open a separate, empty account there (`docs/protocol.md`, "Member recovery"); `identity.unlockWithCode({ code })` -> `{ wrapped: true, lookupId }` (the code never leaves the handle); `identity.finishRecovery()`, a user gesture, creates a new marked passkey, installs the held root bound to it and resolves `{ credentialId, userId, lookupId, blob }` for the app to register (the browser handle wraps the root under the new PRF before it installs, so no wrap fails after the install; an install that fails leaves the node locked and refuses the new passkey as `INSTALL_FAILED`, and a `cancelRecovery()` after the bind undoes the bind and the sealed session), or `{ pending: true }`, after which `complete()` returns that result; `identity.cancelRecovery()` zero-fills the held root and any derived key; `identity.addPasskey()` (unlocked) creates a marked passkey and resolves `{ credentialId, userId, lookupId, blob }` or `{ pending: true }` (then `complete()` returns the add result); `identity.bindPasskey({ credentialId, userId })` rebinds this device's stored record to that passkey ('Trocar a passkey'); `identity.makeRecoveryCode()` (unlocked) -> `{ code, lookupId, blob }`. The discoverable sign-in stays `identity.unlock({ any: true })`. None of these return values carries the root or a wrap key; `code` appears only in `makeRecoveryCode`'s result.
- Staying signed in (`packages/web-member/lib/session-store.js`): after a successful unlock, and only then, the passkey's 32-byte PRF output (the root every member key is derived from) is stored in its own IndexedDB database `'varanda-session'` as ONE record `{ v: 1, rpId, credentialId, publicKey, iv, ciphertext, key }`: sealed with AES-GCM-256 under a fresh 12-byte IV and a `CryptoKey` generated with `extractable: false`, the additional data `'varanda/session/v1\n' + rpId + '\n' + publicKey` binding it to this rp.id and this identity. `start()` reopens it with NO WebAuthn call when the stored passkey record is for this rp.id, the stored diary exists and is not legacy, and the record names the same passkey and public key; then `status().resumed` is `true`. Loading fails closed: any problem (another version, rp.id or key, a malformed field, a failed decryption, an IndexedDB error) clears the record and leaves the node locked, so a transient IndexedDB error signs the person out once. A failure to save still unlocks, with `sessionSaved: false`. The stored session expires after 30 days without the app being opened: the passkey is then asked again, and every open refreshes the period. What it protects: the PRF output is never written in clear, no script can export the AES key, and the record alone, copied to another origin or identity, does not open. What it does NOT protect: the wrapping AES key lives in the same browser profile as the sealed PRF output, so a copy of the whole profile yields the identity until 'Sair' or 30 days idle; a script running on this origin can call decrypt with the stored key and act as the member (an XSS is a full compromise, as it already was while unlocked); and anyone holding the unlocked device or browser profile can post until 'Sair' or the expiry. This reverses the earlier rule that the key existed only in memory.
- The app's in-app web node (the native `web` kind) has the native counterpart of that stored session (`apps/app/src/sessionStore.native.js`, `apps/app/src/identity.native.js`): the host runs the passkey ceremony itself (`apps/app/modules/passkey-prf`, same rp.id and PRF input as the browser, `apps/app/src/passkeyOptions.js`), hands the PRF output to the worklet with `identity.install` (5.50), and after a successful non-resumed install, and only then, keeps `{ v: 1, rpId, credentialId, publicKey, prfHex, usedAt }` as one keychain item (`expo-secure-store`, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`: readable only while the device is unlocked, never synced to iCloud Keychain or backups) under a key naming the rp.id and the public key. Only a successful save calls `identity.sessionSaved` (5.55); a failed one still unlocks with `sessionSaved: false`. At start, with the connection up and NO ceremony, it calls `identity.install` with `resumed: true` when `identity.status` reports the diary exists, is not legacy, has the same public key and passkey and `signedOut` is false; a refusal deletes the item. The item yields the identity until 'Sair' or 30 days idle, with the same load rules as the browser record (another rp.id or key, a missing usedAt or one more than 1 day ahead fails closed and deletes it; every load refreshes the period). What it does NOT protect: anyone holding the unlocked device, or code running in the app, can act as the member until then. 'Sair' calls `identity.forget` (5.54) first, then deletes the item, rejecting `SIGNOUT_INCOMPLETE` with the node locked when the delete fails; `reset()` calls `identity.reset` (5.53) and deletes the item whatever the answer.
- 'Sair' (`identity.signOut()`) always locks. Two independent barriers make it stick: it first writes the kv marker `'signedOut'` in the node storage, which makes `start()` refuse (and clear again) any stored session until the next successful passkey ceremony saves a new one; then it deletes the record (and, if that fails, the whole `'varanda-session'` database). When both deletions fail it rejects with code `SIGNOUT_INCOMPLETE`, `'não foi possível sair por completo neste aparelho: tente de novo'`; the node is locked either way. `reset()` does the same.
- The handle's `media` API: `media.upload({ bytes, mime, width, height, kind?, ms?, sealed?, onProgress })` -> the descriptor a later `post.create` / `post.reply`, `group.post` or `profile.set` `avatar` carries. Images use `MEDIA_MIMES` and positive dimensions; only `{ kind: 'voice', mime: 'audio/mp4', width: 0, height: 0, ms }` admits audio, checked with `audioBounds`, with integer `ms` 1..120000 and at most 1572864 bytes. Voice descriptors include `ms` and are accepted only in chats; diary posts and avatars stay images. `sealed: true` returns the private group item of 5.56. Descriptors come only from `node.media.upload`; the core node never accepts one, but it may remove an avatar (`profile.set` with `avatar: null`, 5.6). It is a host control, not an RPC method, because one request is capped at `MAX_REQUEST` (64 KiB) and an item may be 8 MiB. `bytes` (1 byte to `MAX_MEDIA_ITEM_BLOCKS * MEDIA_BLOCK_BYTES`), `mime` and the dimensions are checked and the bytes copied synchronously; then, serialized with the RPC requests: the identity must be unlocked with a media key and block 0 must exist (`'grave o certificado de membro antes de publicar'`), the SHA-256 is computed (WebCrypto), and the item is stored in this device's media core in `MEDIA_BLOCK_BYTES` blocks. The first upload of a device's media core first declares the core in the diary (one `media-core` record through the write gate and a push, so it needs the seeder) BEFORE any byte of the item is stored, so a failed first upload stores none of it; later uploads into a declared core need no network until the post. `onProgress` hears `0.25`, `0.75` and `1`; errors keep their `code` and `message`. Nothing about the bytes is logged.
- The handle's `follows` API (host controls, unlocked only, block 0 required): `follows.legacy()` -> `{ keys }`, the follows this device kept from before `follow` records existed that neither a `follow` record of the own diary nor a verified pending change mentions (sorted, at most `MAX_INVENTORY - 1`; `[]` once decided; an empty set marks the device done); `follows.confirmLegacy(keys)` -> `{ published }`: each key in both `keys` and that set is queued as a signed `on: true` change (appended by the drain under the replay rule of 5.9), every other legacy key leaves this device's list, and the device is marked done. `keys` must be at most `MAX_INVENTORY - 1` lowercase hex64 strings (else `TypeError('chaves inválidas')`); keys outside the set are ignored; errors keep their `code`. The app shows them as the Seguindo card "Pessoas que você seguia neste aparelho" (`docs/app.md`).
- Media keys: one media core per DEVICE, signed by a key pair derived from the PRF output and the per-device nonce of kv `'mediaDevice'` (protocol §1 "Web member storage"); the pair is handed in with the identity pair (`setKeyPair(pair, { media })`), lives only in memory and is zero-filled with it. A media core holds at most `MAX_MEDIA_BLOCKS` blocks / 256 MiB; when it is full uploads fail with `'espaço de fotos deste aparelho esgotado'` (no rotation yet). The app calls `media.upload` only when the person presses Publicar (attached photos stay in the page's memory until then); once called, the stored bytes are public and permanent in the core even if a later upload or the post fails, and then stay unreferenced.
- Replication of the own media cores: they are opened read-only (lazy storage) and replicated only on the verified seeder link, next to the diary; never announced, never downloaded into, never part of the goals. Push confirmation (the sync event `media-pushed`, diagnostic only, no line): a block counts as held when it is below the seeder peer's advertised contiguous length OR was served to it on this link (Hypercore 10.38.2 has no core-level remote length and the seeder does not re-advertise ranges it downloaded from us); "served" means sent with its proof, not proven stored. Once runs never wait for media; the app keeps a continuous run, which is where the confirmation arrives. Errors carry a `code`: `UNSUPPORTED`, `NO_PRF`, `NOT_SYNCED` (the authenticator data of a new passkey says it is not backup eligible: bound to one device), `CANCELLED`, `EXISTS`, `WEBAUTHN`, `MISMATCH` (the stored diary belongs to another key; `legacy: true` for a store from before the passkeys, whose stored secret the node wipes on its first open, after which the diary stays readable and is never writable; only `reset()` removes it) and `LOCKED` (another ceremony in flight); a `NO_PRF` or `NOT_SYNCED` from a passkey that exists anyway also carries `credentialId` and `userId` (hex), and, when the `register` ceremony of this page load just created that passkey (never a `complete()`, since by then a synced passkey may already be the account on another device; never a sign-in, never a creation restored after a reload, never the stored passkey), `cleaned`: true when the browser accepted the request to drop it (`PublicKeyCredential.signalUnknownCredential`), which means the browser was asked, not that the passkey was deleted. `NONE` (no passkey on the device) is a native-only code (`apps/app`), never raised by the browser handle. These are the handle's own errors, not RPC error codes (section 7). The kv entry `passkeyAttempts` (`{ v: 1, rpId, pending: { credentialId, userId, phone } | null, refused: [{ credentialId, userId, code, cleaned, created }] }`, no secret; `refused` keeps at most 32 entries: the cap evicts the oldest entries other than a `NOT_SYNCED` one with `created` true, and keeps only the newest 32 of those when they alone exceed it, `code` is `NO_PRF`, `NOT_SYNCED`, `SUPERSEDED` for a pending creation replaced by a newer one, `ADD_PENDING` for a recovery passkey creation (`addPasskey` or `finishRecovery`) that answered `{ pending: true }`, written at once because that pending creation lives in memory only (`created` true, `cleaned` false, never signalled for deletion; after a reload it keeps the passkey excluded from later creations and is never offered for `complete()`; a successful `complete()` or `bindPasskey` drops it), or `INSTALL_FAILED` for a new passkey whose PRF came with the creation but whose install failed (`MISMATCH`, `CANCELLED`, a storage error) while an older creation was pending; an entry stored without `created` reads as `created: false`) keeps the pending creation and the refused passkeys across reloads; a record for another rp.id reads as empty, and a stored `credentialId` that is not strict base64url (only `[A-Za-z0-9_-]`, non-empty, length % 4 not 1) is dropped on load. A creation that replaces a pending one supersedes it only once the new passkey is bound: when its install fails the older pending stays, so `complete()` still reaches it. A `{ pending: true }` answer made stale by `lock()`, `signOut()` or `reset()` during its write rejects `CANCELLED` instead, and a pending cleared by `reset()` is never written back. Refused ids are excluded from every later creation but never refused at sign-in, with one exception: a passkey this page created and refused as `NOT_SYNCED` (`created` true) is refused at sign-in too, with `NOT_SYNCED` carrying `credentialId`, `userId` and `cleaned: false`, its PRF output zeroed and nothing installed, while every other passkey, including one refused at sign-in for `NO_PRF`, keeps signing in; such a `NOT_SYNCED` entry is never rewritten to another code by a later failure of the same passkey, and a creation whose authenticator hands back that same passkey (ignoring `excludeCredentials`) is refused the same way, the entry kept. A ceremony's refusal bookkeeping (the entry, its write and the request to drop the passkey) runs before the ceremony lock is released, so a ceremony started meanwhile is refused with `LOCKED`. A successful unlock clears `pending` and drops its own id from `refused`; when it used another passkey than the pending creation, that creation moves to `refused` as `SUPERSEDED` (`created` true, `cleaned` false, no request to drop it) instead of being forgotten; `reset()` keeps the `NOT_SYNCED` entries with `created` true (they describe this browser's password managers, not the account) and clears `pending` and every other refused entry: it writes the entry with only those kept entries (`null` when none) before anything else and rejects with the storage error, changing nothing, when that write fails; a ceremony that began before a `reset()` and fails after it records nothing; `signOut()` keeps it.
- Writes need the key: `cert.add`, `profile.set`, `profile.delete`, `username.add`, `post.create`, `post.reply`, `post.quote`, `post.delete`, `like.set` and `repost.set` fail with `USAGE` `'identidade bloqueada: entre com a passkey'` while the identity is locked (and `NOT_FOUND` `'identidade não encontrada'` with no identity); with a key that does not match the stored diary, `USAGE` `'passkey não corresponde ao diário guardado'`; when the catch-up with the seeder cannot confirm the diary is current (no answer within 15 s, an inventory that completed only by timeout, or the client detached meanwhile), `USAGE` `'sincronize com o semeador antes de publicar'` (or `'conexão encerrada'`) and nothing is written. Each of them first catches up with the seeder (`sync.event` line `'sincronizando antes de publicar'`) and then pushes (`'enviando ao semeador'`); both are internal runs that emit the usual `sync.started` / `sync.event` / `sync.stopped` (`once: true`). Other lines the session may emit: `'diário próprio sincronizado (<n>)'`, `'diário próprio atrasado (<n>/<m>)'`, `'certificado recuperado do semeador'`. `identity.create` and `follow.*` are not gated (the browser node's follow drain runs the gate itself, 5.9); `follow.*` still needs the identity unlocked on the browser node.
- Results never carry a secret: the key pairs (identity and media) exist only inside the session (set by the handle's own `identity` code, zero-filled on lock, sign-out, reset and close), and no RPC result, event or `identity` return value contains them. The only secret at rest is the sealed PRF output of the stored session above (with its wrapping key in the same browser profile).
- The WebSocket is `varanda-serve`'s job (T7): it binds loopback only, checks the `Host` and `Origin` headers, requires a token in `session.open` (high-entropy, compared with `tokensEqual`), rejects binary frames, parses with `parseMessage(text, MAX_REQUEST)` and drops a client whose queued outbound bytes exceed `MAX_OUTBOUND`.
- `tokensEqual(a, b)` is constant-time over the longer length: no early exit on the first difference or on a length mismatch; a length mismatch or a non-string gives `false`.
- Results and messages never carry a filesystem path, a secret key, the bootstrap list or the DHT host (section 5.2, section 7).
- Conversas (5.73 to 5.81, 5.88): every `text`, `preview` and `quote` in a `dm.*` result is peer text, signed but chosen by the sender, and goes through `displayText` (section 10) before it reaches the screen. No `dm.*` result or event carries the box secret key, the local storage key, a stamp or a drop. A media item's blob `key` appears only in a `dm.thread` or `dm.putMedia` result (and in the `dm.send` params that carry it back); no event, error message or log carries it.
- Any protocol error (section 3, a failed `session.open`, an envelope without a usable id) closes the connection; nothing is resent.

## 13. Known limits (v1)

- `diary.peek` exists only on the browser node and only while a verified seeder link is live (5.27); the core node reads local data only.
- `push.sign` is browser-only (5.31): the core node, `varanda-serve` and the CLI answer `USAGE` `'assinatura disponível só no navegador'`.
- `age.sign` is browser-only (5.32): the core node, `varanda-serve` and the CLI answer `USAGE` `'assinatura disponível só no navegador'`. Native and `varanda-serve` members keep the operator certificate path (`assoc certify`).
- `feed.read` and `log.read` page BACKWARDS only, with `before` (5.12, 5.13); there is no forward or `since` paging (newer data needs a reload of the newest page). The page maxima are 31 items and 36 blocks (lowered from 35 and 42 when posts gained media). `follow.list` pages with `offset` and `limit`.
- The app treats a missing `incomplete` field as not syncing (an older node), and `incomplete` is relative to the length the node knows locally: a diary nobody serves is not reported.
- The page maxima are derived from the worst case of section 2 (lone surrogates at every record limit, 4 maximal descriptors per post). Ordinary pages are far smaller; the maxima only guarantee that no page a peer can craft exceeds `MAX_MESSAGE`.
- `peek.read` (5.22): cost grows linearly with the number of admitted diaries (the page deadline and byte budget mark the page `incomplete`). Names are best effort: a profile or username outside blocks 1-2 and the fetched tail reads as 'sem nome' or the older handle. `at` is author-supplied. Rows already shown are not retracted when a new blocklist arrives until the next request (as `feed.read`). Candidates are fetched in a random order per snapshot, so a deadline or budget cut falls on random diaries.
- `peek.read` capacity: the peek link is one extra short-lived external socket per page; the seeder admits at most `maxExternal` external sockets (default 32, `VARANDA_MAX_EXTERNAL` since #168; `packages/core/lib/seeder.js`) and every hosted member already holds one for its sync, so with ~30 hosted members online a peek can be refused: a full seeder closes the socket with WebSocket code 1013 and the read fails with `USAGE` `'Semeador ocupado; tente novamente em instantes.'` (the person retries; a close without a frame stays `'sem conexão com o semeador'`). Measured on loopback with the production caps (64 total, 32 external): 40 member links give 32 admitted and 8 refused, and a peek while the 32 slots are held fails in 2-5 ms. A peek link holds its slot about 10-20 ms on loopback (each network round-trip adds to that). With the lease off (6.1) every visible hosted page holds its sync slot for as long as it is visible, so size `VARANDA_MAX_EXTERNAL` to the concurrent visible tabs plus room for these short links. The Espiadinha still costs a short extra external slot per page while it loads, by design, because it never rides the sync link (5.22, privacy); reusing the sync link for the peek was considered and rejected for that reason.
- `notices.list` (5.28) capacity: each read opens one extra short-lived external socket, like a peek, against the same `maxExternal` = 32 of the seeder, so a busy seeder can refuse it (`USAGE` `'Semeador ocupado; tente novamente em instantes.'` after a 1013 close, 1-3 ms measured on loopback; the app polls every 5 minutes and tries again). The read is still one socket even though it attaches three channels (`'varanda/notices/3'`, `'varanda/notices/2'` and `'varanda/notices/1'`) to it, and the post index (protocol "Notices channel v2") is separate from the follow index and also in memory only. A seeder keeps its notices index in memory only, rebuilt from block 1 whenever a diary is served, with at most 4096 followed targets per author and 262144 fold entries in total (protocol "Notices channel"); beyond a cap the pages are `incomplete`.
